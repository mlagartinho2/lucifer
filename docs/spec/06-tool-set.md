### 6.1 Edits: find/replace blocks

Edits are expressed as find/replace blocks — never full-file rewrites, never line-numbered diffs.

```python
class EditBlock:
    find: str
    replace: str
    replace_all: bool = False   # §6.1 — v0.21, Tier-2 checklist C9

class EditFileArgs:
    file_path: str
    edits: list[EditBlock]   # min length 1 — see below for multi-block semantics
```

**Resolved (B4 deep dive):** a single `edit_file` call may carry more than one find/replace block against the same file — the old draft's shape, adopted after weighing it against real precedent (Claude Code's own `multi_edit` tool does exactly this; Desktop Commander's `edit_block` deliberately doesn't, preferring small single-block edits). Two mechanics make this concrete, neither specified by either draft: blocks apply **sequentially** within one call — block 2 matches against the file content *after* block 1 has been applied, not against the original — and the call is **atomic**: if any block fails to match (zero or ambiguous matches), none of the blocks in that call are staged, the call fails as a whole, and `details` reports which block index failed and why. This keeps the typed result envelope (§5.2) unchanged — one `ok`/`error_type` per call, with the per-block detail living in the already-generic `details` field, not a new envelope shape. The staleness check (§7.2) runs once per call, against the file's state before any block in the call is applied — sequential application among blocks within one call is the model's own edit pipeline, not external drift, so it isn't re-evaluated between blocks; a stale view fails the whole call before any block is attempted, consistent with atomicity.

**Considered and declined (B4 deep dive):** the strongest real-world precedent actually keeps two separate tools — a simple single-edit tool plus a dedicated batch one — rather than one tool taking a list. Not adopted here: it would mean an 11th tool, and §6's "10 tools, no others in v0" was a locked decision at the time (widened since, at v0.69, for a different reason — see §6.6 and the Widened note at the top of §6), not an open gap like the rest of B4 — the marginal schema-ergonomics benefit of a dedicated batch tool over a one-element list didn't clear the bar for revising something locked. Recorded here so it isn't silently re-proposed later without the reason it wasn't adopted being visible.

**ASSUMPTION (unspecified mechanics):**
- If a block's `find` matches zero times in the current server-known content → `SELF_CORRECTABLE` / `FIND_BLOCK_NOT_FOUND`.
- If a block's `find` matches more than once and `replace_all` is `false` → `SELF_CORRECTABLE` / `FIND_BLOCK_AMBIGUOUS` (the model is expected to supply more surrounding context to disambiguate). ~~Whether an occurrence-index or replace-all option should exist at all is still an open design question this draft resolves conservatively (no) pending confirmation — separate from the block-multiplicity question above, which is now resolved.~~

**Resolved (v0.21, Tier-2 checklist C9 — closes §13 item 14's remaining half):** `EditBlock` gains a `replace_all: bool = False` field. With it left at its default, behavior is unchanged from every earlier draft of this spec: a block whose `find` matches more than once fails with `FIND_BLOCK_AMBIGUOUS`, full stop — there is no mode where the tool picks an occurrence on the model's behalf (first match, closest match, or otherwise); the model must either narrow `find` with more surrounding context until it's unique, or set `replace_all=true` to declare, explicitly, that every occurrence should be replaced identically. When `replace_all=true`, a multi-match `find` is expected rather than an error, and all matching occurrences within that block's scope are replaced; this doesn't change §6.1's existing atomicity or sequential-application mechanics — it only changes what counts as a successful match for one block. Occurrence-index addressing (letting the model target, say, "the 2nd match") is declined outright, not left open: no real precedent for it was found in any of the systems researched, and it's the weaker design on its own terms — a positional index can silently point at the wrong occurrence once an earlier block in the same call has already changed the file (a live possibility given §6.1's own sequential-blocks semantics), where "more context" and "all of them, explicitly" both stay unambiguous about intent regardless of what else in the file has shifted. Grounded in real precedent for the adopted half: Claude Code's own multi-edit tool — already cited above for the block-multiplicity question — carries exactly this `replace_all: bool` field, and a live GitHub issue against it (#3337) shows the actual error message it throws for the unset-default case: "Found 2 matches of the string to replace, but replace_all is false. To replace all occurrences, set replace_all to true. To replace only one occurrence, please provide more context to uniquely identify the instance." — the same shape adopted here.

**Resolved (v0.31, Tier-4 checklist C31):** for a failed multi-block call, `details` carries `failed_block_index: int` (0-based, into `edits`) and `total_blocks: int` always, plus a per-error-type field — `find_preview: str` (the failing block's own `find` text) for `FIND_BLOCK_NOT_FOUND`, or `match_count: int` (how many occurrences were found) for `FIND_BLOCK_AMBIGUOUS`. This follows the same discipline §5.2's output-truncation resolution already established for this field: a fact otherwise only stated in prose (Claude Code's own real ambiguous-match error text above embeds "Found 2 matches...") gets pulled out into a structured, model-readable field instead. `failed_block_index`/`total_blocks` are included deliberately even though the two most architecturally comparable real precedents don't have them: decompiling Claude Code's own `MultiEdit` tool shows its failure payload (`result`/`message`/`errorCode`/`meta.actualOldString`) never identifies which array position failed at all — the model has to recognize its own search text inside the message — and Aider's SEARCH/REPLACE editor works the same way, identifying a failed block by echoing its content back rather than by position. Both skip an index because their error paths are less structured to begin with, not because an index is undesirable; Lucifer's own `details` field is already typed and structured everywhere else in this spec, the harness already knows the failing index for free from its own sequential-apply loop (above), and handing it over directly is strictly easier for the model than making it re-derive the same fact by text-matching. The one genuinely different real precedent, Roo-Code's `multi-search-replace`, does report failures by array position — but its mechanism is non-atomic (whichever blocks match get applied, failures reported per-index in an array), a structurally different design from this spec's own atomic all-or-nothing one, so it's supporting evidence that an index-based design is viable, not a design to copy wholesale.

**Considered and declined (v0.31, Tier-4 checklist C31):** a fuzzy closest-match suggestion for the not-found case, the way Desktop Commander's `edit_block` computes a similarity score against real file content. Real precedent, but from a single-block tool with a different design ethos — neither of the two more architecturally comparable ones (Claude Code's `MultiEdit`, Aider) compute one in their model-facing payload either, and adding it here would mean inventing a similarity-matching mechanism nothing else in this spec needs, for a v0 draft's first pass at this field. Not ruled out for a future version, just not built for this one.

### 6.2 `run_command`

```python
class RunCommandArgs:
    argv: list[str]              # executed directly, no shell interpretation, ever
    cwd: str | None = None       # relative to repo root; None runs from repo root
    network: Literal["none", "restricted"] = "none"
    timeout_seconds: int
    expected_outputs: list[str] = []   # generated paths to capture even if normally excluded as build noise
```

- `argv` is a list executed directly — never a shell command string. No shell interpolation, globbing, or piping.
- Network access defaults to `none`. `restricted` mode routes through an explicit host allowlist. There is no "unrestricted internet" mode.
- Runs with a default-deny environment-variable allowlist — the parent process's environment is never inherited wholesale.
- Command policy is allowlist-first. Within that, git's mutating subcommands (`reset`, `clean`, `checkout`, `restore`, `rm`, `stash`, `gc`, `filter-branch`, `push`) are explicitly blocked even though git itself is allowlisted; read-only git (`log`, `blame`, `diff`, `show`, `status`) stays allowed. **Resolved (v0.18, Tier-1 checklist C5 — closes §12 item 8):** `push` was added to this list as defense-in-depth, independent of whatever `restricted` network mode (below) ends up allowlisting. The original blocklist protected only the sandbox's own disposable state, which barely mattered since `run_command` never reaches the real repo directly (§7.3) — but if `restricted` mode's host allowlist ever includes the org's git host, an unblocked `push` (especially `--force`) could reach real upstream and clobber shared history, a genuinely irreversible action in a different risk class from anything else this list addresses. Blocking the whole subcommand, not just `--force`, matches this list's existing granularity (every other entry blocks a subcommand outright) and costs nothing: none of `run_command`'s legitimate uses — tests, builds, lint, read-only git — ever need to push.
- Timeout kills the entire process group, not just the top-level PID (prevents orphaned children from surviving a timeout).
- `expected_outputs` names specific generated paths to capture even if they'd otherwise be excluded as build noise by the sandbox change-detection pipeline (§7.3) — but this can never override the sensitive-path exclusion (§7.4). A path that's both in `expected_outputs` and sensitive is still excluded.
- Executes against the synced sandbox copy of the repo (§7.3), never the real repo directly, and never a purely in-memory simulation.
- **Resolved (self-audit A2):** the sandboxed process has exactly one read-write mount — the sandbox directory itself — with everything else in its filesystem view, if anything, strictly read-only; that some such boundary exists is not optional, since §5.1's `SELF_CORRECTABLE` categorization for `PATH_OUTSIDE_REPO`/`COMMAND_NOT_ALLOWLISTED` depends on a real second gate existing behind the pre-execution check. What else is mounted read-only, and the sandbox directory's own internal read-only carve-outs, are specified concretely below (v0.36, C37).
- **Resolved (v0.18, Tier-1 checklist C1 — closes §13 item 26):** that boundary is backed by Linux namespaces + `seccomp` (`bubblewrap`-style: unshared mount/PID/network namespaces, a syscall filter, and a read-only-by-default filesystem view with an explicit bind-mount allowlist exposing the sandbox directory read-write on top — the literal list is below, v0.36/C37) — the same mechanism both OpenAI's Codex CLI (`bwrap` + `seccomp` on Linux) and Claude Code's own sandboxing use for this identical workload, not a heavier container runtime or a full VM. Two facts specific to this deployment made that the right call rather than reaching for something stronger: sandbox hosts are confirmed Linux-only (matching the precedent directly — no cross-platform Seatbelt/Windows-AppContainer handling to design for), and each session already runs on its own dedicated host/VM rather than a shared multi-tenant pool, which removes the one reason to consider something stronger (gVisor, for the cross-session blast-radius risk a shared pool would create). With that reason gone, the residual risk is a kernel-level exploit escaping the namespace to compromise its own already-disposable, single-session host — a risk both Codex and Claude Code accept as reasonable for this exact class of workload (LLM-suggested shell commands), and this draft accepts it too rather than reaching past real precedent for a threat model that doesn't actually apply here. Confirmed headroom on per-session overhead means cost isn't why gVisor was declined — it's declined because, once the shared-host argument is gone, the two closest production analogues already answer this question and nothing in this deployment's own shape argues for going further. If Lucifer's hosting model ever shifts to shared multi-tenant pools, gVisor is a documented upgrade path at that point: it sits at the same conceptual layer (syscall-level sandboxing), so §7.3's sync model above it wouldn't need to change.
- **Resolved (v0.36, Tier-4 checklist C37):** the literal configuration, not just the mechanism class. Three namespaces are unshared unconditionally — user (`--unshare-user`), PID (`--unshare-pid`) — plus network (`--unshare-net`) specifically when `network="none"`; left shared, but seccomp-restricted, when `network="restricted"`, since a proxy-routed path still needs a route out. The bind-mount list: the root filesystem is read-only by default (`--ro-bind / /`), including standard system paths (`/bin`, `/usr`, `/etc`, shared libraries) so the sandboxed process can still find its own toolchain — self-audit A2's original phrasing ("only writable *and* readable mount is the sandbox directory") is corrected here to mean only *read-write* mount; other paths are readable but not writable, which running any test/build/lint command already requires. The sandbox directory (the synced repo copy, §7.3) is bound read-write on top of that read-only base — and within it, every path already matching `is_sensitive_path`'s starter list (§7.4), `.git/**` included, is re-bound read-only, a second gate alongside the already-locked git-mutating-subcommand blocklist (§6.2) rather than a replacement for it: that blocklist only restricts which `argv` gets dispatched, not what the dispatched process's own file writes touch, so nothing before this closed the gap of a non-git command reaching into `.git/` directly. Seccomp, applied after the mount/namespace view is established (`PR_SET_NO_NEW_PRIVS`, then the filter): unconditionally denies `ptrace`, `process_vm_readv`/`process_vm_writev`, and the `io_uring_*` family; in `network="restricted"` mode, additionally blocks every socket family except `AF_UNIX`, so egress only ever happens through whatever proxy/allowlist mechanism that mode ends up using. Adopted close to verbatim from OpenAI Codex CLI's own real Linux sandbox — the most architecturally comparable precedent (Rust CLI agent, same bubblewrap-primary/Landlock-legacy-fallback design already cited for C1) and the most granularly documented at exactly this level, down to the specific unshare flags and the specific denied syscalls; Claude Code's own real sandbox independently converges on the same overall shape (bubblewrap subprocess, allow/deny path lists, seccomp) without publishing quite this level of syscall-by-syscall detail, corroborating the direction without supplying the literal list itself.
- **Resolved (self-audit A4):** every path-like `argv` element, plus `cwd` when given, is checked against the shared `is_within_repo_root` predicate (§7.4) before dispatch; a path resolving outside the sandbox root is `SELF_CORRECTABLE` / `PATH_OUTSIDE_REPO` (§5.1).
- **Resolved (consistency check, A2/A3):** the same `argv`/`cwd` paths are also checked against `is_sensitive_path` (§7.4) before dispatch, not just `is_within_repo_root` — closing a real gap this pass found: as previously written, only the repo-boundary predicate was wired into `run_command`'s pre-dispatch check, so a command like `cat .env` would resolve inside the repo root and pass that check even though the identical path would be blocked outright from `edit_file`/`create_file`. A path matching `is_sensitive_path` is `SELF_CORRECTABLE` / `SENSITIVE_PATH_BLOCKED` (§5.1), the same category `edit_file`/`create_file` already use for it — no new error type needed, just a missing wire-up.

**Resolved (§12 item 13 deep dive, resource limits — cross-check A3):** CPU/memory/disk/process-count ceilings are enforced by whichever isolation primitive backs the sandbox boundary, using that layer's own native mechanism, not a bespoke limiter this spec invents. Checked against real precedent before assuming this needed new machinery: an independent technical comparison of Claude Code's and OpenAI Codex's actual sandbox internals found that *neither* enforces memory, CPU, or process-count limits at the sandbox-tool layer at all — Codex's own design explicitly treats these as "expected at a higher level," and Claude Code implements only the wall-clock timeout this draft already has locked (`timeout_seconds`, process-group kill, above). That's not a gap in either system; it's a deliberate boundary between what a tool executor owns and what the hosting layer owns, and this draft adopts the same boundary rather than a more elaborate one neither real precedent actually needs. **Resolved (v0.18, Tier-1 checklist C1):** with the primitive now chosen (bubblewrap + seccomp, above), this is concretely cgroups: `bubblewrap` itself doesn't set resource ceilings, but it runs inside whatever cgroup the harness places it in before exec, so CPU/memory/PID limits are a cgroup-v2 slice applied at process launch — the same underlying mechanism a container runtime would use, just invoked directly rather than through a runtime's own abstraction over it. This resolves *what enforces the numbers* and, now, *which primitive is chosen*; real per-limit numeric values remain placeholders (§13 items 48–49, unchanged).

**Resolved (§12 item 13 deep dive, allowlist worked example — cross-check A3):** beyond git's already-locked read-only/mutating split (above), this draft proposes a starter allowlist of common non-git build/test/lint invocations for a few mainstream ecosystems (e.g. `npm test`, `pip install -r requirements.txt`, `pytest`, `pylint`) as an illustrative, per-repo-configurable starting point — the same status as `is_sensitive_path`'s own starter list (§7.4). This is deliberately given with a caveat real research argues is necessary, not optional: an analysis specifically of allowlisting for coding agents shows that "safe-looking" dev tools are often *not* safe to allowlist by name, because they're designed to execute project-authored code, not resist a malicious or wayward one — `go test`/`go generate` run arbitrary code the agent can plant via the files under test; `eslint`'s own JS-based config format accepts an injected `execSync` call; `pnpm run`/`make` execute whatever `package.json`/`Makefile` says; Docker access is close to host-level access outright. None of that is a gap in this draft's design, though — it's confirmation that the command allowlist was never meant to be the actual security boundary here, and this draft already resolved that the sandbox mount is (v0.2, above): the same research states the general principle back almost verbatim — "the operating system enforces the sandbox boundary on the running process, so it holds regardless of what the model chose to run and even if an allowed command does more than its name suggests." The worked list is useful as a starting policy; it is explicitly not, by itself, the thing standing between a compromised trajectory and the real repo.

**Further resolved (v0.58, Tier-3 checklist C20):** the worked example is broadened from two ecosystems to five, still explicitly illustrative and per-repo-configurable — this item was checked first for whether any real production coding-agent tool ships a curated, per-ecosystem default command allowlist worth adopting wholesale, and none do: OpenAI Codex CLI's sandboxing is pure filesystem/network isolation with no built-in command allowlist at all (commands are only optionally gated by user-authored rules, no shipped defaults); Claude Code's permission system is entirely user-configured glob patterns, its own docs giving only a few scattered examples rather than a maintained list; and `cplt`, a real open-source sandbox wrapper for coding agents, auto-discovers installed tools and allowlists environment variables/paths rather than curating commands at all. That's a real finding in its own right — it cross-checks, against three independent tools rather than the one study originally cited, that this item's own "per-repo config, not a fixed universal policy" framing was already the right call — but it also means there's no single real value to adopt the way other Tier-3 items had; this stays data an operator supplies per repo. What real research could usefully ground instead is broader, better-cited coverage for the worked example itself: GitHub's own official "Building and testing" documentation, a directly authoritative per-language source, adds three ecosystems taken verbatim from its guides rather than invented — Java (`mvn test`, or `mvn verify` for the full build-and-test lifecycle), Go (`go build ./...`, `go test ./...`), and Rust (`cargo build`, `cargo test`) — alongside the existing npm/pytest examples. The build-time-arbitrary-code caveat already given for `go test`/`eslint`/`make`/Docker is extended to cover the same risk in the newly added ecosystems, not glossed over: Maven and Gradle's plugin/lifecycle systems execute arbitrary JVM code as part of an ordinary build, and Cargo's `build.rs` executes arbitrary Rust code before compilation even starts — the identical shape of risk, reinforcing rather than undermining why the sandbox mount, not this list, is the real boundary.

Symlink handling for this section's own argv/`cwd` check is resolved alongside the predicates themselves — see §7.4.

### 6.3 `get_diagnostics`

**Resolved (v0.24, Tier-4 checklist C25 — closes §13 item 15):** sandbox-tool-based, not a live language-server client. `get_diagnostics` shells out to whatever language-specific tooling the repo already has — its own linter, type-checker, or compiler (`tsc`, `mypy`, `ruff`, `eslint`, `cargo check`, etc.) — through the same sandboxed execution path `run_command` already uses (§6.2/§7.3), parsing that tool's output into structured diagnostics. No new subsystem, no new process class to sandbox, and no dependency beyond what a repo's own build/lint tooling already provides.

Grounded in real precedent, including a genuine cross-check against a closer analogue than first considered: GitHub Copilot's cloud coding agent (an ephemeral GitHub Actions environment — the same headless, no-IDE shape Lucifer has) relies purely on shelling out to the repo's own tests/linters, with no LSP anywhere in it. GitHub Copilot CLI — the more architecturally similar product, since it's also a local, terminal-based agent with no IDE attached — does go further, independently spawning and managing its own per-language LSP server processes; that rules out "a CLI-only agent can't reasonably support LSP" as a categorical objection, but doesn't change the recommendation for Lucifer's v0, because of how and when Copilot CLI actually built it: it shipped for roughly eight months doing exactly what's adopted here — shell-out only, no LSP — and only added self-managed LSP support later, as an opt-in layer on top, with zero servers bundled and each language's server binary left for the user to separately install and configure. That sequencing — ship the shell-out mechanism first, treat LSP as a later, addable layer — is the shape adopted here.

**Considered and declined (for v0), documented upgrade path:** a genuine LSP-client integration — mirroring how gVisor was named a documented upgrade path for the sandbox isolation primitive (§6.2, Tier-1 checklist C1) rather than ruled out entirely — is not built for v0, for reasons specific to Lucifer's own deployment rather than a belief that it can't be done at all. Provisioning and keeping current a per-language server binary for every language Lucifer needs to support is a real, org-wide deployment burden that Copilot CLI's own "install it yourself" model doesn't remove, just relocates. A language server is also a long-lived child process, not a single command that runs and exits — running one safely means extending Lucifer's namespace+seccomp sandbox (§6.2, C1) to a meaningfully bigger surface than the "run one command, capture its output" shape `run_command` already handles. The resource cost is real and independent of who manages the server: rust-analyzer alone can use multiple gigabytes of memory, and JVM-based servers (`jdtls`) can take up to two minutes to cold-start — costs that don't disappear just because a CLI tool proved a server can be spawned independently of an IDE. Separately, Lucifer's verification gate (§3.4/§3.5, Tier-2 checklist C8) already runs the repo's real build/test/lint commands as the authoritative signal at `done` time — a sandbox-tool-based `get_diagnostics` is an earlier, cheaper preview of that same real signal, not a second independent subsystem, the same "earlier surfacing, not a substitute" logic already used for the risk-flag mechanism (§5.4, C7). If Lucifer's deployment shape ever changes in a way that makes provisioning per-language servers org-wide cheap (e.g., a shared base image with them pre-installed), LSP integration is a well-precedented, buildable enhancement to layer on top later — not a redesign.

### 6.6 Custom Agents & Skills

**Resolved (v0.69, Tier-4 checklist C55/C56/C57 — new, at your request; closes §13 items 70–72):** operator/repo-authored `.md` files can now define two new kinds of reusable configuration — **agents** (specialist personas) and **skills** (reusable, task-specific capability bundles) — matching the concepts named after GitHub Copilot's own current custom-agents/agent-skills feature set, cross-checked directly against its real, current documentation rather than assumed. A second, equally real precedent grounds most of the mechanism below: Claude Code's own subagent/skill convention — the very environment this spec-drafting session itself runs in, whose `.claude/agents/*.md` frontmatter shape is directly, first-hand verifiable rather than secondhand-researched. The two aren't competing conventions to pick between: GitHub Copilot's own current skill-discovery docs already recognize `.claude/skills` as an equally-valid path alongside its own `.github/skills`, confirming a real, converging cross-tool standard rather than two vendor-specific islands — this draft leans on that convergence rather than picking one vendor's shape arbitrarily.

Four architecture-defining forks were decided by you directly, not inferred, since real precedent for each genuinely diverges (Copilot's own docs, checked, don't settle any of them one way):

1. **Delegation model — both, gated by whether an agent is pinned at invocation.** If `--agent <name>` is given at invocation, that agent's persona governs the *entire* trajectory from the start — matching Copilot's own literal `--agent`/`/agent` mechanic exactly, no nesting. If no agent is pinned, Lucifer's default persona runs as usual, but the model may itself dispatch a bounded, nested sub-task to a specialist agent mid-trajectory and resume with its result — matching Claude Code's own real Agent/Task-tool mechanic instead. Both real precedents are adopted, not merged into one — they answer two different questions (what governs the *whole* session vs. what happens *mid*-session) that Copilot's own docs don't actually pit against each other either.
2. **Agent selection — the model can infer/switch**, not only the operator. This is a deliberate, named first for Lucifer: every other routing decision in this spec (`ESCALATION_PATH`, the triage heuristic, C2/§4.1) is operator-declared, never model-inferred, on the reasoning that a real classifier's judgment wasn't trustworthy enough to hand a *model*-selection decision to. Agent selection is a different axis, though, not a rerun of that same question: which underlying *model* runs is untouched — §4's routing/escalation machinery is completely unaffected by which persona is active (per fork 4, below) — so a model inferring "this sub-task calls for the security-reviewer persona" carries none of the risk the original C2 reasoning was guarding against (which model is capable enough to trust with the task itself). The two questions were only entangled by coincidence of both being "the model deciding something," not by any real shared risk.
3. **Skill activation — auto-discovery, matching Copilot's real mechanic**, not an explicit tool call. This is the one place this draft knowingly departs from its own long-standing "every mechanism is mechanical/typed, never a silent judgment call" discipline (§5.2's structured `details` fields, C43/C50's mechanical signals, this section's own dispatch-completion signal below) — named honestly as a real, deliberate exception, at your explicit direction, not a lapse. The *decision* to activate a skill is judgment-based; the *record* that it happened is not (below).
4. **No per-agent model field.** An agent restricts persona (instructions) and tool access; it never pins or overrides which underlying model runs it. `ESCALATION_PATH`/model routing (§4) stays the single source of truth regardless of which persona is currently active — matching Copilot's own real agent-profile schema (description/prompt/tools/MCP servers — no model field) more closely than Claude Code's own subagent `model` override, which this draft deliberately declines to adopt.

**Agent definitions.** A `.md` file with YAML frontmatter plus a markdown body (the persona's own instructions/system-prompt addition) — functionally identical to both real precedents; the `.agent.md` extension (Copilot CLI's own real convention) is adopted for the file's own name, but the frontmatter shape below draws more heavily from Claude Code's own more granular, directly-verifiable schema. Discovered from `.github/agents/` and `.claude/agents/` at the project level (both real, current paths — Lucifer recognizes either rather than picking one vendor, matching the same convergence reasoning as skills, above); a personal, user-level fallback (`~/.copilot/agents/`, `~/.claude/agents/`) is recognized too, but only meaningfully — this deployment's own dedicated-per-session-host, fresh-process-per-session topology (§1, v0.39) means a personal directory is populated and stable across sessions for the "developer's own CLI invocation" deployment shape, and simply absent/empty for the "container spun up fresh per CI job" shape; nothing in this mechanism requires it to be present, the same config-presence-gates-availability discipline already used throughout this draft (C48/C49).

```python
class AgentDefinition:
    name: str                        # required; lowercase, hyphens only — matches the file's own basename
    description: str                 # required; what this agent is for and when it should be used — the field the model's own selection judgment (fork 2) and the auto-discovery match (below) both read
    tools: list[str] | None = None   # optional allowlist, a subset of Lucifer's fixed tool set (§6); None inherits the full set. May include "dispatch_agent" itself, gating recursive spawning (below) — omitting it is the mechanism for opting a specific agent out, the same config-presence-gates-availability pattern C48/C49 already established, not a new one
    skills: list[str] | None = None  # optional; named skills to deterministically preload for this agent regardless of the auto-discovery match below — reconciles Claude Code's real explicit-preload `skills` field with Copilot's real auto-discovery mechanic, rather than picking one
    max_turns: int | None = None     # optional; a per-dispatch iteration cap tighter than whatever remains of the parent trajectory's own budgets (below) — real field, Claude Code's own `maxTurns`
    # instructions: the markdown body below the frontmatter
```

Declined outright, named honestly rather than silently omitted: `model` (fork 4, above — Claude Code's own real field, not adopted); `permissionMode`, `hooks`, `memory`, `mcpServers`, `isolation`, `background`, `effort`, `color`, `initialPrompt`, `experimental` (all real Claude Code fields, none adopted — each corresponds to a mechanism Lucifer doesn't have: no MCP integration anywhere in this spec, no lifecycle-hook concept, no cross-session persistent memory beyond C28's own per-session state, no background/async execution model anywhere in this architecture (the same fact just established for C54's index-build blocking), no git-worktree concept, and no separate permission-mode taxonomy distinct from this spec's own `UNSAFE`/risk-flag/suspend-resume model, §5.3–§5.5). `disallowedTools` (Claude Code's real denylist counterpart to `tools`) is also declined: Lucifer's tool set is small, fixed, and fully enumerable (unlike Claude Code's own open-ended, MCP-extensible universe), so a single allowlist is sufficient — a denylist would only ever restate the same information in reverse.

**Two runtime modes, per fork 1 above.**

*Persona-select* extends §10/C27's CLI invocation shape with a new `--agent <name>` flag (mirroring Copilot's own real, identical flag) — the named agent's `description`/instructions/`tools` restriction govern the whole trajectory in place of Lucifer's default persona, from the very first iteration. No nesting; this is the *only* mode available to the non-interactive/CI invocation (C27), since nested dispatch (below) presumes a model already mid-trajectory deciding to delegate, and a scripted, single-shot CI run has no such moment.

*Nested dispatch* is the new `dispatch_agent` tool (§6, table above), callable whenever no agent was pinned at invocation (the active persona is still Lucifer's default), or — per fork 2 — by an already-active named persona itself, subject to the depth cap below.

```python
class DispatchAgentArgs:
    agent: str      # must match a discovered AgentDefinition.name
    prompt: str     # the bounded sub-task's own delegation prompt
```

Mechanics, grounded directly in Claude Code's own real, current subagent behavior rather than invented:
- **Isolated sub-context, shared everything else.** The dispatched agent starts with a fresh transcript — its own instructions plus the delegation prompt, *not* the parent's own conversation history — matching Claude Code's real default (non-fork) subagent behavior exactly, and keeping the parent's own context/compaction budget (§8) unpolluted by the nested agent's turn-by-turn detail. It operates against the *same* Workspace instance (§7) as the parent — no per-agent workspace — since its edits, if any (governed by its own `tools` restriction), need to land in the same repo/session. Considered and declined: Claude Code's real "fork" mode (inheriting the parent's full history) — the less common of its two real options, and the one that would defeat the context-isolation benefit just named; not adopted for v0.
- **Shared budgets, not a second allocation.** Every iteration/token/second the nested agent consumes counts directly against the *same* `max_iterations`/`wall_clock_seconds`/`token_budget` totals (§3.2) the parent trajectory was already accumulating — no new budget dataclass, extending the identical "a slower, already-existing backstop is an acceptable trade-off for not adding new machinery" reasoning just used for C54's index-build blocking case. An agent's own optional `max_turns`, when set, additionally caps *that one dispatch's* own iteration count even with budget still remaining overall — a real, distinct Claude Code field (`maxTurns`), adopted as an extra, narrower safety knob layered on top of the shared budgets, not a replacement for them.
- **Risk-flag/suspend-resume stay persona-agnostic.** §5.4's triggers and §5.5's shared mechanism already key off Workspace state and the shared budget counters, neither of which cares which persona is currently active — so a nested agent's own mutating edit can trip the identical pause the parent's own edit would, with no new mechanism, and the pause surfaces to the human exactly as any other suspend does.
- **Counters reset on dispatch return, extending C44's own reasoning.** While a nested agent is active, its failures accumulate against the same tool-kind/verification-kind counters (§3.2) the parent was already using — one shared loop, temporarily following a different persona's instructions, not a second counter set. Completing a dispatch — successfully or not — resets both counters to zero for whichever persona resumes control next, extending C44's own justification for resetting on an escalate ("the failures belonged to the model just replaced, not the one taking over") to a persona swap: the failures belonged to the dispatched agent's own sub-goal, not to whatever the resuming persona does next.
- **No nested verification gate.** §3.4/§3.5's baseline-diff verification is a whole-trajectory, top-level-only concept — a nested dispatch's own completion is a simpler success-plus-summary or failure-plus-reason return, not a second `done`/verification pass layered underneath it.
- **Recursion, bounded.** A dispatched agent's own `tools` list may include `dispatch_agent` itself, permitting further nesting. `AGENT_DISPATCH_DEPTH = 3` — adopted directly from Claude Code's own real, current default (not invented for this draft) — bounds it; at the depth ceiling, `dispatch_agent` simply isn't included in the tool schema offered to that nested context, the identical "consult one more condition when assembling the tool schema" pattern already established for every registry-gated tool (C48/C49/C50), extended to a depth-gated one rather than a new kind of check. Omitting `dispatch_agent` from a specific agent's own `tools` list opts that agent out of spawning further, independent of the depth cap — also real precedent (Claude Code's identical mechanism).
- **Considered and declined: concurrent dispatch.** Claude Code's own real precedent supports genuine parallelism (up to 20 concurrent subagents). Declined for v0 — your own framing ("the main loop might decide to call a specialist... and gets a result back, then continues") is explicitly sequential, and concurrent dispatch would need concurrent Workspace access and concurrent budget accounting nothing else in this spec has, a materially bigger change than asked for. Named as a documented future extension, the same "seam kept, not built now" treatment already given the reranker (§9) and live LSP integration (§6.3).

**Skill definitions.** `SKILL.md` (exact filename required, matching both real precedents exactly), one per subdirectory, directory name equal to the skill's own `name`. Discovered from `.github/skills/<name>/`, `.claude/skills/<name>/`, `.agents/skills/<name>/` at the project level, and the personal-level equivalents under the identical deployment-shape caveat already named for agents — this list is adopted verbatim from GitHub Copilot's own real, current, multi-path discovery convention (itself already recognizing `.claude/skills`, the same convergence already cited above).
