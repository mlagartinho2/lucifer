## 1. Purpose & System Context

Lucifer is an in-house coding agent intended to be a functional equivalent of GitHub Copilot's agentic coding experience, built on the org's own model infrastructure rather than a third-party vendor.

- Models are served from the org's own GPUs or Azure — never local/CPU-only inference.
- Available models (registry, v0): `google/gemma-4-26B-A4B-it`, `openai/gpt5.4`, `openai/gpt-5.6-luna`, `ibm-granite/granite-4.1-30b`, `text-embedding-3-small`, `Qwen/Qwen3.6-27B`, `openai/whisper-large-v3`. `text-embedding-3-small` is the *active* embedding-role entry by default — `text-embedding-3-large` is equally reachable via the same direct Azure OpenAI subscription and fully cataloged with real specs (§2), config-switchable in place of it at any time, not merely a future candidate — see the v0.66 resolution in §2. `Qwen/qwen-embedding-8B` and `Qwen/qwen-reranker-8B` stay named in this spec's vocabulary as documented future candidates, not part of the live v0 registry — see the v0.65 resolution below.
  - **ASSUMPTION** (naming inference only, not a policy choice): `openai/gpt5.4`, `openai/gpt-5.6-luna`, `Qwen/Qwen3.6-27B`, `ibm-granite/granite-4.1-30b`, `google/gemma-4-26B-A4B-it` are general-purpose instruction/tool-calling chat models and are the candidate pool for triage/escalation (§4). `text-embedding-3-small` is retrieval-only (§9) and never appears in the triage/escalation pool — unlike every other entry here, it is not Gateway-routed; see the v0.65 resolution below and §2's `direct_endpoint` field. `openai/whisper-large-v3` is speech-to-text; nothing in the locked decisions gives it a role in a CLI-first, text-in/text-out agent, so it is listed in the registry but **out of scope for v0** pending an actual voice-input feature.
    **Narrowed in practice (v0.51, Tier-3 checklist C21 — §4.3):** `google/gemma-4-26B-A4B-it` remains an eligible candidate by this definition — it does support tool-calling — but is not actually included in the configured `ESCALATION_PATH`. See §4.3 for why.
  - **Resolved (v0.45, Tier-3 checklist C13):** confirmed against real code-level Gateway call strings, supplied directly — every registry entry actually carries a `<provider>/<model>` namespace prefix (`google/`, `openai/`, `ibm-granite/`, `Qwen/`) that this draft's earlier illustrative names omitted entirely; this was a real, structural gap, not just a casing detail, matching the real convention used by production multi-provider LLM gateways/routers (LiteLLM, OpenRouter both take a single `"<provider>/<model>"` string as the model identifier, not a bare model name). `ModelSpec.id` stays one combined string rather than splitting into separate `provider`/`model_name` fields — matches that real precedent directly (the whole string is what actually gets passed to a completion call, nothing downstream needs to parse or reconstruct it) and avoids new schema surface for no behavioral benefit, the same reuse-over-new-mechanism discipline this draft has applied repeatedly (self-audit A1, B2, C35). One real inconsistency worth flagging so it isn't later "corrected" as a presumed typo: casing genuinely varies within the `Qwen` namespace itself — `Qwen/Qwen3.6-27B` capitalizes the model name, `Qwen/qwen-embedding-8B`/`Qwen/qwen-reranker-8B` don't — confirmed as the real registered strings, not a transcription error. The registry list above, §2's `CONTEXT_WINDOW_AND_MAX_OUTPUT` table, and every other current reference to these models in this spec are updated to the real strings in this same pass. See §2, §9.
  - **Resolved (v0.46, Tier-4 checklist C48):** `Qwen/qwen-reranker-8B` is confirmed not yet deployed at the Gateway as of this draft ("available soon," no firm date) — the real values recorded for it above and in §2's `CONTEXT_WINDOW_AND_MAX_OUTPUT` table (C12/C13) are its correct target spec and are unaffected by this. It is deliberately left out of the *live* registry config until it's actually callable, rather than added early and left to fail at call time — the same config-driven, load-at-startup mechanism this registry already uses generally (the v0.39 deployment-topology note below) brings it online automatically, with no code change, once it's added. See §9 for what v0 actually ships with in the meantime. **Superseded (v0.65, Tier-3 checklist C53 area):** this deployment's actual Azure AI Foundry access has since been checked directly, sharpening "not yet deployed" into a firmer negative — see the v0.65 resolution below.
  - **Resolved (v0.47, Tier-4 checklist C49):** `Qwen/qwen-embedding-8B` is confirmed not yet deployed at the Gateway either, extending C48's finding from the reranker alone to both retrieval-pipeline models — neither is live. `openai/whisper-large-v3` is confirmed not deployed too, with no design consequence: it was already out of scope for v0 (above) with no mechanism referencing it, so its deployment timing changes nothing here; noted for the record, not as a design question. The embedding gap is the consequential one — unlike C48, which left `search_code` able to run in reduced, single-stage form, `search_code` now has no retrieval-pipeline model to call at all. See §6 for the resulting tool-availability resolution. **Superseded (v0.65):** the embedding gap this resolution names no longer holds — `text-embedding-3-small` closes it via a direct, non-Gateway access path. See the v0.65 resolution below and §6.
  - **Resolved (v0.65):** two real facts confirmed together, from checking this deployment's actual access directly rather than only tracking the Gateway's own "coming soon" status. First, `Qwen/qwen-embedding-8B` and `Qwen/qwen-reranker-8B` are confirmed not reachable through this org's Azure AI Foundry access specifically — a firmer, access-path-level finding than C48/C49's "not yet deployed at the Gateway," though not in tension with it (both agree neither model is usable today). Cohere Rerank — Azure AI Foundry's own dedicated reranking offering, and the strongest reranker candidate available in principle — is separately confirmed unavailable in this tenant/project's current configuration, blocked by a Hub-based-project requirement Cohere's Azure Marketplace listing currently carries (per Microsoft's own support guidance) that this deployment's project type doesn't meet. Second, and independently: real, callable capacity exists today outside the Gateway entirely — a direct Azure OpenAI subscription gives this deployment working access to both `text-embedding-3-small` and `text-embedding-3-large`, with `-small` adopted as the default active tier and `-large` a config-switchable alternative, not a hypothetical one (§2's resolution below, revised v0.66). With no reranker reachable via any path, `search_code` ships single-stage — see §9 — and `text-embedding-3-small` closes C49's tool-availability gap directly: `search_code` is offered today, not withheld. `Qwen/qwen-embedding-8B`/`Qwen/qwen-reranker-8B` stay named in this spec's registry vocabulary as a documented, config-swappable future upgrade (the same treatment already given gVisor, C1, and live LSP integration, C25) rather than deleted — see §2's `direct_endpoint` field and §9 for the kept seam.
- All models sit behind one Gateway, unified under an OpenAI-compatible API (chat completions with native tool/function calling — required, since the tool-calling format decision below depends on it; streaming — required, since the CLI presenter streams output) — **with one confirmed exception (v0.65):** `text-embedding-3-small` is accessed directly against a separate Azure OpenAI subscription, bypassing the Gateway entirely. This is the first registry entry that doesn't fit the "all models sit behind one Gateway" statement literally, and needed a real representational answer rather than a footnote — see §2's `direct_endpoint` field for the mechanism, grounded in how production multi-provider LLM proxies (LiteLLM, Portkey) actually represent a per-model routing exception without abandoning one shared registry/calling-convention.
  - **Resolved (v0.65):** the Gateway's own `/embeddings` endpoint question is now moot for what v0 actually calls — `text-embedding-3-small` is reached directly, not through the Gateway, via Azure OpenAI's own standard `/embeddings` surface (confirmed, not assumed, since this is documented first-party API). Whether the Gateway *also* exposes a standard `/embeddings` endpoint for a future `Qwen/qwen-embedding-8B` stays an open ASSUMPTION, relevant only if that dormant path is ever activated — reranking was never a standard OpenAI endpoint shape either way, and with no reranker reachable via any path today (above), `Qwen/qwen-reranker-8B`'s access pattern stays unresolved and moot for the same reason — see §9.
- Editor integration starts with a CLI, not an IDE plugin (§10). No IDE-side protocol (LSP-adjacent extension, VS Code webview, etc.) is in scope for v0.
- The target repository is assumed to be a git repository throughout — every path in this spec that touches "the repo" assumes `.git` exists and standard git plumbing (`log`, `status`, `diff`, `show`) is usable.
- **Locked (v0.39):** every session's working files — the target repo, the `run_command` sandbox copy (§7.3), and the `.lucifer/sessions/<id>/` persistence directory (§7.7) alike — sit on local disk in both of this deployment's real shapes: a developer's own machine, or a container spun up fresh per GitLab CI pipeline job. Neither shape puts any of this on network-backed storage. This wasn't needed for the sandbox-isolation-primitive decision (§6.2, Tier-1 checklist C1), which turns on OS/kernel facts, not storage backend — but it is directly load-bearing for §7.7's session-persistence mechanism (C28, C42): the atomic-write guarantee (temp-file-then-rename) and the per-write latency assumptions both mechanisms lean on hold reliably on a local filesystem in a way they wouldn't on network-backed storage.
