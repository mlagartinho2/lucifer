## 8. Context Management & Compaction

Two separate stores:

- **Workspace** — authoritative, per §7. Never compacted or summarized-away; it's not part of the transcript at all.
- **Transcript** — token-budgeted, the actual conversation/tool-call history sent to the model.

A protected tier of the transcript is never compacted: system prompt / tool schema / task description, recent turns, pending diffs, active retry/error messages, and a small pinned record of each escalation event (§4.3) — not the raw turns around it, which get no special protection beyond whatever `recent turns` already gives them.

~~**ASSUMPTION (unspecified):** how many turns "around an escalation trigger" are protected (this draft assumes ±2 turns as an illustrative placeholder).~~ **Resolved (v0.59, Tier-3 checklist C22):** the raw-turn-window mechanism is replaced outright rather than given a number — no number was needed once the actual problem was named precisely. The point of protecting "turns around an escalation trigger" was never the raw turns themselves; it was making sure a compaction pass, possibly long after the swap, can't erase *why* the trajectory is now on a different model. That's exactly the shape of problem this draft already solves elsewhere with a small deterministic record rather than raw content — the tier-2 reference-eviction pointer (§8 below, C33) and the deterministically-rendered file-touch history (this section's own stated reasoning, below) both exist because this draft already prefers a cheap structured fact over lossy raw replay for administrative state, the same principle `tool_call_reliability` (§2) applies to model behavior itself. A raw ±N-turn window was the odd mechanism out against that pattern before this resolution, not a considered exception to it.

The replacement: at the moment `escalate()` (§4.3) actually substitutes a new model, the harness pins a small structured record — `{event: "escalation", from_model, to_model, trigger_reason, turn}` — into the protected tier, permanently, the same treatment the system prompt already gets. `trigger_reason` is one of the three counter kinds already tracked in §3.2 (`tool`, `verification`, `gateway`) — no new vocabulary invented. The raw turns immediately before and after the swap get no special carve-out: while they're still recent they're covered by the already-separate `recent turns` protection, and once they age out they go through the same three-tier pipeline (§12 item 10 deep dive, below) as everything else — drop-entirely if they turn out to be a resolved failed attempt, reference-evict if they're a non-mutating tool call, model-summarize otherwise. Nothing about escalation exempts them from that pipeline anymore.

Grounded in real research specific to this problem, not just the general reuse-over-invention pattern: a recent paper studying context-compaction safety (arXiv 2606.22528, "Governance Decay") found that *pinning a small structured fact* — not protecting a positional window of raw turns — is what actually survives compaction reliably, re-injecting roughly 47 tokens of pinned content after every compaction pass and verifying 0% loss across seven tested models; a positional window is exactly the kind of mechanism it argues against for protecting non-recent-but-important information. Separately, I checked what real coding-agent context-management systems protect by way of any window at all, and found a clean, informative mismatch rather than a transferable number: Hermes Agent's real shipped compaction protects "first 3 + last 4 turns" positionally, OpenCode protects "the last 2 user turns" plus a 40,000-token cushion, Codex CLI caps recent-message extraction at ~20,000 tokens, and Claude Code protects its most recent tool-call results with no published count — every one of them protects by *recency*, none by *importance of a past event*. That's not a mechanism real production systems build at all, which is itself the strongest evidence that C22's original framing (tune a number for a positional window) was asking the wrong kind of question, not just an untuned one.

One more check worth recording: does permanent pinning risk the same unbounded-accumulation problem C33 found and fixed for tier-2 pointers (dropped after one further compaction pass, precisely because they could otherwise accumulate without limit)? No — `ESCALATION_PATH` has exactly four models (C21) and `escalate()` no-ops at the ceiling (already locked), so at most three escalation events, and therefore at most three pinned records, can ever exist in one trajectory. Permanent pinning is safe here for a structural reason tier-2 pointers never had, not an oversight repeating the same gap C33 already closed once.

**Resolved (§12 item 11 deep dive):** what triggers a compaction pass is a per-model, not a flat, threshold:

```python
DEFAULT_COMPACT_THRESHOLD_PCT = 0.65   # confirmed (v0.55, Tier-3 checklist C17), moved down from an earlier 80% guess — see below

def usable_budget(model: ModelSpec) -> int:
    pct = model.compact_threshold_pct if model.compact_threshold_pct is not None else DEFAULT_COMPACT_THRESHOLD_PCT
    return int(model.context_window * pct)   # compaction triggers once the transcript reaches this many tokens
```

This mirrors the same general shape §4.4's `max_tokens_for(model, effort)` already established — a per-model registry fact combined with something else to produce one concrete per-call number, not a new pattern invented for this. **Consistency note (v0.54):** the two mechanisms diverged slightly once C16 (Tier-3 checklist) made `EFFORT_MAX_TOKENS` itself per-model — `max_tokens_for` now combines two independently-set per-model quantities via a min-clamp, with no shared policy default left in the picture; `usable_budget()` here still falls back to one shared default, `DEFAULT_COMPACT_THRESHOLD_PCT`, whenever a model has no `compact_threshold_pct` override, which `max_tokens_for` no longer has an analog for. The general pattern (combine per-model registry facts into one derived number, re-read fresh on every call) still holds; the "registry field plus policy default" specifics no longer match exactly. Why the illustrative default moved down from a flat 80%: Chroma Research's "Context Rot" study found real usable context degrading well before a model's advertised limit across all 18 frontier models tested, with aggregate findings putting effective capacity closer to 60–70% of the advertised maximum — and for agentic, whole-repo-reasoning workloads specifically (this spec's own use case), some writeups suggest planning for meaningful degradation as early as 25–30%. 80% was too generous a default even before considering per-model variation; 65% sits inside the aggregate range research actually supports, without adopting the more aggressive worst-case agentic figure as a blanket default absent Lucifer-specific tuning data. Per-model overrides exist for the same reason `tool_call_reliability` does: the research confirms the degradation *curve's shape* varies model to model even though the *direction* doesn't, so a weaker/smaller-context model can reasonably be given a lower `compact_threshold_pct` (compacting sooner, relative to its own window) than a stronger one — the old draft's own worked example, now backed by a real citation rather than just precedent from another draft.

**Further resolved (v0.55, Tier-3 checklist C17):** `DEFAULT_COMPACT_THRESHOLD_PCT = 0.65` is confirmed as final, not revised — but not without a real tension surfaced along the way. Every production coding agent checked (Claude Code, OpenAI Codex CLI, OpenCode — the same set already cited elsewhere in this draft) compacts far later than 65%: real community reverse-engineering puts Claude Code's own default somewhere in the 83–95% range (two independent write-ups disagree on the exact figure, since Anthropic doesn't publish it), and Codex CLI applies a 95% safety margin against its effective context window. Raising Lucifer's own default to match was considered and declined for two real reasons. First, Claude Code's own GitHub issue tracker carries multiple live feature requests asking for auto-compact to trigger *earlier* than its shipped default — real users hitting real quality problems well before that late threshold, independently corroborating Chroma's original degradation finding from the demand side rather than the benchmark side. Second, and specific to this spec: Claude Code's late default exists because auto-compact is effectively its *only* protection against running out of room; Lucifer already has three independent hard backstops for that (`max_iterations`, `wall_clock_seconds`, `token_budget`, §3.2), so compaction here doesn't have to double as last-line overflow protection and is free to stay tuned toward the thing Chroma's research actually measured — answer quality, not budget survival. No per-model `compact_threshold_pct` override is introduced for any of the four real `ESCALATION_PATH` models: none were tested directly in the Chroma study, and the only available signal is family-level and one generation removed (Qwen3-8B/32B/235B for `Qwen3.6-27B`'s vendor, GPT-4.1 for `gpt5.4`/`gpt-5.6-luna`'s vendor; no data at all for `granite-4.1-30b`) — meaningfully thinner than C14/C46's adjacent-sibling evidence, too indirect to turn into a placeholder honestly. All four models stay on the shared default until Lucifer has its own telemetry; the registry field itself (§2) is untouched and ready to take a real override the moment that data exists.

One consequence falls out for free rather than needing its own mechanism: because `usable_budget()` reads whichever model is currently active, a mid-trajectory escalation (§4.3) automatically picks up the new model's own `context_window` and `compact_threshold_pct` the next time the compaction check runs — no separate recomputation step, the same way `max_tokens_for` already re-derives per active model on every invocation. **Confirmed (v0.55, Tier-3 checklist C17 — closes §13 item 45):** this lazy behavior is the actual decision, not merely an unconfirmed assumption — forcing an eager, out-of-band recompute at the moment of escalation would make compaction the one mechanism in this spec that gets special-cased on a model swap, when every comparable mechanism (`max_tokens_for`, `token_budget`) already re-derives fresh at its own next natural check with no forced trigger of its own (self-audit A1, B2's declines of unwarranted new structure). No new mechanism needed to confirm this — an internal-consistency argument, not new external research.

**Resolved (§12 item 10 deep dive):** everything outside the protected tier is handled by three mechanisms, applied in this order, rather than one blanket model-summarization pass over all of it:

1. **Drop entirely, no trace.** A `SELF_CORRECTABLE`/`INFRA` tool attempt that failed and was then retried successfully at the same tool (§5.1) — the failed attempt has no forward value once resolved — and a §3.5 intermediate verification run superseded by a later one in the same session (only the most recent run, and the `done`-time run against baseline, ever matter going forward). Neither is worth keeping even as a pointer.
2. **Reference-evict.** Once it ages out of the protected tier's recent-turns window, a call to any of the five non-mutating tools (`read_file`, `list_directory`, `search_code`, `grep_search`, `get_diagnostics`) has its output replaced by a compact, mechanically generated pointer — never model-authored — naming the tool, its arguments, and the turn it occurred at. Nothing is copied to a separate store to make this recoverable: all five of these tools are deterministic, idempotent reads against state that already persists on its own (the sandbox, Workspace, the retrieval index — §7, §9), so the same call can simply be reissued to see the content again.
3. **Model-summarize.** Only what's left after 1 and 2 — genuinely untracked reasoning, per the existing rule below — gets a narrow model pass.

Running the two mechanical tiers first is the point, not an implementation detail: it shrinks how much ever depends on a model's lossy compression of exact content, for the same reason file-touch facts are already rendered deterministically rather than asked of a model (below) — a coding agent's compaction carries a correctness risk chat-style compaction doesn't, since a misremembered file body or function signature can silently corrupt a later edit.

**Considered and declined:** two real, simpler, already-shipping designs were the obvious default absent a specific reason not to use them, and each was declined for a different reason. Anthropic's own compaction — one model-generated summary replacing everything before a cut point, no tiers, no distinction between deterministic fact and model prose — was declined because it would routinely put a `read_file` call's exact content through model summarization once a transcript runs long, and this draft already refuses that same trade for action-history facts (below) on correctness grounds; the same argument extends to raw file/search content, not just to "what the agent did." Per-tool-result fixed-length truncation-with-a-marker (a pattern seen in production coding-agent context-management writeups) was declined for an unrelated reason, not the model-summarization one: it isn't a use-over-time eviction mechanism at all, it's a write-time bound on one individually oversized result, and once applied the truncated tail is gone for good — there's no re-issuable call that recovers it, unlike tier 2's pointer. That's a real, useful answer to a different problem (bounding one call's output size the moment it's produced, not managing how the aggregate transcript ages over a session) — §12 item 13 tracked it as its own, separate question at the time, and nothing in this resolution closed it. It's since been resolved on its own terms (§5.2, §12 item 13 deep dive): a fixed-length, middle-truncated cap at capture time, which is in fact close to the same shape declined here for compaction — the difference this paragraph draws still holds even once adopted elsewhere, since it answers "how big can one result be" rather than "how does the transcript's total size stay bounded over a session," and the two compose rather than conflict. A design that externalizes evicted content to a separate store — the pattern that most directly inspired tier 2 above — was also considered and simplified away: since Lucifer's five non-mutating tools are already deterministic reads against state that already persists, a pointer that just names the original call is enough to recover the content; a side-store would duplicate data that's already sitting somewhere recoverable.

**Resolved (v0.33, Tier-4 checklist C33):** all three open questions from this section's original ASSUMPTION are resolved together, since research on real production compaction systems answered them as one connected picture rather than three independent ones.

The pointer's fields simplify from four to three: `{tool, args, turn}` — `content_hash_prefix` is dropped outright, not carried forward as a placeholder. Nothing in this mechanism ever reads or compares a content hash: recovery works by re-issuing the deterministic call fresh against live state, never by verifying a stored digest against anything, so the field would exist purely as unused overhead. `turn` is retained and doubles as the natural key into `transcript.jsonl` (§7.7, C28) — the same append-only, one-line-per-action-result log a pointer's `turn` value already indexes into, rather than a second addressing scheme invented just for this. Grounded in real precedent for "location over verification data": Claude Code's own real "persist large results to disk" layer replaces an oversized tool output with a pointer holding a file path and a short preview, not a hash; the "Context as an Environment" paper's own eviction-index design ties a compact landmark to an exact event-log address for on-demand materialization, the same address-not-hash shape.

"Superseded" stays recency-only, and content-aware detection is now formally declined rather than left as an open maybe. This is grounded in a genuine full convergence, the same strength of evidence C27's CLI-shape decision rested on: Claude Code's own real five-layer compaction cascade, and the OpenCode/Codex CLI/Amp comparison researched alongside it, all evict purely by age or idle time; none detect that a later, more specific tool call (e.g. a narrower `search_code`/`grep_search` covering the same ground) makes an earlier one's content redundant. The Scroll paper's own eviction ordering is likewise driven by recency and recovery cost, never content analysis. No real system researched does the content-aware version this draft's own prior text floated as a "possible future refinement" — so it's declined outright rather than continuing to be named as a plausible later addition.

A tier-2 pointer is not kept indefinitely: it is dropped outright (tier-1 treatment, no trace) at the *next* compaction pass after the one that created it, rather than surviving for the rest of the session. This reuses the same "aged out of a window" idea that already promotes an entry into tier 2 in the first place — applied a second time, one level out — rather than inventing a new numeric cap (a pointer count ceiling, a token budget for the pointer set, or a separate time horizon). It presumes compaction can run more than once over a session, which C29's own uncapped repeated budget grants (v0.29) already make a real possibility, not merely hypothetical. Grounded in Claude Code's own real behavior: a later layer of its cascade goes past the lightweight-pointer stage and fully clears old tool-result references (`cache_edits` deletes them from the server-side cache entirely; a subsequent layer replaces content with a literal "[Old tool result content cleared]" marker) — real confirmation that production systems don't treat a lightweight reference as permanent either, once it's aged enough. The Scroll paper's own choice to keep eviction indices for the life of a session was considered and declined here specifically because it's solving a different-scale problem (a system built for continuous, potentially unbounded interactive history) than Lucifer's own single, budget-bounded trajectory — and because a from-scratch re-search after losing an old, already-many-turns-stale pointer is a reasonable price for keeping the compacted digest itself from growing without bound over an unusually long, many-times-extended session.

File-touch and action-history facts in a compacted summary are rendered deterministically from Workspace's edit history — never generated by a model. A model is only ever asked to summarize genuinely untracked reasoning (i.e., the parts of the transcript that aren't already recoverable as structured fact from Workspace or, per tier 2 above, as a reference-eviction pointer).
