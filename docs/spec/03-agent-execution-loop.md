## 3. Agent Execution Loop

### 3.1 Loop shape

Reactive, not planned: propose one tool call → execute → observe the typed result → decide the next action. No upfront multi-step plan is generated before execution begins (explicitly rejected as a design — see §11).

```
loop:
    if any budget exhausted: → suspend/resume (§3.2, §5.3/§5.5) — never a direct hard-abort; only ends if a human then chooses to abort outright
    action = model.next_action(transcript, tool_schemas, invocation_params)   # §4.4 — exactly one tool call
    if invocation itself failed (e.g. truncated/incomplete response, gateway error): → INFRA (§5.1), feed back as observation, retry
    validate action against tool JSON schema                # §5.6 — before dispatch
    result = dispatch(action)                                # typed envelope, §5.2
    if result triggers stuck/UNSAFE/risk-flag: → §5
    append (action, result) to transcript
    if action.tool == "done": → verification gate (§3.4)
```

### 3.2 Budgets

The loop is bounded by multiple **independent** budgets — never a single iteration cap:

```python
class Budgets:
    max_iterations: int
    tool_escalate_threshold: int          # consecutive "kind=tool" SELF_CORRECTABLE failures — INFRA excluded, see below; resets on success, resume, or a genuine escalation, v0.38/C41 & v0.41/C44
    tool_abort_threshold: int
    verification_escalate_threshold: int  # "kind=verification" failures
    verification_abort_threshold: int
    gateway_escalate_threshold: int       # consecutive GATEWAY_ERROR against the active model — no abort pair, see below; resets on success, resume, or a genuine escalation, v0.49/C47
    wall_clock_seconds: int
    token_budget: int                     # total tokens across the trajectory
```

Each budget is tracked and checked independently; hitting one doesn't reset or mask the others.

**Partially resolved (v0.27, Tier-3 checklist C15):** three of the seven numeric defaults are revised from arbitrary illustrative placeholders to precedent-grounded illustrative placeholders — still not measured facts about Lucifer's own real usage, but no longer picked without evidence either: `max_iterations=80` (up from 40), `tool_abort_threshold=4` (down from 6), `wall_clock_seconds=1800` (up from 1200). `max_iterations` moved toward the closest real analogue found — mini-SWE-agent's SWE-bench harness, which uses a 250-step limit for the same class of full autonomous coding task, considerably higher than general-purpose agent frameworks like LangChain/LangGraph (15–25) that lack Lucifer's other two independent budgets (wall-clock, token) as backstops; 80 splits the difference deliberately, leaning toward more headroom given those other two budgets already exist to catch a genuinely runaway trajectory. `tool_abort_threshold` moved toward Aider's real, shipped `max_reflections=3` — the closest precedent for "how many self-correction attempts before giving up" — landing at 4 rather than adopting 3 outright, since Aider's counter is scoped to one narrower edit-then-test-then-reflect loop while Lucifer's tool-kind counter spans any self-correctable failure across the whole trajectory, a broader scope that argues for slightly more tolerance. `wall_clock_seconds` moved to 1800 to match OpenAI Codex CLI's own documented default for spawned-agent jobs, sitting just above where GitHub Copilot's cloud coding agent's sessions are observed to actually stop in practice (20–30 minutes) despite its documented 59-minute hard cap.

The remaining four — `tool_escalate_threshold`, `verification_escalate_threshold`, `verification_abort_threshold`, `token_budget` — stay exactly as originally drafted (`3`, `1`, `2`, `300_000` respectively — `verification_abort_threshold` was later revised `2→3` at v0.52, see the next paragraph), explicitly for lack of any transferable precedent rather than an oversight: none of the systems researched (Claude Code, Aider, Codex CLI, GitHub Copilot) auto-escalate to a different model on tool or verification failure at all, so there's no real number to borrow for either escalate/abort pair tied to that mechanism; and `token_budget` is denominated in raw tokens, which needed §2's own `context_window`/`max_output_tokens` question (§12 item 5, Tier-3 checklist C12) answered with actual model specs before it could even be approached — **that precondition is now met (C12, v0.44)**, but the number itself is still unpicked, since knowing what one call can hold doesn't say how many tokens a whole trajectory should reasonably spend; the closest real analogue found, SWE-agent's per-instance cost limit, is denominated in dollars and doesn't translate without knowing this deployment's actual token pricing either. All seven values, including the three just revised, remain genuinely provisional until Lucifer has real production telemetry to tune against — this pass upgrades three from ungrounded guesses to precedent-grounded ones; it doesn't claim to finalize any of them.

**Further resolved (v0.52, Tier-3 checklist C15 — second research pass):** the remaining four values, revisited with a second, broader research pass rather than left as first found. Two are confirmed rather than changed, now for a real reason instead of by default: a broader survey of coding-agent architectures (beyond the original four systems researched at v0.27) still turned up no system that swaps to a stronger model after repeated tool or verification failures, reconfirming `tool_escalate_threshold=3` has no closer transferable number to move toward; and `verification_escalate_threshold=1` (escalating on the very first verification failure) is kept as consistent with self-audit A3's own reasoning above — triage is deliberately not conservative because escalation is a cheap, fast safety net, so burning a retry on a model already shown unreliable at verification before escalating would work against that same logic. One is revised: `verification_abort_threshold` moves `2→3`, toward OpenHands' real, shipped "Critic" refinement-loop cap (`max_iterations=3` at a 0.6 success-score threshold) — not a perfect analog, since OpenHands retries the same model rather than escalating first, but note where the change actually bites. With `verification_escalate_threshold=1` and C44's reset (v0.41, below), every verification failure short of the ceiling model just escalates and resets the counter, so `verification_abort_threshold` only governs a model with nowhere further to escalate (the ceiling, §4.3) — which, at 3, gets three consecutive verification failures before the trajectory gives up rather than two. That is the OpenHands shape exactly (retry the same model up to its cap), so the analogy is closer than it first looked. (Corrected at v0.70: this paragraph originally described the change as giving the *escalated* model two real attempts, which didn't account for C44's reset.) `token_budget=300_000` is kept, now checked rather than merely carried forward: real per-task cost data (Aider's polyglot benchmark, $0.03–$0.13 per bounded task) checked against C21's real registry pricing (§4.3) puts 300,000 tokens at roughly 15–65x a typical single task's real cost even at the priciest configured model (`gpt5.4`) — a sane multiple for a backstop meant to catch a trajectory that's clearly gone wrong, not a typical-usage ceiling, so this value is confirmed rather than replaced. Caveat named rather than glossed over: Aider's benchmark tasks are single bounded exercises, likely smaller in scope than a multi-file Lucifer trajectory, so this is a sanity check on the existing placeholder, not a precise derivation of a new one. A real methodology for the number this deployment should eventually adopt is recorded for when it's actually available, rather than invented now: sample 50–100 representative real trajectories once Lucifer is running, take the 90th-percentile total token usage, add a 20% buffer — a documented real production practice, not invented for this draft, just not yet applicable here for lack of the underlying data. All seven `Budgets` values now carry a reasoned, precedent-or-sanity-check-grounded number; none of the seven, including the three from v0.27 and the one changed here, are claimed as final — all stay provisional pending Lucifer's own real production telemetry, the same status this section has held since v0.27.

**Resolved (v0.64, Tier-3 checklist C51 — closes §13 item 67):** `gateway_escalate_threshold = 3`, the eighth `Budgets` value (added v0.49, C47, after the seven above were already settled). No coding-agent framework researched auto-switches models on repeated failure at all (the same absence already noted for `tool_escalate_threshold`, C15), so the real grounding here comes from the closest analogous mechanism instead — systems that count consecutive failures against one specific backend before routing away from it. Two independent clusters of real, documented defaults converge on the same number: infrastructure health-checking (Kubernetes' `failureThreshold`, HAProxy's `fall` count, and the low end of Envoy's outlier detection all default to 3) and, more directly in-domain, LLM-API retry/fallback conventions (AWS Bedrock's SDK `max_attempts` default of 3, and LiteLLM Router's own `allowed_fails` default of 3 before a deployment enters cooldown — the single closest same-domain precedent found). Anthropic's and OpenAI's own SDKs default to 2 retries (3 total attempts), consistent with the same cluster read as attempt-count rather than failure-count. `3` is adopted as the real, converged-on value across both clusters, not a number reached by splitting a difference.

See §9 for `retrieval_gateway_threshold` (C52), resolved alongside this item using the same research pass — a related but distinct number, deliberately set higher, for a mechanism with a materially costlier one-way consequence.

There are exactly two "kinds" with a full escalate/abort pair: **tool** (failures during the normal reactive loop) and **verification** (failures during the post-`done` gate, §3.4). **ASSUMPTION:** stuck-repeat detection (§3.3) increments the *tool*-kind counter rather than a third counter — the locked decisions describe only tool vs. verification as the two kinds, so a stuck mutating-tool retry is modeled as a tool-kind failure, not a separate budget dimension. Flagged for confirmation. **Resolved (v0.49, Tier-4 checklist C47):** a third kind, **gateway** (consecutive `GATEWAY_ERROR` against the active model), was added below — escalate-only, deliberately with no abort counterpart, so it isn't a full third pair the "exactly two" framing above needs updating for structurally; see the C47 resolution below for why.

**Escalate vs. abort, and what "abort" actually means:** an escalate-threshold breach hands control to the Model Router (§4.3) to swap to a stronger model, without pausing the loop. An abort-threshold breach raises the abort signal (§5.3), which — combining the locked decisions on error-budget aborts and on pause-vs-hard-abort — routes to the **suspend/resume** mechanism (§5.5) in all cases *except* when the triggering error is itself categorized `UNSAFE`, which hard-aborts regardless of which budget it came from.

**Resolved (B3 deep dive):** `max_iterations`, `wall_clock_seconds`, and `token_budget` exhaustion are all resumable, not terminal — routed through the same suspend/resume mechanism (§5.5) as stuck/failing/risk-flagged, never a separate `ABORTED` state. Two things make this the right default rather than just the path of least resistance: it's consistent with how verification-kind budget exhaustion is already treated as a `Suspend` trigger (§5.4) — a budget breach and a quality problem are already both suspend triggers in this spec, so there's no principled reason a third kind of budget (iterations/wall-clock/tokens) should be handled differently. And "resume" for a budget-driven pause specifically means the human grants an extended allotment (more iterations, more wall-clock, a higher token ceiling) as part of resuming — not a bare "continue," which wouldn't mean anything against a counter already at its ceiling. Declining to grant more isn't a new mechanism either: it's just the existing "abort the session outright" option in §5.5, which now includes a forced final summary before the session actually ends (§5.5, B3 deep dive — wind-down step). This resolves the cross-check's B3 divergence — the old draft made `max_iterations` specifically terminal (paired with a forced graceful-summary turn) and said nothing about wall-clock/token; this draft treats all three the same way, deliberately not carrying that asymmetry forward. `UNSAFE` remains the only category with no override and no resume.

**Resolved (v0.29, Tier-4 checklist C29):** granting an extended budget on resume reapplies that dimension's own already-resolved default again — a fixed increment, not a value the human types — matching the one real precedent found that's actually architecturally comparable to this spec's live, human-in-the-loop resume prompt: Cursor's agent mode, which shows a "Continue" affordance at its own fixed tool-call ceiling and simply reapplies that same ceiling again, with no numeric-entry field. Every other tool researched for genuine precedent (GitHub Copilot's cloud coding agent, OpenAI Codex CLI, Aider, LangChain's `AgentExecutor`, LangGraph) either offers no interactive extend mechanism at all — a hard stop requiring a developer to edit config and re-invoke in code — or, in Copilot's case, states its time cap explicitly "cannot be extended or bypassed"; none of them let a human type a bespoke new ceiling at the moment of hitting one, so this draft doesn't invent that UX either. Concretely: a `max_iterations`-driven resume adds another 80 (§3.2's own default); a `wall_clock_seconds`-driven resume adds another 1800; a `token_budget`-driven resume adds another 300,000 (itself still a placeholder pending C12, but the increment mechanism doesn't depend on that number being final). No new placeholder is introduced — each increment reuses the value §3.2 already carries as that dimension's default, rather than adding a second, separate "increment size" field. Repeated grants on the same trajectory are not capped, again matching Cursor's real behavior (repeatable continues, no built-in ceiling): the safety property here isn't a countdown of allowed extensions, it's that suspend/resume already puts an explicit, discrete human decision at every single budget boundary — a trajectory needing several grants in a row is visible to whoever keeps approving them, not silently self-extending. Whether a trajectory needing unusually many grants deserves its own soft signal (e.g., surfaced at diff-review time) is a natural future refinement, not built for v0.

**Resolved (B3 deep dive, wind-down step):** what the human sees at a budget-driven resume prompt is the specific counter and threshold that tripped (e.g. "iterations: 80/80 used"), surfaced mechanically — the same "specifically-labeled reason" pattern §5.4 already uses for a policy-blocked-command pattern, not a model-generated explanation. What happens if the human declines and aborts outright instead is defined once, for every path that reaches that same choice, in §5.5 — not repeated here.

**Resolved (B6 deep dive, second sub-question):** `token_budget` itself needs no new mechanism for the fact that effort (§4.4) now directly affects how fast it depletes — no separate effort-rate budget dimension, and no different resume options depending on why it depleted. Declining a new dimension matches this section's own precedent, twice over: self-audit A1 declined a third, INFRA-specific counter, and B2 declined bifurcated escalation paths, both because the locked decisions don't call for the extra structure and the existing budgets already backstop a pathological trajectory without it — an effort-rate budget would be the same kind of addition for the same marginal benefit. Declining different resume options follows from §5.5 already offering every option (approve, inject guidance, grant an extended budget, abort outright) at any budget-driven pause regardless of why it tripped — a human who suspects sustained high effort isn't converging can already inject guidance instead of granting more tokens, with no need for effort-awareness built into the choice itself.

What *does* change is the budget-status-at-resume display this section resolved just above: since B6's first half (§4.4) makes `effort` a per-invocation, per-call fact, a `token_budget`-driven resume specifically (not `max_iterations`/`wall_clock_seconds`, which don't vary this way) also surfaces a deterministic tally of invocations per `EffortLevel` across the trajectory (e.g. "token_budget: 300,000/300,000 used — 6 calls at low, 2 at high, 4 at max"), alongside the raw counter/threshold line already shown. This closes a real gap the flat token count leaves open on its own: two trajectories hitting the same 300,000-token ceiling could be an 80-iteration low-effort run or an 8-iteration max-effort one, and those call for a different human judgment about whether granting more tokens is likely to help. The tally is one small new piece of bookkeeping — a per-trajectory counter incremented on each invocation — not a new budget, and it's mechanically computed and shown exactly like everything else at this resume prompt, never model-generated (same principle as the resolution just above, and as §8's compaction rule).

**Resolved (self-audit A1):** `INFRA` failures no longer count toward either kind's escalate or abort threshold at all. Escalation exists to respond to a model that isn't capable enough for the task — an `INFRA` failure (sandbox crash, timeout, gateway error) says nothing about model capability, so letting it feed the same counter as `SELF_CORRECTABLE` mistakes meant a run of pure infrastructure flakiness could trigger a pointless, more expensive model swap. Rather than inventing a third, infra-specific budget dimension alongside tool/verification — which would add budget machinery beyond the two kinds the locked decisions actually specify — the fix is simply not to count it. A pathologically infra-flaky trajectory is still caught: every `INFRA` failure still consumes an iteration and wall-clock time, so `max_iterations`/`wall_clock_seconds` remain the backstop and already route to suspend/resume per the resolution above. Worst case, that backstop is slower to trip than a dedicated counter would be — a real trade-off, flagged here rather than hidden, in exchange for not adding a budget dimension nothing in the locked decisions calls for.

**Narrowed (v0.49, Tier-4 checklist C47):** the "backstop is slower to trip" trade-off just above is exactly what C47 (below) revisits — but only for `GATEWAY_ERROR` specifically, not `INFRA` generally. This resolution's own reasoning ("says nothing about model capability") still holds fully for the rest of `INFRA` — `SANDBOX_ERROR`, `SANDBOX_SYNC_FAILURE`, `COMMAND_TIMEOUT`, `NETWORK_ERROR`, `INTERNAL_ERROR` are genuinely uninformative about whether the active model itself is usable, and stay excluded from every threshold exactly as decided here. `GATEWAY_ERROR` turns out to be a different kind of signal: it's not "infrastructure flakiness" in the sense this paragraph means, it's a direct report about the one resource escalation exists to route around. See C47 for the narrow, separately-argued addition — this paragraph's original decision is not reversed, only carved around for one error type out of six.

**Resolved (self-audit A5):** a "stuck" event increments its counter once, not twice. Stuck-detection classifies *why* a `SELF_CORRECTABLE` failure counted (worth a different hint back to the model), it doesn't add a second, additional increment on top of the failure's own. One failed mutating-tool call always contributes exactly one unit to the tool-kind counter, whether or not it's also flagged stuck.

**Resolved (self-audit A6):** each threshold fires exactly once, when its counter first *reaches* the threshold value (equality, not a standing "at or above" check). This keeps `escalate()`/the abort signal from firing repeatedly across one bad stretch; `escalate()` is already a no-op once at the ceiling (§4.3) or already escalated, so a repeat firing wouldn't be incorrect, just redundant noise worth avoiding.

**Resolved (v0.38, Tier-4 checklist C41):** the tool-kind and verification-kind counters (`tool_abort_threshold`/`tool_escalate_threshold`, `verification_abort_threshold`/`verification_escalate_threshold`) are genuinely consecutive, not cumulative across the whole trajectory — resolving the "consecutive/rolling" hedge above outright in favor of "consecutive." Two distinct events reset a counter to zero, and both were previously unspecified: an ordinary intervening success during normal loop operation (not itself a suspend/resume event — just the counter's own definition, matching §3.3's stuck-repeat detection, which likewise only ever looks at "the immediately preceding attempt," never a longer window), and a human resuming the trajectory through §5.5 after any suspend — whichever of §5.4's rows triggered it, and whichever of the three resume options the human picks (approve and continue, inject guidance, approve a partial diff), since all three are exits from the same shared suspend/resume mechanism (§5.5) with no principled reason to treat them differently for this purpose. Grounded in two independent real precedents rather than asserted: the canonical circuit-breaker pattern (Microsoft's own reference architecture) explicitly distinguishes an automatic half-open trial, where only a *success* fully resets the failure count, from a human-initiated **manual reset**, which the same documentation states plainly resets the counter outright — "you should provide a manual reset option that enables an administrator to close a circuit breaker and reset the failure counter" — and a human choosing "approve and continue" is exactly the manual-reset case, not the automatic-trial one. Separately, Aider's own `num_reflections` counter — the real system this draft already cites for `tool_abort_threshold`'s numeric value (v0.27, C15) — is confirmed, from its actual source (`base_coder.py`), to reset to zero inside `init_before_message()` at the start of every new user turn, not persist cumulatively across a session; Lucifer's closest analogue to a fresh user turn mid-trajectory is exactly a human resuming from a suspend. A full reset also directly extends reasoning this draft already adopted rather than inventing new philosophy: C29's own resolution for the other three budgets argues "the safety property here isn't a countdown of allowed extensions, it's that suspend/resume already puts an explicit, discrete human decision at every single budget boundary" — that argument applies identically here, just was never extended to these two counters. The worry a full reset invites — a human reflexively clicking "approve and continue" forever on a trajectory that never really recovers — is already answered by an existing backstop, not a new one: `max_iterations` and `wall_clock_seconds` keep accumulating regardless of any tool/verification-kind reset (§3.2's own "hitting one doesn't reset or mask the others") and are untouched by a plain approve, only by an explicit C29-style grant, so a trajectory that's genuinely not converging is still caught there — the same "a slower backstop is an acceptable trade-off for not adding new budget machinery" reasoning self-audit A1 already used. This also fixes a real latent bug self-audit A6 (above) didn't anticipate: left unreset, a counter sitting *at* its threshold after a suspend would sail past it on the very next failure (e.g. 4 → 5) without ever satisfying A6's exact-equality re-fire condition again, silently defeating the second suspend the threshold exists to guarantee. Resetting to zero on both a success and a resume is what correctly re-arms that condition for a later climb back to threshold, with no separate "already fired" flag needed to patch around it.

**Resolved (v0.41, Tier-4 checklist C44):** an escalate-threshold breach also resets the counter it fired on (tool-kind or verification-kind, whichever tripped) to zero — but conditionally, not unconditionally: the reset only happens when `escalate()` (§4.3) actually substitutes a new model, not merely when the counter reaches the escalate-threshold value. At the ceiling of `ESCALATION_PATH`, `escalate()` is already an explicit no-op (§4.3's own pseudocode) — reusing that same check here, rather than inventing a second one, means a trajectory stuck on the strongest configured model gets no free reset: its counter keeps climbing toward the abort threshold exactly as it would without this resolution, so abort still fires when there's genuinely nowhere further to escalate to.

This deliberately does not just extend C41's own reasoning to a new case — C41 was explicit that a human's discrete approval is the safety property behind a full reset, and an automatic escalate-threshold breach has no human decision in it at all, so that argument doesn't transfer, exactly the gap C44 was opened to name. The justification here is narrower and different: the failures that built up the counter belong to the model that just got replaced, not to the model taking over — attributing one model's failure streak to a different, more capable model's fresh budget doesn't reflect anything real about the new model's own reliability, and leaving the counter where it was would work directly against self-audit A3's own stated premise (§4.1) that escalation is "a path up," not a dead end. Left unreset, a freshly-escalated model would start with as little as one unit of tolerance on the tool side (`tool_escalate_threshold=3`/`tool_abort_threshold=4`) and two on the verification side (`verification_escalate_threshold=1`/`verification_abort_threshold=3`) before the trajectory suspends anyway — undercutting escalation's whole point. (Re-checked at v0.70: when C44 was resolved at v0.41 the verification pair was `1`/`2`, also one unit apart; C15's v0.52 revision to `verification_abort_threshold=3` widens it to two. The argument needs only one tight pair, and the tool pair still is, so it holds unchanged — somewhat weaker for verification, where the unreset case leaves the escalated model two failures before abort rather than one.)

Grounded in the same circuit-breaker precedent already cited for C41 (v0.38), read here for the distinction it actually draws rather than reused wholesale: the pattern's own reference documentation separates an automatic half-open trial — where only a *success* fully closes the circuit — from a human-initiated manual reset, which alone resets the counter outright. An unconditional reset on every escalate-threshold touch would blur that distinction exactly the way this resolution's ceiling case shows is unsafe; conditioning the reset on a genuine model substitution is the version of "the automatic trial gets a real but bounded chance" that stays faithful to the same precedent, adapted to this spec's two-state (escalate/abort) design rather than the pattern's own three-state (open/half-open/closed) one.

The bounded consequence of this design is named rather than left implicit: a trajectory can in principle escalate through every model on `ESCALATION_PATH`, resetting each time, before its counter's climb toward abort becomes real again at the ceiling — but `ESCALATION_PATH` is finite and operator-configured (§4.3), so this is bounded by however many models are actually on the path, not unbounded, and every attempt along the way still consumes `max_iterations`/`wall_clock_seconds`/`token_budget` regardless of what the tool/verification-kind counters do — the same "a slower, independent backstop is an acceptable trade-off" reasoning self-audit A1 already used for `INFRA` failures and C41 already reused for the reflexive-approval worry, reused here a third time rather than re-argued from scratch. One specific numeric consequence is worth stating plainly rather than left for later discovery: with `verification_escalate_threshold=1` (every single verification failure reaches it), this resolution means verification-kind abort is effectively reachable only once a trajectory is already on the ceiling model — everywhere earlier on the path, the first verification failure just escalates and resets. That reads as the right shape, not an accident: abort as a last resort only once there's genuinely nowhere further to go, matching the philosophy the rest of this resolution rests on — but it's a direct, concrete effect of combining this fix with C15's already-locked numbers, not a hidden side effect.

Considered and declined: an unconditional reset on every escalate-threshold breach, mirroring C41 exactly with no ceiling check — declined for the concrete ceiling bug above, not just for imprecisely extending C41's reasoning. A partial/probationary reset (e.g., decrementing rather than zeroing) was also considered and declined: no real precedent for that shape turned up in any system researched for this document, and it would be new budget machinery the locked decisions don't call for — the same category of addition already declined twice elsewhere in this draft (self-audit A1's declined third counter, the B2 deep dive's declined bifurcated escalation paths).

**Extended (v0.69, Tier-4 checklist C57 — §6.6):** the reset event this resolution establishes for an escalate isn't unique to model substitution — completing a `dispatch_agent` call (§6.6), successfully or not, resets these same two counters for the persona resuming control, on the identical justification just given above: the failures belonged to whichever persona was active when they happened, not to the one taking over next. `dispatch_agent`'s own iterations/tokens/wall-clock still count against the shared budgets above without a separate allocation (§6.6) — only the tool/verification-kind counters get this reset, the same scope the escalate/resume reset events already have.

This resolution reuses the counter-reset side effect C41 already established rather than inventing a second one: the reset lives in the orchestrator's own escalate-threshold handling, not inside `escalate()` (§4.3) itself, which stays the pure, stateless function it already is — that handling logic simply also consults `escalate()`'s own no-op-or-not outcome to decide whether to reset. No new field, no new mechanism.

**Resolved (v0.49, Tier-4 checklist C47 — closes §13 item 63):** nothing currently escalates away from the *active* model itself going unreachable mid-trajectory, since `GATEWAY_ERROR`/`INFRA` failures are excluded from every threshold by self-audit A1 above — a trajectory stuck on a dead model would retry it indefinitely, bounded only by `max_iterations`/`wall_clock_seconds`/`token_budget`, for a reason that wouldn't read as "the model is gone" to a reviewer. Fixed with a third, dedicated counter: `gateway_escalate_threshold` (added to `Budgets` above) tracks *consecutive* `GATEWAY_ERROR` results against the currently active model specifically — not the rest of `INFRA`, which stays excluded per the narrowed note above — and triggers `escalate()` once past threshold, exactly like the existing tool/verification counters. It resets to zero on a successful call to the active model, on `escalate()` actually substituting a new model (reusing C44's own conditional-reset guard immediately above, so a freshly-escalated model doesn't inherit the dead one's count), and on any human resume (reusing C41's reasoning) — the identical three reset events already established for tool/verification-kind, extended to a third dimension rather than invented fresh.

Deliberately no `gateway_abort_threshold`: unlike tool/verification-kind, this dimension has no abort pair. If every model on `ESCALATION_PATH` turns out unreachable — not just the one the trajectory started on — `escalate()` reaches the ceiling and no-ops exactly as its existing pseudocode (§4.3) already handles, and the counter would keep climbing with nowhere left to reset to; `max_iterations`/`wall_clock_seconds`/`token_budget` are the backstop for that case, the same treatment C44 already gave the identical "stuck at a bad ceiling model" shape. This isn't a new gap accepted here — it's the same one, extended one step further back. `escalate()`'s own pseudocode needs no change, for the same reason C44's didn't: the new counter's tracking and reset logic live in the orchestrator, which now consults a third dimension alongside the existing two, not inside the pure function itself.

Grounded in real precedent, checked rather than assumed. Claude Code's own `fallbackModel` — already cited repeatedly in this draft as precedent for `ESCALATION_PATH` itself — has a live, filed, unresolved gap of exactly this shape: a real GitHub issue (anthropics/claude-code-action#594) confirms its fallback only triggers on "overloaded" (rate-limit-style) errors, not on server downtime, invalid models, or general unreachability, and it's still open with no fix at time of writing. That's useful two ways: it confirms this is a genuine, non-trivial problem even the closest production precedent this document leans on hasn't solved, and it's a caution rather than a template — Lucifer's own `GATEWAY_ERROR` category (`error_type` enumeration, §5.1) is already a broad "model API failure" bucket, not scoped narrowly to rate-limiting the way Claude Code's trigger is, so this resolution doesn't need to broaden what counts as a failure, only to wire the category that already exists into something that acts on it. LiteLLM's Router is the closer positive precedent for the counter's *shape*: it tracks failures per deployment via an `AllowedFailsPolicy` — a configurable count per exception type before that deployment is cooled down — genuinely separate, dedicated tracking rather than blending into one generic retry count, which is exactly why this resolution gives `GATEWAY_ERROR` its own counter instead of folding it into `tool_escalate_threshold`. Where LiteLLM's mechanism does *not* transfer: its cooldown is time-based (a bad deployment is excluded for N seconds, then retried), sensible for a stateless multi-tenant router where a deployment recovering mid-flight is a common, live case — considered and declined here, since Lucifer's `escalate()` has no de-escalation concept anywhere in this spec (C44: "escalation is a path up, not a dead end"), and reverting to a previously-broken model mid-trajectory isn't a shape this architecture has any other use for; building it would be new machinery for a case that doesn't otherwise arise.

Considered and declined: folding `GATEWAY_ERROR` into the existing `tool_escalate_threshold` counter instead of adding a new one — smaller schema footprint, but it blends two different failure semantics into one number (two bad tool calls plus one gateway hiccup would read as "three tool-kind failures"), which only partly answers the diagnostic-clarity problem this item names in the first place — a reviewer still couldn't tell, from the threshold alone, whether escalation happened because the model kept messing up tool calls or because it went unreachable. Kept separate instead, matching LiteLLM's own per-exception-type tracking rather than one blended count.

`gateway_escalate_threshold`'s real numeric value is left as a new placeholder — no researched system gives a single transferable number here any more than one existed for `tool_escalate_threshold` itself (C15, v0.27): LiteLLM's policy is configurable per exception type with no universal default, and circuit-breaker literature generally suggests small thresholds (3–5) without pinning one for this specific system. Same status as every other still-open Tier-3 numeric default. See §13 item 67 / checklist Tier-3 item C51.

This is scoped narrowly to the *active* chat/escalation-pool model — the same model `ESCALATION_PATH` already governs (§4.3) — and does not resolve C50 (§13 item 66): a `search_code` call whose internal embedding/rerank request fails has no `ESCALATION_PATH`-style alternative to escalate to at all, since retrieval-role models are excluded from the triage/escalation pool by design (§1). That gap needs its own resolution shape and stays open.

**Resolved separately (v0.50, Tier-4 checklist C50 — §6/§9):** C50's own fix doesn't extend this counter either — retrieval-role models still have no `ESCALATION_PATH` alternative to escalate to, so nothing here changes. Instead it adds two new, independent counters that reuse C48/C49's tool-availability/degradation mechanisms, not `escalate()`, and live in §6/§9 rather than in `Budgets` above — see the resolution there for why they're deliberately kept out of this dataclass.

A same-pass gap check confirmed two things need no further change: §5.4's suspend/resume trigger table needs no new row, for the same reason C44's own gap check already established for the original escalate-threshold counter — an escalate-threshold breach (of any kind, now including gateway) never pauses the loop, so it was never a suspend/resume event to begin with; and §3.3's stuck-repeat detection needs no change either — "retrying after an `INFRA`-category failure is never penalized" (below) is a separate mechanism (whether a repeat counts as *stuck*) from this new counter (whether consecutive `GATEWAY_ERROR` results trigger escalation), and the two coexist without conflict, now cross-referenced at §3.3 directly. Updated §3.2 (`Budgets`, the "two kinds" note, this resolution, and self-audit A1's narrowing note), §5.1 (the `INFRA` row's loop-behavior column), §4.1 (the escalation trigger description), and §13 item 63 (resolved) / item 67 (new).

### 3.3 Stuck-repeat detection

A repeat is only "stuck" when **all** of the following hold:

1. The tool is mutating: `edit_file`, `create_file`, or `run_command`.
2. The current attempt is identical to the immediately preceding attempt on that tool.
3. The preceding attempt's failure was categorized `SELF_CORRECTABLE`.

Repeating a read-only tool (`read_file`, `list_directory`, `search_code`, `grep_search`, `get_diagnostics`) is never penalized, regardless of outcome. Retrying after an `INFRA`-category failure is never penalized, regardless of which tool. Both are treated as normal loop behavior. **Unchanged by v0.49/C47 (§3.2):** this is about whether a repeat counts as *stuck* — a separate question from whether consecutive `GATEWAY_ERROR` results trigger escalation, which is now tracked independently. An `INFRA` failure, `GATEWAY_ERROR` included, still never makes a repeat "stuck" here. **Also unchanged by v0.50/C50 (§6/§9):** the two new retrieval-specific withdrawal/degradation counters there are a third, independent consumer of the same `GATEWAY_ERROR` signal, coexisting with this rule the same way `gateway_escalate_threshold` already does — retrying `search_code` after an `INFRA` failure still never counts as *stuck* here, regardless of whether that same retry is also feeding one of §6/§9's counters toward a withdrawal.

**ASSUMPTION:** "identical attempt" is defined as same tool name plus same normalized arguments — same file path and same list of find/replace blocks in the same order for `edit_file` (updated for the B4 deep dive: the comparison is now over the whole `edits` list, not a single block, and order matters since blocks apply sequentially — the same blocks in a different order aren't the same attempt); same file path and content for `create_file`; same `argv` list for `run_command`. Whether "normalized" includes whitespace/ordering normalization is unspecified; this draft assumes exact structural equality after JSON-normalizing the argument object (key order doesn't matter, string content does).

### 3.4 `done` and the verification gate

`done` never ends the trajectory by itself. Calling it triggers a verification gate; the model's self-declared "I'm finished" is never trusted alone.

```python
def on_done(args: DoneArgs):
    if set(args.files_changed) != workspace.staged_paths():
        trigger_review_pause("files_changed mismatch")  # §6.5 — does NOT affect what follows
    if not verification_suite_configured():
        proceed_to_commit_flow(verification_status="skipped — no suite configured")  # §3.5, §7.5
        return
    result = run_verification(scope=workspace.staged_paths())  # always Workspace's real state
    if result.new_regressions:
        # feeds back as an observation; counts toward "verification"-kind budget
        continue_loop()
    else:
        proceed_to_commit_flow(verification_status="passed")  # §7.6
```

**Resolved (v0.20, Tier-2 checklist C8):** when no verification suite is configured for the repo, `run_verification` is never invoked at all — there's nothing to run a baseline or post-edit check of. `on_done` routes straight to the commit flow instead, carrying a `verification_status` that gets surfaced at diff-review time (§7.5) rather than the trajectory silently behaving as if a check had passed. See §3.5 for the full resolution and the reasoning behind dropping auto-detection entirely.

`files_changed` is used **only** as a trust/consistency signal that can trigger a review pause on mismatch. It never drives which files get diffed, verified, or committed — that is always derived from Workspace's own staged-file state (§7.2).

### 3.5 Verification semantics — baseline diff

Verification is baseline-diffed: only *new* regressions block completion; pre-existing failures are informational only.

- A baseline run of the verification suite (tests/lint/typecheck/build — whichever is configured) executes once, in the sandbox, against the pre-existing repo state.
- At `done` time, the same suite re-runs against the sandbox with staged edits applied.
- A check that failed in both runs is pre-existing and informational. A check that passed at baseline and fails post-edit is a new regression and blocks completion. A check that failed at baseline and passes post-edit is a net improvement, also informational (never required, never penalized).

**Resolved (B5 deep dive):** the baseline run is captured **eagerly, anchored to the first dispatch of a mutating tool — not to literal session start, and not deferred to first `done`.** Concretely: the suite runs once, in the sandbox, immediately before the first call to any of the three mutating tools (`edit_file`, `create_file`, `run_command` — §6) is dispatched, regardless of whether that particular call ends up succeeding or actually changing anything on disk. This is a deliberately different (and simpler) anchor than "before Workspace's first staged edit actually lands": for `edit_file`/`create_file` the two coincide exactly, but a `run_command` side-effect (§7.3) is only ever discovered *after* that command has already executed — there's no way to insert a capture "before" a specific `run_command` call once the harness already knows, in hindsight, that it was the edit-producing one. Anchoring to dispatch rather than outcome sidesteps this: the harness only needs a call's tool name before running it, which it always has. A session that never calls any mutating tool never triggers a baseline run in the first place — and, independently (v0.20, Tier-2 checklist C8), a session against a repo with no verification suite configured at all never triggers one either, regardless of how many mutating tools it calls: with nothing to run a baseline or post-edit check of, `run_verification` is never invoked in the first place. See §3.5's C8 resolution below for that second condition.

This is deliberately not the same thing as "run it at turn 1 no matter what," but it's also narrower than "free until the first edit actually lands." The five non-mutating tools (`read_file`, `list_directory`, `search_code`, `grep_search`, `get_diagnostics`) can be called any number of times first, for free — baseline still only runs once, right before whichever mutating call comes first, however many read-only turns precede it. `run_command` itself, however, always counts as that trigger on its *first* use in a session, even when that particular invocation turns out to be read-only in effect (e.g. running the test suite once just to check current status, or a bare `git log`) — because §6 classifies `run_command` as mutating regardless of what any single call actually does, and the harness has no way to know in advance which calls will and won't produce a side-effect. The reason this timing is free rather than merely early is mechanical, not incidental: per §7.3, the sandbox is only ever re-synced with Workspace's *staged* edits, so up until the first mutating-tool dispatch, the sandbox is already, by construction, identical to the pre-existing repo state — no revert, no second sandbox, no special-cased snapshot. The existing pre-command state that §7.3's change-detection already inspects before every `run_command` is the same checkpoint this reuses; nothing new is added to capture it.

**Considered and declined (B5 deep dive):** deferring capture further, to the first `done` call (the old draft's approach), was considered and declined. By the time a model calls `done` for the first time it has almost always already staged at least one edit, so the sandbox is no longer pristine — getting a true baseline at that point would require either reverting the live sandbox's staged edits, running the suite, and restoring them, or standing up a second, throwaway sandbox seeded from the real repo — mechanism that does not exist anywhere else in this spec, invented solely to save one verification run. It also concentrates that cost at the worst possible moment: the first `done` call would silently absorb roughly double the sandbox work (a revert/restore or dual-sandbox pass, plus the post-edit run) compared to every other `done` call in the same session, right when the model is trying to close out the task. The dispatch anchor gets nearly the same efficiency benefit — a session that never calls a mutating tool at all pays nothing — without that added mechanism or its cost concentration. The one case first-`done` capture would still save that this anchor does not is a session that calls at least one mutating tool and is then abandoned before ever calling `done`; this draft accepts paying the baseline cost for that case as the cheaper trade against inventing new sandbox machinery.

**Resolved (v0.20, Tier-2 checklist C8 — closes §13 item 7's remaining half):** "the verification suite" is defined by explicit, per-repo configuration only — no language-heuristic auto-detection, and no fallback to one. Two real systems facing a closely analogous problem both land here with no guessing fallback at all, not just a mild preference for one: Aider requires an explicit `--test-cmd` and runs nothing automatically if it's unset; SWE-bench's own evaluation harness — architecturally the closer precedent, since it also needs the command known before any model touches the code, the same requirement B5's dispatch-anchored baseline capture (above) has — maps every repository to an explicit, hand-curated command via a registry, never inferred at runtime. GitHub Copilot's coding agent and Claude Code both confirm the same lesson from the other direction: neither one requires configuration, but neither reliably gets by without it either. Copilot's own documentation admits that skipping its optional setup file leaves it falling back to "a process of trial and error" that is explicitly "slow and unreliable... and in some cases... completely unable" to work at all; Claude Code has no automatic check by default whatsoever unless a human wires one up, to the point that Anthropic's own guidance states plainly that without one, "you become the verification loop." Nothing found here — real precedent or cautionary tale — supports the auto-detection fallback the earlier draft leaned toward; dropped rather than kept as an untested hedge.

A repo with no configured verification suite is a distinct, explicit state, not a guessed one: the baseline capture above and the whole `done`-time verification gate (§3.4) are both skipped for that trajectory rather than the harness inventing a command. This is never silent: `on_done` marks the diff presented at review time (§7.5) as unverified — a deterministic, mechanically-attached signal, the same way `summary` and the diff itself already are, not something the model asserts or can suppress. A repo with no configured suite gets zero automated regression protection under this design — a real, named tradeoff, not a hidden one — but it's stated plainly to whoever reviews the diff rather than the trajectory quietly proceeding as if a check had passed.

**Resolved (v0.22, Tier-2 checklist C10 — closes §12 item 3):** whether verification should attempt to confirm the task's actual target was fixed (vs. only detecting new regressions) was named as a known gap with no accepted solution; this draft now accepts that gap explicitly, as a permanent v0 limitation, rather than leaving it merely unaddressed. The one real mechanism found that mechanically answers this question — SWE-bench's evaluation harness, via its `FAIL_TO_PASS`/`PASS_TO_PASS` test split — depends on a human having already curated, ahead of time, exactly which test(s) are expected to flip from failing to passing for that specific task; a general-purpose agent handling arbitrary day-to-day work has no equivalent oracle available at runtime, so that precedent doesn't transfer as a mechanism, only as proof the question is answerable in principle given foreknowledge this deployment doesn't have. Neither of the two closest production systems closes this gap either: Claude Code and GitHub Copilot's coding agent both stop at "no new regressions," relying on the human reviewing the diff to judge whether the actual intent was met — the same backstop Lucifer's own §7.5 review step already provides. Accepting this outright, rather than continuing to carry it as an open question that looks solvable but isn't given what's actually available at runtime, is a legitimate close, not a compromise.
