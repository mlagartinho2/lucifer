## 2. Model Registry Shape

```python
class ModelSpec:
    id: str                      # gateway-registered name, OR the real deployment name at a direct_endpoint (see below)
    role: Literal["chat", "embedding", "reranker", "speech"]
    context_window: int | None   # real per-model values below — Tier-3 checklist C12, resolved v0.44
    max_output_tokens: int | None  # real per-model values below — Tier-3 checklist C12, resolved v0.44; None for non-generative roles, see below
    supports_tool_calling: bool  # required True for anything in the triage/escalation pool
    tool_call_reliability: Literal["native", "flaky", "unknown"] | None  # ASSUMPTION/placeholder — see §4.3
    compact_threshold_pct: float | None  # per-model override — resolved v0.55 (Tier-3 checklist C17) as left unset for all four real registry models, pending real telemetry; see §8
    is_default_triage_model: bool = False  # exactly one chat-pool model must set this True — §4.1, resolved v0.18
    direct_endpoint: DirectEndpointConfig | None = None  # v0.65, Tier-3 checklist C53 — set only for a model reached outside the Gateway; None means Gateway-routed, the default for every entry but the two direct-Azure embedding tiers (text-embedding-3-small/-large, v0.66)

class DirectEndpointConfig:
    provider: Literal["azure_openai"]        # the shape of the direct call, not a free-form URL — closed set, extend only for a real, confirmed second case
    api_base_env_var: str                    # e.g. "AZURE_OPENAI_EMBEDDING_ENDPOINT" — the endpoint URL is read from this environment variable at call time, never inlined in config
    api_key_env_var: str                     # e.g. "AZURE_OPENAI_EMBEDDING_API_KEY" — same indirection, credentials never appear in ModelSpec or in this document
    deployment_name: str                     # the real Azure deployment name, which may differ from ModelSpec.id
```

**Resolved (v0.65, Tier-3 checklist C53; extended v0.66 to `text-embedding-3-large`):** `direct_endpoint` is new — the first field this registry has needed for a model that doesn't sit behind the Gateway at all. `text-embedding-3-small` and `text-embedding-3-large` are both reached directly against a separate Azure OpenAI subscription (§1), each with its own `direct_endpoint` entry (distinct `deployment_name`, per the table below), so a `ModelSpec` entry alone (Gateway-registered name, chat-completions-shaped call) can't represent either correctly; every other current registry entry leaves this field `None` and is unaffected. Grounded in how production multi-provider LLM proxies actually handle a routing exception like this, checked rather than invented: LiteLLM's router accepts a per-model `litellm_params` override (`api_base`/`azure_endpoint`/`api_key`) alongside its `custom_llm_server`/`custom_provider_map` hooks for a non-standard backend, with credentials referenced via an `os.environ/VAR_NAME` indirection rather than written inline — adopted directly as `api_base_env_var`/`api_key_env_var`'s own shape; Portkey's config carries the equivalent as a single per-model `custom_host` field. Both keep one registry and one calling convention from the orchestrator's point of view, pushing the routing distinction down into per-model config rather than surfacing it as a second parallel code path — the same shape adopted here. OpenRouter was checked and set aside as a negative precedent: it has no mixed-routing concept at all, every listed model is itself proxied through OpenRouter, which isn't a real option for representing a model this deployment reaches directly. `provider` is deliberately a closed `Literal`, not a free-form string or URL template, matching this draft's existing discipline of stating a real, confirmed shape rather than a speculative general one (the same restraint self-audit A1/B2/B6 already apply elsewhere) — it widens only once a second real direct-access case actually exists, not preemptively. Real values for `api_base_env_var`/`api_key_env_var`/`deployment_name` are genuine deployment data, not a design question — tracked as this same checklist item's remaining half, alongside C12/C13's own status.

```python
CONTEXT_WINDOW_AND_MAX_OUTPUT: dict[str, tuple[int | None, int | None]] = {

    "Qwen/qwen-reranker-8B":       (8_192,     None),   # reranker role — future candidate, not in the live v0 registry (§1, v0.65) — kept for the dormant upgrade path

```

**Resolved (v0.65, Tier-3 checklist C53 area; revised v0.66 — activation is config, not a one-time pick):** `text-embedding-3-small` added — real, public OpenAI spec (8,191-token context, confirmed against OpenAI's own current documentation; embedding role, `max_output_tokens=None` for the same never-generates reason `Qwen/qwen-embedding-8B`'s own row already established). `text-embedding-3-large` is added alongside it, both confirmed reachable via the same direct Azure OpenAI subscription (§1) — real, distinct `DirectEndpointConfig` per tier, since Azure OpenAI deployments are provisioned per model: `provider="azure_openai"` and (in this deployment's own convention) the same resource, so `api_base_env_var` can be shared, but a distinct `deployment_name` per tier, and `api_key_env_var` shared or split depending on how this subscription's own secrets are actually organized — real values for both tiers are C53's own remaining scope, unchanged in kind by this revision, just now covering two entries instead of one.

`-small` is the default *active* entry — exactly one embedding-role `ModelSpec` sits in the *live* registry config at a time, reused directly from the mechanism C48/C49 already established for the Qwen retrieval models ("a model absent from the loaded registry reads as unavailable everywhere else in this spec," and the reverse — a model present with `role="embedding"` is what `search_code` actually calls). Switching the active tier is therefore a pure config change, not a design decision requiring a new mechanism each time: point the live registry's one `role="embedding"` slot at `text-embedding-3-large` instead, no code change, the identical "config presence gates activation" discipline already used for bringing a future Qwen model online. This is a genuine widening from v0.65's original framing, which treated `-small` as chosen *instead of* `-large`, full stop — real deployment access turned out to make both tiers equally callable today, not one now and one later, so the "config-swappable, not deleted" treatment already given the dormant Qwen path applies here too, just to a same-vendor tier choice available immediately rather than a future one.

**Load-at-startup only, no runtime hot-swap (v0.67):** editing the config to switch the active tier takes effect on the *next* fresh Lucifer process, not inside a trajectory already running — no in-place reload of a live session. This isn't a new constraint invented for this mechanism; it's the same behavior the registry has always had, made explicit here because it's genuinely consequential for this specific case. The v0.42→v0.43 changelog entry already established why: the model registry is "config-driven, validated at load/startup, no persistent-daemon reload step needed, given the locked v0.39 deployment topology — every session is already its own fresh process" (a developer's own CLI invocation, or a container spun up fresh per CI job, §1). Nothing in this spec's design ever assumed a long-lived daemon process that config changes would need to reach mid-flight, so there's no reload mechanism to build or omit — restarting Lucifer *is* how any registry change, this one included, takes effect, the same way it already is for adding a new chat-pool model or editing `ESCALATION_PATH` (§4.3's own load/startup validation, v0.17). A running trajectory that has already resolved its `role="embedding"` model for the session keeps using it for that session's whole duration, even if the config file underneath it changes mid-run — consistent with, and reinforced by, the reindex requirement below: a config edit that took effect mid-trajectory without a restart would leave a running `search_code` call querying an index built for a different embedding model entirely, exactly the mixed-vector-space problem that paragraph exists to prevent.

`-small` stays the sensible default rather than an arbitrary one: `-large`'s real quality edge is genuine but not overwhelming for this deployment's actual task — MTEB 62.3 vs. 64.6 general-purpose, MIRACL 44.0 vs. 54.9 multilingual retrieval (a larger gap, but Lucifer's own retrieval is source-code search, not multilingual prose) — while its cost is 6.5x `-small`'s (\$0.13 vs. \$0.02 per 1M tokens) and its dimensionality is 3,072 vs. `-small`'s 1,536, doubling persistent-index storage for a quality delta that hasn't been measured against Lucifer's own chunking/retrieval design specifically. No successor or newer embedding model exists from OpenAI/Azure as of this research (September 2026) that would change either tier's standing. `Qwen/qwen-embedding-8B`/`Qwen/qwen-reranker-8B`'s own rows are unchanged in value — real target specs, unaffected by their live-registry status — only their comment is updated to reflect they're a documented future candidate, not a currently-deployed entry.

**Operational consequence, named rather than left implicit (v0.66; sequencing tightened v0.67):** switching the active embedding-role entry — either tier swap, or later activating a Qwen model — requires a full persistent-index rebuild, not an incremental update. Embeddings from two different models occupy non-comparable vector spaces (different dimensionality entirely for `-small` vs. `-large`, 1,536 vs. 3,072; a different model family outright for Qwen), so a mixed index would silently compare vectors that were never meant to be compared. This is standard operational practice for any embedding-backed retrieval system, not a gap specific to Lucifer's own design, and isn't a case §9's existing staleness-tracking mechanism (commit-time incremental updates against a fixed embedding model) needs to detect or automate — changing which model is active is itself the operator's deliberate act, and triggering a full reindex as part of that same config change is the operator's responsibility, the same way rotating `direct_endpoint` credentials or adding a model to the live registry already are. The real operational sequence, made explicit by the load-at-startup resolution just above: edit the config, rebuild the persistent index against the newly active model, then (re)start Lucifer — not necessarily in that exact order between the first two, but both must be done before the next session starts, since a fresh process picks up the new config immediately (above) and would otherwise query a stale-model index from its very first `search_code` call.

**Narrowed (v0.68 — see §9's new resolution, Tier-4 checklist C54):** the "rebuild... is the operator's responsibility" framing just above is narrowed, not reversed. §9 now keys the persistent index by both repo identity and the active embedding model's identity, so "no index recorded for this (repo, active-model) pair" is a fact the harness detects and acts on itself — on the very next `search_code` call after a restart — rather than a step the operator has to separately remember to run. The real operational sequence shrinks to just the first two steps above: edit the config, then restart. The third step (rebuild) is no longer something the operator does at all; it's something the next session's first qualifying `search_code` call does automatically, blocking that one call while it happens (§9). This closes a real gap the original wording left implicit: previously, an operator who forgot the manual rebuild step would get either a silently mixed-vector-space index or a confusing failure with no clear cause; now there's no manual step left to forget.

**Resolved (v0.44, Tier-3 checklist C12):** real per-model values, supplied directly rather than sourced from public documentation — several of these are org-internal Gateway deployments with no public spec sheet to verify against, so this is genuine deployment data, not a researched precedent. Every budget calculation in §3.2 and §8's `usable_budget()` that references "% of context window" now runs against real numbers for the models with published-here values, rather than a shared illustrative placeholder.

Two small clarifications made while integrating this data, not new design questions of their own. First, `max_output_tokens` is retyped `int | None`: `Qwen/qwen-embedding-8B`/`Qwen/qwen-reranker-8B` are non-generative roles (embedding, reranking) that never produce text, so the field doesn't conceptually apply to them, and nothing in this spec's mechanisms reads it for a non-`"chat"`-role entry (`max_tokens_for()`, §4.4, is only ever invoked for the triage/escalation pool) — `None` records that accurately rather than standing in for a missing number. Second, `openai/whisper-large-v3`'s own real spec (448) maps to a decoder/output ceiling, not a `context_window` in the text-model sense its architecture doesn't have (a fixed-size mel-spectrogram input, not a token-counted context) — recorded as `max_output_tokens=448`, `context_window=None`, for registry completeness only, since this model stays out of scope for v0 per §1 and nothing computes against it. `context_window` is retyped `int | None` to accommodate this one real case, not as a general escape hatch — every in-scope chat/retrieval model has a real value.

This directly unblocks part of C15's own remaining gap (§3.2, v0.27): `token_budget` was left unpicked specifically because it "only becomes a real number once §2's own context_window/max_output_tokens question... is answered with actual model specs" — that precondition is now met, but the number itself is still a separate judgment call (how many tokens a trajectory should reasonably spend, not just what a single call can hold), not resolved by this pass — tracked at C15 itself, not folded into C12.

**Resolved (B6 deep dive):** `max_output_tokens` here is the model's own hard ceiling — a registry-level capability fact, never requested-per-call. §4.4 adds a separate, per-invocation `max_tokens` (how many tokens *this specific call* is allowed), which must never exceed this field regardless of what effort level requested. The two are related but distinct: this one bounds what the model can physically produce; that one bounds what one call is asked for.

**Resolved (B2 deep dive):** added `tool_call_reliability` as a registry field. Not itself a locked requirement, but needed to make the escalation-ordering criteria in §4.3 concrete: a model can be strong at reasoning about code and unreliable at emitting well-formed tool calls, or the reverse, and escalation triggers separately on tool-kind vs. verification-kind failures (§3.2) — so which axis a model is weak on matters for what "stronger" should mean when picking the next step. Populated empirically (from testing against the gateway, against Lucifer's own tool schema), the same status as `context_window`.

**Resolved (v0.18, Tier-1 checklist C6 — closes §12 item 14):** kept, as documentation-only. Nothing in this spec reads it programmatically anymore — `ESCALATION_PATH` (§4.3) is operator-declared, not computed from it — but it stays in `ModelSpec` as reference context for whoever composes that config: a human ordering models by hand benefits from seeing each one's measured tool-call reliability next to its name, even though no mechanism consumes the field automatically. Removing it outright was the alternative considered; kept instead since an unread-but-informative registry field costs little to carry, and the composition-time context it offers a human operator is real, not merely decorative.

**Resolved (§12 item 11 deep dive):** added `compact_threshold_pct` as a registry field, same shape and status as `tool_call_reliability` — optional, empirically populated later, falling back to a document-level default (§8) when a model has no override set. Closes cross-check A1: the old draft's compaction section made this a per-model field feeding a `usable_budget()` formula; this draft's compaction section (§8) previously expressed the trigger as one flat percentage applied to every model's own `context_window` alike. Grounded in real research rather than asserted: Chroma Research's "Context Rot" study (18 frontier models tested) found every model's real usable context degrades well before its advertised limit, and — while the study doesn't hand over a clean small-model-vs-large-model breakdown — it does confirm the degradation *curve's shape* differs model to model even though the *direction* (always downward) doesn't, which is exactly the empirical basis the old draft's per-model override was reaching for. See §8 for the resulting mechanism and the reasoning for moving the illustrative default down from 80%.
