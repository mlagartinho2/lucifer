## 7. Workspace & Staging Model

### 7.1 Core model

All edits are staged in memory (Workspace); nothing touches the real filesystem until an explicit `commit()`. Workspace is the authoritative record of what the agent has done in-session, independent of the (token-budgeted, compactable) transcript (§8).

### 7.2 File status and staleness

```python
class WorkspaceFile:
    path: str
    status: Literal["unmodified_tracked", "modified", "created"]
    staged_content: str
    last_exposed_hash: str     # server-side — what content was last shown to the model
```

- File staleness checks are server-side: the harness tracks what content was last exposed to the model for a given path and compares against that at edit time. This never depends on the model echoing back a hash itself — the model doesn't supply or verify a hash; the harness does the comparison. A mismatch (someone/something changed the file server-side since it was last shown) is `SELF_CORRECTABLE` / `STALE_FILE_VIEW`, prompting a fresh `read_file`.
- "Currently staged" is always derived from each file's own `status` field (`modified` or `created`) — never tracked as a separate parallel set that could drift out of sync with per-file state.

### 7.3 Sandbox: synced copy, host-side change detection

- `run_command` executes against a synced sandbox copy of the repo — not the real repo, not a pure in-memory simulation.
  **ASSUMPTION (sync timing unspecified):** the sandbox is re-synced — real-repo base plus Workspace's current staged edits applied on top — before each `run_command` invocation, so the sandbox always reflects Workspace's live staged state at command time.
- Sandbox change-detection uses a host-side content-hash snapshot walked by the orchestrator, not git state inside the sandbox (git-state-based detection was tried and rejected after repeated failure modes — `.gitignore` interactions, detached-HEAD edge cases, etc.). After a `run_command` execution, the orchestrator walks the sandbox filesystem, hashes contents, and diffs against the last snapshot to find what the command changed on disk.
- Detected changes are folded back into Workspace as new staged edits, subject to: the sensitive-path exclusion (§7.4) always wins; `expected_outputs` (§6.2) can rescue an otherwise-excluded-as-noise path but never a sensitive one.
- The verification baseline run (§3.5) reuses this same pre-command checkpoint rather than a mechanism of its own: it's captured at the sandbox state that exists immediately before the first dispatch of any mutating tool (`edit_file`, `create_file`, or `run_command`) in the session — not at whichever specific call turns out to actually change something, since for `run_command` that's only ever known after the fact, once this same change-detection step has already run.

### 7.4 Sensitive-path predicate

One shared predicate, `is_sensitive_path(path) -> bool`, reused everywhere a sensitivity check is needed: sandbox change-detection filtering, `edit_file`/`create_file` dispatch (blocks direct edits), `run_command`'s `argv`/`cwd` path check (§6.2, consistency-check fix — previously missing), `commit()` (defense in depth), diff-review flagging.

For content, the most directly on-point real precedent isn't a general-purpose coding agent at all — it's `aiignore-cli`, an open-source tool purpose-built to protect secrets from AI coding agents specifically, with a real, maintained pattern list spanning several categories this list previously missed entirely: cloud configuration beyond AWS (`.gcp/`, `.azure/`, `.kube/config` — this list had zero non-AWS cloud coverage), package-registry auth dotfiles (`.npmrc`, `.pypirc`, `.netrc` — personal auth tokens for package registries, a distinct category from env vars/SSH keys/cloud config the original list didn't touch at all), GCP service-account keys (`service-account*.json`, corroborated independently by a second practical guide on protecting files from AI agents), and infrastructure-state files (`*.tfstate`/`.terraform/**` — Terraform state routinely contains plaintext secrets/resource IDs, a well-known real leak vector). Nine new patterns added on this basis, the existing nine left untouched.

Deliberately not adopted from that same source, named honestly rather than silently dropped: database files (`*.sqlite`/`*.db`, `dump.sql`) — legitimate, common dev artifacts, not inherently sensitive, and a real false-positive risk if blocked outright; AI/MCP tool configuration (`mcp.json`, `.aider.conf.yml`, and similar) — a different category (tool config, not credentials) that doesn't fit this predicate's own definition; and `*.crt`/`*.cer` — these are typically *public* certificates, not secrets, and including them would be a real content mistake, not just unnecessary breadth. The bare `*secret*` wildcard from the same source was also declined — too broad, with real false-positive potential against ordinary source files (e.g., a test file named for secret-handling logic).

**Resolved (self-audit A4):** by the same pattern the locked decisions establish for sensitive paths, this draft adds one shared `is_within_repo_root(path) -> bool` predicate too, reused everywhere a repo-boundary check is needed: `edit_file`/`create_file` dispatch, `run_command`'s argv path-resolution check (§6.2), and `commit()`'s defense-in-depth re-check (§7.6). **ASSUMPTION:** unlike `is_sensitive_path`, a shared predicate for the repo-root boundary was not itself a locked requirement — applying the same "one shared predicate, reused everywhere" shape here is a design choice made for consistency, not a stated decision.

**Resolved (§12 item 13 deep dive, symlink handling — cross-check A3):** both shared predicates resolve a path to its real target — following any symlink — before checking, everywhere they're used (listed above and in §6.2). Checking the literal argument string instead would leave a real hole: a symlink created inside the repo pointing at, say, `~/.ssh/id_rsa` or anywhere outside the repo root reads as an in-bounds, non-sensitive path under a literal-string check, while actually resolving somewhere both predicates exist to block — a genuine symlink-escape, not a hypothetical one. Grounded in real precedent rather than invented: Claude Code's own sandbox does the analogous thing for its protected settings paths — when a symlink appears at a protected path, the sandbox extends protection through the symlink to whatever it points to, rather than stopping at the symlink's own literal path. This is a small, targeted extension of predicates already defined as shared and reused everywhere a check is needed, not a new mechanism.

**Resolved (§12 item 13 deep dive, credential-file handling — cross-check A3):** credential files (`.env*`, `id_rsa*`, `.aws/**`, `.ssh/**`, etc.) are not physically removed from the sandbox filesystem at init — this draft declines that mechanism rather than adopting it. They're already covered by `is_sensitive_path`'s own starter list above, and real precedent confirms reuse over new machinery is the right call here, not just the cheaper one: Claude Code's own sandbox doesn't scrub credential files from disk either — its documented default is "read access to the entire computer, except certain denied directories," which still permits reading `~/.aws/credentials`/`~/.ssh/` unless a deny rule names them explicitly. The mechanism in both cases is the same shape: a deny-list (here, `is_sensitive_path`) checked before access, not a filesystem wiped clean of secrets beforehand. What item 13 was actually reaching for with "a layer distinct from the model-facing checks" is real, though, and still holds: `is_sensitive_path` gates dispatch (already resolved, above and §6.2), but the sandbox's own isolation primitive needs to independently enforce the same denial at its OS/mount boundary — the same two-gate shape v0.2's `PATH_OUTSIDE_REPO`/`COMMAND_NOT_ALLOWLISTED` resolution already established for the repo-boundary case, extended here to credentials specifically. **Resolved (v0.18, Tier-1 checklist C1 — closes §13 item 26):** with the primitive now chosen (bubblewrap + seccomp, §6.2), this second gate is concrete rather than deferred: `bubblewrap` constructs the mount namespace explicitly, bind-mounting in only the sandbox directory — credential paths like `~/.aws/`, `~/.ssh/` simply aren't bound into the namespace at all, so they're unreachable regardless of what `is_sensitive_path` catches or misses at the dispatch-time gate above. That's a stronger version of the same "second gate" shape this draft already committed to, not a new mechanism. This applies to paths genuinely external to the sandbox directory (`~/.aws/`, `~/.ssh/`, and similar) — excluded from the mount namespace entirely, unreachable at any permission level. `.git/**`, also on `is_sensitive_path`'s starter list above, needs different treatment since it sits *inside* the sandbox directory that has to be bound in for `run_command` to function at all, and §6.2 already allows read-only git operations (`log`, `blame`, `diff`, `show`, `status`) that need to read it: **Resolved (v0.36, Tier-4 checklist C37):** `.git/**` stays mounted, but forced read-only even though its parent (the sandbox directory) is otherwise read-write — present and readable, never writable by anything other than the harness's own `commit()` boundary (§7.6). See §6.2 for the full concrete bind-mount list this is part of.

### 7.5 Diff review and partial approval

Partial diff approval does not commit the approved subset while any file in the same round is still rejected or pending retry — approved files stay staged until the whole round resolves, unless the reviewer explicitly overrides.

**Resolved (v0.34, Tier-4 checklist C34):** a "round" is the set of files currently staged in Workspace (`workspace.staged_paths()`, §7.2) at the moment any suspend/resume checkpoint is reached — not limited to a `done` call or a risk-flagged pause specifically. The narrower two-checkpoint wording this replaces undercounted what §5.5 already establishes: "approve a partial diff subject to the hold-the-round rule" is listed as a resume option available at *every* suspend, not just risk-flag's — meaning a human resuming from a tool-kind abort, a verification-kind abort, a budget-exhaustion suspend, or `commit()`-time external-drift review (six of §5.4's seven trigger rows — every one but the terminal `UNSAFE` row, which never reaches suspend/resume at all) can just as validly choose partial approval as one resuming from `done` or a risk-flag. Broadening the checkpoint list to match closes that mismatch rather than introducing a new one: whichever of §5.4's trigger types actually reaches suspend/resume, whatever's staged in Workspace at that moment is the round, and "hold the whole round" (above) applies identically regardless of which trigger got it there.

Out of v0 scope, per locked decisions: dependency analysis to determine true file-coupling for partial-approval safety (the "hold the whole round" default is the deliberately simpler substitute) and auto-merge on an external-change conflict at commit time (conflicts are detected and refused, never auto-resolved).

### 7.6 `commit()`

```python
def commit(paths: list[str] | None):
    # paths=None  → "no argument given" (Resolved, v0.35, C35: defaults to committing all currently-staged files, mirroring plain `git commit`'s own no-pathspec behavior)
    # paths=[]    → explicit empty list, distinct from paths=None — commits nothing, is a valid no-op call
    ...
```

- Single atomic git commit over explicit target paths — never `git commit -A`.
- **Resolved (v0.2), defense-in-depth:** re-validates every target path against the sensitive-path predicate (§7.4) and the repo-root boundary (via the shared `is_within_repo_root` predicate added in §7.4) at the commit boundary itself, not only at `edit_file`/`create_file`/`run_command` dispatch time. This is a second gate behind those tools' own `PATH_OUTSIDE_REPO`/`SENSITIVE_PATH_BLOCKED` checks — §5.1's reasoning for keeping those `SELF_CORRECTABLE` rather than `UNSAFE` explicitly depends on the staging model providing a real second checkpoint before anything touches disk, so this makes that checkpoint actually exist rather than assuming it.
- Detects and refuses real-repository changes made outside the session rather than silently overwriting them. **Resolved (v0.35, Tier-4 checklist C35):** compares current real-repo `HEAD` against the harness's own last-known-good `HEAD` — not a value fixed once at session start, but a running value initialized to the session's captured start-`HEAD` (§7.7) and then updated to each new commit's own SHA immediately after every successful `commit()` call. A mismatch refuses the commit and routes to the review/pause path (§5.5) rather than being silently retried by the loop, since auto-merge is explicitly out of scope. This corrects a real bug the original single-fixed-value wording carried: since a session can resolve and commit more than one round over its lifetime (§7.5), pinning the expected value to the *original* start-`HEAD` forever would make the session's own first successful commit look identical to external drift the moment a second `commit()` call checked against it — the trajectory's own legitimate prior work would spuriously block its next commit. Grounded directly in git's own documented semantics for `update-ref`'s compare-and-swap argument: per git's own docs, for a sequence of updates on the same ref, each `<old-oid>` should be "the currently expected value... not the original starting SHA" — the second call's expected value is the first call's own `<new-oid>`. Genuine external drift (something outside the session touching `HEAD` — whichever branch it's attached to, or `HEAD` itself directly if detached, v0.37/C38) is still caught exactly as before; only the session's own prior commits stop looking like drift to its own next one. This running value needs no separate persistence of its own: within one continuous session it's just the harness's own in-memory record of what it last wrote, and across a resume (§5.5, §7.7) the harness simply re-observes the real repo's actual current `HEAD` as its fresh baseline — equivalent to re-running the same start-`HEAD` capture a brand-new session would do, not a second piece of durable state to keep in sync with `workspace.json` (§7.7, C28).
- `commit(paths)` distinguishes an explicit empty list from "no argument given" — never conflates the two. **Resolved (v0.35, Tier-4 checklist C35):** "no argument given" (`paths=None`) defaults to committing everything currently staged. Confirmed rather than merely carried forward as a guess: this mirrors plain `git commit`'s own real, decades-old behavior with no pathspec given — committing whatever's in the index — and `commit()` is already explicitly modeled as a thin wrapper around real git operations (this section already replaces a plain `git commit` with `git update-ref` for the actual write, below). No new mechanism; the existing default already matches the tool it wraps.

**Resolved (v0.18, Tier-1 checklist C3 — closes §12 item 1):** the ref-level compare-and-swap fix is adopted outright, replacing the plain `git commit` as the actual mechanism. The commit boundary now does `git update-ref HEAD <new-commit-sha> <expected-old-sha>` (v0.37, C38 — see below for why `HEAD` rather than a resolved branch name) rather than a plain `git commit`, with `<expected-old-sha>` being the harness's own last-known-good `HEAD` value the drift check above already tracks and compares against — initialized to the session's start-`HEAD` and updated after each successful commit (v0.35, C35), not a value fixed once at session start. `update-ref` fails atomically if the ref has moved since that expected value was read, closing the separate check-then-write window "compare `HEAD`, then separately commit" left open. This was already identified as the theoretically correct fix and simply never written into the mechanism; there was no real tradeoff to weigh here, just a gap to close.

**Resolved (v0.37, Tier-4 checklist C38):** the ref-level compare-and-swap targets `HEAD` itself, not `refs/heads/<branch>` — a genuine simplification, not just a fix for the detached-HEAD case that motivated it. Grounded directly in git's own `update-ref` documentation, which uses exactly this as its worked example: "Given two arguments, stores the `<new-oid>` in the `<ref>`, possibly dereferencing the symbolic refs. E.g. `git update-ref HEAD <new-oid>` updates the current branch head to the new object." Without `--no-deref`, `update-ref` follows a symbolic ref before writing — and on a normal checkout, `HEAD` *is* a symbolic ref to `refs/heads/<branch>`, so targeting `HEAD` dereferences straight through and updates the branch, identically to the original `refs/heads/<branch>` wording, but without ever needing to resolve or hardcode a branch name. In a detached-HEAD checkout — the default result of `actions/checkout` in an unmodified GitHub Actions workflow, and therefore a real, likely state for a session launched via C27's non-interactive/CI invocation mode, not just a hypothetical — `HEAD` isn't symbolic at all, it holds a raw commit SHA directly, so the identical command just updates `HEAD`'s own stored value, which is the only sensible target when no branch exists to name. One target string now handles both checkout shapes; no branch-name-resolution step is needed at all, where the original wording implicitly assumed one without ever specifying it. A bare-repository checkout is not a shape this needs to handle: §1 already presupposes a working tree (".git exists and standard git plumbing... is usable" against real on-disk files), and virtually every other mechanism in this draft — `edit_file`, `run_command`'s sandbox-copy sync (§7.3), `is_within_repo_root` — already presupposes real files to read, sync, and diff, which a bare repo doesn't have; §7.9 now states this explicitly as a non-goal rather than leaving it an unstated implication. One real, narrow limitation is accepted rather than engineered around: a commit made while detached isn't pointed to by any branch, so unlike a branch-tip commit it's only reachable via `git reflog`/`git fsck --unreachable` until git's own default grace window elapses (`gc.reflogExpireUnreachable`, 30 days by default) — not indefinitely durable the way this draft's other commits are. This is not a risk specific to Lucifer; it's exactly what a human would already face running plain `git commit` in the same detached state, and Lucifer never creates or pushes branches on the session's behalf (§6.2, C5) to route around it the way GitHub Copilot's cloud coding agent does (which always works from a freshly created branch for this reason). Accepted the same way C4 already accepted the working-tree-level commit race — a real, named limitation, not a placeholder standing in for unbuilt machinery.

**Resolved (v0.18, Tier-1 checklist C4 — closes §12 item 2):** the working-tree-level race between checking external drift and writing at commit time is accepted as a documented limitation, not left open pending a fix that doesn't exist. No portable git tooling closes the gap between "read the working tree to stage a commit" and "the working tree hasn't changed since," the way `update-ref` closes the equivalent gap at the ref level above — filesystem-level locking across that whole window isn't something git itself offers, and inventing bespoke locking here would be new mechanism nothing else in this spec needs, for a race that's already narrow (the window is whatever one `commit()` call takes, not an open-ended interval) and whose consequence is refused, not silent (the `HEAD`-mismatch check above still catches the common case of external drift; what's specifically unclosed is a change landing in the narrow window between that check and the write completing). Accepted, the same treatment already given to §9's ssh/https git-URL non-unification (§12 item 12's resolution) — a real, named limitation rather than a placeholder standing in for a design that hasn't happened yet.

### 7.7 Session snapshot marker

Workspace captures a session-level snapshot marker at session start: repo `HEAD` at that point, plus a session ID — in addition to the per-file `last_exposed_hash` values in §7.2.

**Resolved (v0.28, Tier-4 checklist C28):** since checkpoint/resume is implied to exist (the source material explicitly rejects persisting the sandbox's pending-sync queue "verbatim across a checkpoint/resume," saying it's rebuilt from current state instead — which presupposes checkpoint/resume as a real capability), Workspace state is serialized to local disk under `.lucifer/sessions/<session_id>/` as two files, each in the format that matches what it actually holds. `transcript.jsonl` is an append-only JSON-Lines log, one line per `(action, result)` pair, mirroring §3.1's own loop pseudocode (`append (action, result) to transcript`) directly rather than inventing a separate log shape — the same pattern OpenAI Codex CLI's `rollout-*.jsonl` resume files and Claude Code's own per-session JSONL transcripts both use in production, chosen specifically because it's crash-safe by construction: a process killed mid-write loses at most its last, incomplete line, never the file as a whole, unlike a single large JSON blob that must be rewritten in full each time. `workspace.json` is a single JSON file, not a log — Workspace's staged files, their statuses, and the session snapshot marker (repo `HEAD` plus the session ID) are current-state facts that get overwritten in place, not events that accumulate, so a whole-file JSON snapshot fits it better than an append-only format would. It is written atomically (temp file, then rename) specifically to avoid the file-corruption failure mode a same-path in-place overwrite risks on a mid-write crash, a real documented problem for at least one production coding-agent extension (Cline) that persists comparable state as ordinary overwritten JSON. The sandbox's pending-sync queue specifically stays out of both files — it's rebuilt from Workspace's current staged state on resume, per the locked decision, unchanged from this section's prior draft. A SQLite-backed alternative (real precedent: Cursor CLI, opencode) was considered and declined: nothing in Lucifer's design needs to query across multiple past sessions, and a plain-text session directory keeps faith with the value §7.7's own abort-preservation resolution (v0.23, C11) already committed to — that a human should be able to open and inspect a session directory by hand — which a SQLite file makes meaningfully harder than two `cat`-able JSON files do. One consequence needs no separate mechanism: because `transcript.jsonl` captures every invocation, the per-`EffortLevel` invocation tally shown at a `token_budget`-driven resume (§13 item 37) can always be recomputed by replaying it, rather than needing its own persisted counter — resolving that item's persistence question, though not its separate, still-open display-shape question.

**Resolved (v0.23, Tier-2 checklist C11 — closes §12 item 9):** a true, unresumable abort (§5.5) does not delete this directory. No explicit purge/cleanup step is added anywhere in the abort path — whatever Workspace state (staged files, statuses, the snapshot marker) is already sitting in `.lucifer/sessions/<session_id>/` from the persistence mechanism above simply stays there, available for a human to open and inspect, or manually recover from, after the fact. This is a real distinction from resume, not the same path reused: resume actively reads this directory to reconstruct Workspace and continue the trajectory; a post-abort read is just a human looking, by hand, at a session the harness itself will never pick back up. The wind-down step's forced model summary (§5.5) narrates what the model was attempting; this resolution is about the actual staged diff surviving alongside it, not a substitute for it — a reviewer doing a post-mortem gets both the narrative and the real file content, not just one or the other. Grounded in a real incident report from Cursor's own user community: its agent was found to silently run a `git stash` followed by a hard reset, discarding 45 files of uncommitted work with no warning, during what the user believed was a routine operation. The lesson that incident points to — an agent must never let uncommitted work become unrecoverable without deliberate, visible human intent — applies directly here: a human choosing to abort the *session* is not the same as anyone asking to discard the *work* that session produced, so deleting it as an automatic side effect of abort would repeat that same failure mode under a different name. If disk usage from accumulated aborted-session directories ever becomes a real operational concern, that calls for a separate, deliberately-designed retention/cleanup policy later — not something folded silently into the abort path itself.

**Resolved (v0.39, Tier-4 checklist C42):** `workspace.json` is write-through, not periodically synced — rewritten atomically (per its existing temp-file-then-rename requirement, C28 above) after every call that mutates Workspace state: `edit_file`, `create_file`, `run_command`'s post-execution change-fold-in (§7.3), and `commit()`. No batching, debouncing, or checkpoint-only cadence. Ordering relative to `transcript.jsonl` is specified deliberately: for a given action, the `workspace.json` rewrite completes before that action's `(action, result)` pair is appended to `transcript.jsonl`. This makes the two files' relationship asymmetric by design — after a crash, `workspace.json` can be momentarily *ahead* of what `transcript.jsonl` shows (an action fully staged on disk whose transcript entry never got appended), but never behind it — closing exactly the gap C11's (v0.23) abort-preservation guarantee depends on: a human doing a post-mortem after a true abort can trust that the staged diff sitting in `workspace.json` reflects the trajectory's real last state, not a stale snapshot from before whatever the transcript's last line describes.

Grounded in real precedent, specifically the closer architectural analogue rather than the most prominent one considered: Cline — the same comparable coding-agent extension already cited above for `workspace.json`'s own atomic-write requirement — checkpoints its equivalent on-disk state after every single tool use in its real shipped behavior, not on a periodic or batched cadence. Claude Code's own visibly sparser session-persistence cadence was considered and set aside as the wrong comparison to reach for by default here: that cadence is calibrated for a sustained, high-throughput logging workload where per-write cost compounds across many writes, which isn't this loop's actual shape — Lucifer's own trajectory is bounded (`max_iterations`/`wall_clock_seconds`, §3.2) and dominated at every step by LLM round-trip latency, the identical latency profile Cline's own per-tool-use checkpoint already runs inside without it being a real cost concern in practice. A debounced or batched middle ground was considered and declined rather than left unexamined: it reopens the same staleness question this item exists to close, merely at a smaller window instead of eliminating it.

The atomic-write mechanism itself rests on a precondition that §1 now states as a locked fact rather than an assumption: every session's working files, `.lucifer/sessions/<id>/` included, sit on local disk in both of this deployment's real shapes — a developer's own machine, or a container spun up fresh per GitLab CI pipeline job — never network-backed storage. That matters concretely, not just formally: POSIX rename-on-the-same-filesystem is what actually makes the temp-file-then-rename write atomic, and that guarantee (along with the low, roughly-constant latency a local write is assumed to have) weakens or breaks outright on network filesystems, where rename semantics are a documented source of real-world corruption bugs. With locality confirmed, that risk doesn't apply to either of this deployment's actual shapes.

Per-write cost, separately, is real but currently estimated rather than measured, and is named here as a provisional assumption rather than folded silently into the mechanism as settled fact — the same treatment this document already gives other unvalidated numbers pending real telemetry (C15, §3.2). Serializing and atomically rewriting a JSON snapshot of whatever Workspace currently has staged is expected to be negligible next to LLM round-trip latency, for ordinary source-file-sized edits. But that expectation rests on an assumption this spec does not actually enforce anywhere: nothing bounds the size of an individual staged file's content. A session that stages something unusual — a large generated lockfile, a vendored data file, a sizeable binary-adjacent asset checked in as text — grows `workspace.json`'s per-write serialization cost along with it, a case this resolution leaves uncharacterized rather than affirmatively ruling out as safe. This is a newly-surfaced gap in its own right, not merely a caveat on this item, and is deliberately distinct from two existing size-related mechanisms elsewhere in this spec: §5.2's 30,000-character output-size cap bounds captured tool *output* (e.g. `run_command` stdout) at capture time, not staged file content; §5.4/C39's diff-size risk-flag threshold is a *behavioral trigger* over an aggregate review round, not a hard cap on any single file. Neither one bounds what this item is actually about. §9's already-tracked C43 (no cap on how many in-session-edited files' chunks feed the reranking stage) is a second, independent symptom of the same underlying absence — no cap anywhere in this spec on an individual staged file's content size. See §13 item 61.

**Resolved (v0.42, Tier-4 checklist C45):** accepted as a named, documented limitation — no cap on an individual staged file's content size, no new numeric threshold, no new `WorkspaceFile` field. A hard cap would block a legitimate, ordinary edit to a file that simply happens to already be large in the target repo, which this spec has no reason to treat as disallowed; and of the two costs this gap was originally found to bear on, only one still needs a cap. C43's own shared-ceiling resolution (v0.40, §9, above) already bounds the reranking stage's cost independently of individual file size — a session staging one huge file or many ordinary ones now hits the same `MAX_RERANK_CANDIDATES` ceiling either way, so C45 closing doesn't change that cost's shape at all. `workspace.json`'s write-through cost (C42, above) is different: it genuinely cannot be capped here without either blocking legitimate staging outright or reintroducing the periodic-sync staleness C42 itself just closed, undermining C11's (v0.23) abort-preservation guarantee at exactly the sessions most likely to need it — so this cost stays real, named as accepted rather than engineered around, the same treatment already given C4's working-tree race and C38's detached-HEAD reflog window.

A third cost surface, not previously named anywhere in this spec, pays the identical unbounded price for the identical reason and is folded into this same acceptance rather than tracked as a separate item: §7.3's sandbox re-sync, which re-stages Workspace's current content into the sandbox before every `run_command` call, scales with staged-file size exactly the way `workspace.json`'s serialization does — nothing bounds what either is copying.

This resolution also folds in, rather than merely noting alongside, a related imprecision found while checking whether any existing mechanism already covered this gap: §5.4/C39's "unusually large or deletion-heavy diff" risk-flag criterion (§13 item 55, still open on its own numeric threshold) is understood to score an aggregate review round (§7.5, broadened by C34 to every suspend/resume checkpoint), not any single file's absolute content size — so a small, targeted textual change to one already-enormous staged file is not itself unusual by that criterion's own aggregate-lines-changed logic, even though it carries the identical unbounded-size characteristic just accepted above for cost purposes. This is not a new detection gap to fix — a second, size-based risk-flag trigger alongside the diff-size one would be new risk-flag machinery with no more real precedent behind it than the partial/probationary reset already declined for C44 — it's a documented characteristic of accepting no individual-file-size bound at all: whoever eventually picks C39's real numeric threshold (§13 item 55) should do so knowing this scenario exists and isn't independently caught by that criterion either. §5.4's own ASSUMPTION paragraph now carries a pointer back to this finding so it's recorded at its point of relevance too, not left only here.

Individual staged-file size, on the rare occasion anything needs it, is always re-derivable rather than needing a new persisted field: it's just the length of `workspace.json`'s already-persisted `staged_content` for that path (C28, above) — the same don't-add-a-field-for-something-already-reconstructable discipline this draft has applied repeatedly (self-audit A1, B2, C35's running-`HEAD` value). Spec: §7.3, §7.7, §9 (cross-reference), §5.4/C39 (cross-reference), §13 item 61 (resolved).

### 7.8 New file lifecycle

- A newly created file (`status="created"`) that is later rejected in review is removed from Workspace entirely — not left behind as a stale entry.
- `discard()` clears the reverted file's edit history (not just its staged content) — a subsequent fresh edit of that path starts clean, with no memory of the discarded attempt.
- A file with no prior in-session Workspace record (e.g. first touched via a sandbox side effect, §7.3) is checked against the real repo to distinguish "genuinely new" (`status="created"`) from "pre-existing, first touched via a side effect" (`status="modified"`).

### 7.9 Explicitly out of scope (v0)

Locking or arbitration between multiple concurrent Workspace sessions on the same repo is out of scope for now — no multi-session locking is designed here.

**Resolved (v0.37, Tier-4 checklist C38):** a bare-repository checkout (no working tree) is not a supported target — not a newly declined mechanism, just made explicit here rather than left an unstated implication of §1's working-tree-presupposing scope. See §7.6 for the reasoning.
