## 9. Retrieval & Indexing

- **Resolved (v0.65 — supersedes the "temporary bootstrap" framing below):** single-stage retrieval is v0's real, current design, not a placeholder waiting on a future deployment — embedding-based recall only, via `text-embedding-3-small` (accessed directly, outside the Gateway, §1/§2), with no reranking stage. This isn't a design preference; it's what this deployment's actual, checked access supports today: neither `Qwen/qwen-embedding-8B`/`Qwen/qwen-reranker-8B` nor Cohere Rerank (Azure AI Foundry's own dedicated reranker offering, the strongest candidate researched for this role) is reachable, while `text-embedding-3-small` is (§1's v0.65 resolution). The two-stage design immediately below (v0.46) is kept as a documented, config-swappable future upgrade — not deleted, not reverted-to by default — see the compensating-mitigations and kept-seam notes further down for how v0 stays honest about running a smaller, single-stage pipeline in the meantime.
- Two-stage retrieval (original target design — see the v0.46 resolution directly below for the history of why v0 didn't ship it, and the v0.65 resolution just above for why it now stays a documented future path rather than an imminent one): embedding-based recall (via `Qwen/qwen-embedding-8B`) followed by cross-encoder reranking (via `Qwen/qwen-reranker-8B`) on the shortlist.
- Code is chunked by AST/symbol unit, not fixed-size windows.

**Resolved (v0.46, Tier-4 checklist C48):** discovered while gathering C14's real batching data that `Qwen/qwen-reranker-8B` is not yet deployed at the Gateway ("available soon," no firm date) — nothing to test against, and more consequentially, nothing for v0's own two-stage design above to actually call at launch. Two-stage retrieval is the target design, not what v0 ships with: v0 launches on single-stage, embedding-only retrieval — `search_code` returns `adaptive_top_k` results straight from `Qwen/qwen-embedding-8B`'s recall stage, with no reranking step at all. `Qwen/qwen-embedding-8B`'s own real values (C12/C13) are unaffected and already correct; only the reranker side is missing.

No new mechanism bridges the gap, deliberately, and this matches real precedent rather than being invented for this one case: production multi-provider registries (LiteLLM, OpenRouter — the same two already cited for C13's namespaced-string convention) only list a model once it's actually deployed behind a real endpoint; neither is built to represent "coming soon." Once `Qwen/qwen-reranker-8B` is added to the live model registry config — the same config-driven, load-at-startup mechanism already established for the registry generally (§1's v0.39 deployment-topology note, and the reasoning traced through while discussing C47) — `search_code` simply finds a `role='reranker'` model present and runs the full two-stage pipeline as specified above, an ordinary config change, not a code change or a version bump of this spec. No new `ModelSpec` field (e.g., an `available: bool`) is added to express "not deployed yet" either: a model absent from the loaded registry config already reads as unavailable everywhere else in this spec, the same way `ESCALATION_PATH` (§4.3) only ever contains what's actually configured — a second, explicit flag for the identical fact would be new schema surface for no behavioral benefit, the same reuse-over-new-mechanism discipline this draft applies repeatedly (self-audit A1, B2, C35, C13).

Considered and declined: a runtime fallback inside `search_code` itself — catch a failed or missing reranker call and degrade to embedding-only on the fly. That's real, general-purpose resilience machinery, worth having for a model that goes unreachable *after* being live, but it solves a different problem than the one actually in front of this decision, which is a one-time bootstrapping gap, not a recurring runtime failure. Building it now would also risk tangling with C47's still-open gap (§13 item 63, whether escalation triggers when the *active* model goes unreachable mid-trajectory) — that item is specifically about a model that *was* working and drops out mid-trajectory; conflating the two would make C47 harder to reason about, not easier, without buying v0 anything a plain "not yet configured" state doesn't already give it for free.

`adaptive_top_k(model)` (below) needs no change to support this: with no reranker-role model configured, it trims the recall stage's own output directly to the same final count it would otherwise trim reranked results to — one shared final-count mechanism either way, not two. `RECALL_K` (C14, §12 item 4) and `MAX_RERANK_CANDIDATES` (C46, §13 item 62) both stay genuinely open, not resolved by this pass — their real values are unaffected by *when* the reranker ships, only by *what it can do* once it does — but both are now explicitly blocked on `Qwen/qwen-reranker-8B`'s deployment rather than simply unstarted, since neither is empirically testable against a model that isn't callable yet.

**Superseded in part (v0.47, Tier-4 checklist C49 — §6):** `Qwen/qwen-embedding-8B` was also subsequently confirmed not deployed, so the "v0 launches on single-stage, embedding-only retrieval" description above is the state once the embedding model ships, not v0's actual state at this draft's own writing — right now, with neither model live, `search_code` is withheld from the offered tool set entirely. See §6/C49 for the resolution and the current, accurate three-step rollout.

**Superseded again (v0.65):** `search_code` is no longer withheld — `text-embedding-3-small`, reached directly outside the Gateway (§1/§2), fills the embedding-role gap this note and C49 describe, so v0 runs the single-stage form described two paragraphs above as its actual, current, offered state, not a future one. See §1 and §6's own v0.65 superseding notes for the full reasoning; this note stays for the historical record of how that gap was first found and tracked, matching this draft's own established practice of not rewriting superseded prose out of the document (see the v0.39→v0.41 registry-data-correction changelog entries for the same treatment).

**Compensating for no reranker, with a smaller default embedding tier (v0.65; tier-switching noted v0.66):** losing the rerank stage entirely, and defaulting to `text-embedding-3-small` rather than `-large` (§2's resolution), are two real, compounding precision constraints, not one — addressed with three mitigations, none requiring new mechanism beyond what this section already specifies. First, embedding `dimensions` truncation is declined: whichever tier is active, its full native output is kept rather than reduced for storage/cost savings (1,536 dimensions for `-small`, 3,072 for `-large` if the operator switches, §2) — this is exactly the situation where retrieval quality is scarcest and shouldn't be spent to save infrastructure cost. This mitigation and the third (below) apply regardless of which tier is active; only the second is `-small`-specific, and narrows automatically — without a spec change — if `-large` is ever activated, since `-large`'s own higher MTEB/MIRACL scores already close part of the gap this mitigation exists to cover. Second, `MAX_TOP_K` (already resolved at 15, C18, v0.56) is deliberately not tightened for this smaller pipeline — if anything, a design with genuine narrowing headroom to spare would tighten it, and this one doesn't have that headroom, so 15 stays the accepted, already-generous-relative-to-Continue.dev's-`nFinal=5` ceiling rather than being cut further; widening it beyond 15 was considered and declined, since `adaptive_top_k`'s own mechanical finding (§13 item 47) already shows every current pool model clears `MAX_TOP_K` comfortably; a wider ceiling would mean returning more, less-confidently-ranked results to the model with nothing having re-sharpened their order, trading noise for headroom the model would have to sort through itself. Third, `grep_search` is named a first-class complement, not a fallback of last resort, for exact-name/pattern lookups specifically — sidestepping embedding-quality risk entirely for the class of query it's weakest at (symbol names, literal strings), matching the "semantic search as a layer on top of, not a replacement for, lexical search" framing this draft already established for the `search_code`/`grep_search` split itself (§6's own ASSUMPTION).

**Resolved (v0.50, Tier-4 checklist C50 — closes §13 item 66, reranker half):** the same gap, mirrored for `Qwen/qwen-reranker-8B` going unreachable after being live rather than never deployed (C48's case). A second counter, same shape as §6's embedding-side one and sharing the same `retrieval_gateway_threshold` constant, tracks consecutive `GATEWAY_ERROR` results from calls to the live `role="reranker"` model specifically. Once it trips, two-stage retrieval degrades to the single-stage, embedding-only form C48 already specifies, for the rest of the trajectory — reusing C48's own mechanism (the same code path that already runs when no reranker-role model is present in the registry at all) rather than building a second degrade path, so `adaptive_top_k`'s existing trim-the-recall-stage-output behavior applies unchanged. Same reset semantics as the embedding-side counter (§6): resets to zero on a successful rerank call; one-way once tripped; not reset on a human resume, for the identical reason (a resume doesn't indicate the model recovered — only a fresh session's load-time re-probe does, v0.39). Same mechanical signal on the tripping call: `ToolResult.details` gains `retrieval_degraded_to_single_stage: true`, the reranker-side counterpart to §6's `retrieval_capability_withdrawn` field, same discipline (§5.2/C43).

**Dormant (v0.65):** this counter has nothing to trip against right now — no `role="reranker"` model is live on any path (§1), so there is no reranker-side `GATEWAY_ERROR` for it to count, and nothing to "degrade" a pipeline that already runs single-stage by design, not by fallback. The mechanism itself is unchanged and reactivates automatically, with no code change, the moment a reranker model is ever added to the live registry — the same "config presence is the only switch" discipline C48/C49 already established. §6's embedding-side counter, by contrast, stays fully live: `text-embedding-3-small`'s `direct_endpoint` calls (§2) can fail with `GATEWAY_ERROR` exactly as a Gateway-routed call can (§5.1's v0.65 broadening), so that counter keeps doing real work, now against a directly-routed model instead of a Gateway-routed one — no change needed there either, since the counter only ever cared about the `GATEWAY_ERROR` category, never about which transport produced it.

One shared constant rather than two independent ones: `retrieval_gateway_threshold` governs both counters, the same reasoning C43 already used for expressing `MAX_RERANK_CANDIDATES` in `RECALL_K`'s own unit rather than adding a second, separately-tuned number — both counters measure the identical kind of event (consecutive `GATEWAY_ERROR` against a retrieval-pipeline model), just against two different models, and nothing researched suggests they'd warrant different tolerances.

Considered and declined: a LiteLLM/`mcp-context-forge`-style time-based cooldown, retrying the dead model automatically after some interval rather than withdrawing/degrading one-way for the rest of the trajectory. Real precedent exists for exactly that shape — IBM's own `mcp-context-forge` gateway specs (github.com/IBM/mcp-context-forge#301, closed via #1070) a classic three-state closed/open/half-open circuit breaker with a time-based cooldown before a trial retry, the same shape LiteLLM's Router already uses and this draft already declined once for C47. Declined here for the same underlying reason, checked against a closer analog rather than just reasserted: `mcp-context-forge` is a persistent, multi-tenant gateway that amortizes a periodic recovery probe's cost across days of future traffic — an investment this architecture's short-lived, fresh-process-per-session topology (§1, v0.39) has no "future traffic" within one trajectory to pay back, and by the time a realistic cooldown elapsed, a bounded trajectory (`max_iterations`/`wall_clock_seconds`) is often nearly over anyway. The closer real analog — a single bounded agent loop, not a persistent service — converges on the simpler shape this resolution adopts instead: openclaw/openclaw#67399, a real incident report (an agent burning 3.57M tokens/~$70 calling a broken tool 754 times before anything intervened), was fixed with a per-tool consecutive-failure counter and a one-time action, scoped to the session, with no cooldown or automatic retry at all — the same shape adopted here, not copied blind but because the operating context actually matches.

Also considered and declined, for reasons already established rather than reargued: placing these counters in `Budgets` (§3.2) alongside `gateway_escalate_threshold`. C47's counter drives `escalate()`; these drive C48/C49's existing tool-availability/degradation mechanisms instead, which already live in §6/§9, not in `Budgets` — `Budgets` is the trajectory-wide numeric-ceiling dataclass for dimensions that escalate or abort through the shared suspend/resume path (§3.2's own framing), and neither of these counters does either. Keeping them where C48/C49 already are avoids stretching `Budgets`'s own scope for a mechanism that doesn't fit its actual job.

A same-pass gap check confirmed three things need no further change beyond a direct cross-reference: §5.4's suspend/resume trigger table needs no new row, since neither counter tripping pauses the loop — the trajectory keeps running in a reduced-capability mode, the same "never a suspend/resume event" reasoning C44's and C47's own gap checks already established for escalate-threshold breaches, extended here to a withdrawal/degradation event instead; §3.3's stuck-repeat detection needs no behavior change, only the cross-reference now added there directly — retrying after an `INFRA` failure, `GATEWAY_ERROR` included, still never makes a repeat *stuck*, and these new counters are simply a second, independent consumer of that same signal, not a new meaning for it; and `Budgets`' own `gateway_escalate_threshold` (§3.2, C47) is unaffected, since it only ever tracks the active chat/escalation-pool model, a disjoint population from the two retrieval-role models these new counters track. Updated §3.2 (cross-reference on the C47 paragraph), §3.3 (cross-reference), §5.1 (`INFRA` row), §6 (embedding-side resolution), §9 (this resolution), and §13 (item 66 resolved, new item 68).

**Resolved (v0.64, Tier-3 checklist C52 — closes §13 item 68):** `retrieval_gateway_threshold = 5`. This shares its research pass with `gateway_escalate_threshold` (C51, §3.2) but is deliberately not set to the same value, on reasoning named honestly as this draft's own extrapolation beyond direct precedent: no real system researched was found to pair a lower consecutive-failure threshold for a cheap, auto-recovering action against a higher one for a costly, one-way action, the way this spec's two placeholders are structured — real health-check/circuit-breaker systems keep their trip count roughly flat (2–5 across every source checked) and instead make the *consequence* itself auto-reversible (continued probing, cooldown-and-retry), a different mechanism than what withdrawing `search_code` for the rest of a session actually does here (deliberately no automatic recovery at all, per this section's and §6's own already-locked one-way design, above). The one real precedent found for a *stricter* bar specifically guarding a more consequential action is Envoy's own outlier-detection default of 5 consecutive gateway failures before ejecting a host from its pool entirely — a materially closer analog in shape to `retrieval_gateway_threshold` (session-long capability withdrawal) than to `gateway_escalate_threshold` (an ordinary move up an already-planned fallback chain). Named honestly: `5` rests on one strong analog plus this draft's own reasoning about differentiated cost, not the broad multi-source convergence `3` carries for C51 — if a single shared value is preferred for being more precedent-conservative, `3` (the modal number across nearly every source checked for either mechanism) is the defensible fallback.

**Resolved (v0.25, Tier-4 checklist C26 — closes §13 item 21):** tree-sitter backs the chunker, via a pre-built multi-language grammar bundle (e.g. `tree-sitter-language-pack`) rather than hand-compiling grammars per supported language. This isn't really a fresh choice so much as a confirmation of something this spec already leaned on without saying so: the cAST research paper already cited above (§12 item 12 deep dive) for the AST-chunking mechanism itself states directly that its own implementation "uses the tree-sitter library... for the AST tree parsing" — so the parser and the chunking mechanism it backs share the same real precedent, not two independently-argued choices. Every production RAG-for-code chunker researched converges on the same library: LlamaIndex's `CodeSplitter`, Continue.dev's chunker, Aider's repo-map, and Supermemory's code-chunk all use tree-sitter under the hood. It's also the real, converged-on answer to the underlying multi-language problem more broadly — one grammar format and one query API reused across (per community grammar bundles) 370+ languages, versus a bespoke native-parser integration per language (Python's `ast`, TypeScript's compiler API, `go/ast`, etc.), each with a different API and tree shape, multiplying integration effort by language count. Real adopters at this same "one parser, many languages, structural awareness" task: Neovim, Zed, Helix, Emacs, and GitHub itself, which built tree-sitter and used it internally.

Two real limitations are accepted rather than glossed over. Tree-sitter produces a concrete syntax tree, not a semantically-resolved AST — no type information, no cross-file symbol resolution. This doesn't matter for chunking specifically, since chunk boundaries only need structural nodes (where a function/class/method starts and ends); actual semantic/type correctness already goes through `get_diagnostics` (§6.3, Tier-4 checklist C25) as a separate mechanism entirely. And grammar quality/packaging is genuinely uneven across languages — most grammars are community-maintained, version-sync issues exist between how they're bundled for different ecosystems, and real native-binding build failures show up in the wild on newer language runtimes. Which exact grammar package and pinned version to trust per supported language is therefore left as its own residual placeholder (§13 item 56), not resolved by this choice of library.

**Resolved (v0.63, Tier-3 checklist C40 — closes §13 item 56):** adopt `tree-sitter-language-pack`, exact-version-pinned rather than left unpinned or floor-ranged — not a fresh choice, since this is already the example a bundle-approach was named after above, but now a specific package/version/pinning-discipline commitment grounded in real, current evidence rather than left as an illustrative name. As of this research (September 2026), it's actively maintained (currently `1.16.1`, under `xberg-io/tree-sitter-language-pack` on PyPI, having changed maintaining orgs twice), bundling 371 languages with a weekly-ish grammar-pin refresh cycle, and is the real package both Aider's repo-map and LlamaIndex's own `CodeSplitter` (both already cited for this section's chunking mechanism, C26) actually depend on in their real, current source — not a hypothetical option. Its predecessor, `tree-sitter-languages`, is confirmed dead: no release since February 2024, and a real filed issue against Aider's own `grep-ast` (#7) documents exactly the failure mode this section's own limitation-list already anticipated above — it left downstream users stuck on an old tree-sitter core version once it stopped shipping updates.

Exact-pinning, not just picking the bundle, is the real lesson this research surfaced: Aider's own dependency lockfile has drifted to a `tree-sitter-language-pack` version roughly ten months stale relative to current, an accident of an unconstrained-version dependency further upstream rather than a deliberate choice; and LlamaIndex's `CodeSplitter` source carries a live compatibility guard raising an explicit `ImportError` for exactly this reason — the package's own 0.x→1.x boundary was a real breaking change, not a hypothetical one. tree-sitter's own ABI churn compounds this: real, recent breakage incidents (Zed #24632, NixOS/nixpkgs #209114, Doom Emacs #8503/#8531) all trace to a parser compiled for one core ABI version failing to load against another, and `tree-sitter-language-pack` itself currently hedges by pinning most grammars at ABI 14 while a few (C++, C#) already sit at ABI 15 — a real, live inconsistency within the bundle itself, not a solved problem. Lucifer therefore pins an exact version of `tree-sitter-language-pack` (not a floor/range), bumped only deliberately, with each bump re-validated against the specific languages Lucifer actually needs (parser API shape plus per-language ABI compatibility) rather than trusted blindly — the same discipline Aider's own accidental drift and LlamaIndex's breaking-change guard both argue for by real counterexample. Full per-language individual pinning (the alternative named alongside the bundle approach above) wasn't found in real production use anywhere researched as anyone's *default* strategy — Aider uses it only for a handful of extras the bundle doesn't cover well, a fallback pattern worth keeping in reserve for Lucifer too, not the primary approach.

**Resolved (§12 item 12 deep dive, chunk granularity/composition — cross-check A5):** three previously-unspecified mechanism questions, each grounded in real code-retrieval systems researched for this rather than assumed:
- **Oversized symbols.** A symbol too large for one chunk is split by recursing into its own AST child nodes, not a sliding token-window — this is what two real code-chunking systems (the cAST research paper's structural approach, and a shipping AST-aware chunker) actually do, and it never risks splitting mid-expression the way a fixed window can. Small resulting sibling fragments are greedily re-merged so the split doesn't produce a scatter of tiny, low-value chunks. The old draft's own instinct that sub-chunks need linking back together is kept, but the mechanism moves to a pattern real production RAG systems already use for exactly this (parent-document retrieval): every sub-chunk of one oversized symbol shares a parent `chunk_id`; at query time, matches are deduplicated by parent and a parent's relevance is boosted when more than one of its children hits, rather than surfacing several disjoint fragments of the same function as unrelated results.
- **Chunk composition.** Beyond a symbol's own body, each chunk is prepended with its scope chain (e.g. `UserService > getUser`), its own signature, the specific imports it references, its file path, and its docstring/leading comment — adopted from a real shipping AST-chunker's exact convention (formatted as a comment-style header ahead of the code, before embedding) rather than invented here.
- **Non-code files.** Prose docs (README, markdown) are chunked by heading boundary — standard practice in general (non-code-specific) RAG, not something either code-chunking system researched for this actually addresses, since both are source-code-only. Structured config (YAML/JSON/TOML) has no comparably established convention: this draft proposes whole-file-as-one-chunk below a size threshold, falling back to a split by top-level key above it — a genuinely more provisional answer than the code-chunking mechanism above, flagged as such.

~~**ASSUMPTION (illustrative, not locked):** the config whole-file-vs-key-split size threshold, and the exact greedy-merge/size constants for oversized-symbol splitting, are unspecified placeholders — see §13.~~ **Resolved (v0.56, Tier-3 checklist C18):** both reuse one real ceiling rather than each getting an independently-invented number. The oversized-symbol greedy-merge target is `MAX_CHUNK_CHARS = 1_500` (equivalently `MAX_CHUNK_TOKENS ≈ 512`) — sibling fragments are merged back together as long as the combined result stays under this ceiling — taken directly from LlamaIndex's `CodeSplitter` (`DEFAULT_MAX_CHARS`/`DEFAULT_MAX_TOKENS`), the same real, currently-shipping tool already cited for the chunking mechanism itself (C26, v0.25) and for the cAST paper's own structural approach. A fragment is worth merging in the first place once it's under `MIN_MERGE_CHUNK_TOKENS = 128` (~25% of the ceiling) — no real precedent exists for this specific "how small before merging" question in anything researched (neither cAST nor the shipping chunker cited actually re-merges small siblings the way this draft's own mechanism does), so this is named honestly as this draft's own reasoned judgment, the same status `MAX_RERANK_CANDIDATES`'s ~1.5x scaling already carries. The config whole-file-vs-key-split threshold reuses the identical `MAX_CHUNK_CHARS = 1_500` ceiling rather than an independently-tuned fourth constant — close enough to general RAG's own real convention (roughly 250 tokens/~1,000 characters as a sensible default chunk size) that inventing a separate config-specific number wouldn't be better-grounded, only one more constant to carry; no config-format-specific convention exists in anything researched, confirming §9's own original framing that this half is more provisional than the code-chunking mechanism it sits beside.

- Files already edited in the current session are excluded from the persistent index's results and scored fresh instead — i.e., in-session edits don't go stale against the persistent index; they're just handled out-of-band (likely via `search_code` also doing a lightweight fresh pass over Workspace's staged content for those specific paths).

**Resolved (v0.32, Tier-4 checklist C32):** the fresh pass skips the embedding-based recall stage entirely for these files, rather than either fully re-embedding them or falling back to an unscored heuristic. Workspace's staged content for each in-session-edited path is chunked using the same AST/tree-sitter mechanism already specified above (C26) — no second chunking scheme — and those chunks are fed directly into the cross-encoder reranking stage (this section's second stage) alongside whatever candidates `RECALL_K` (§12 item 4) pulled from the persistent index, rather than being embedded and recalled through the first stage at all. Recall's only job is narrowing an index too large to score exhaustively; that problem doesn't exist for a handful of paths the harness already knows by name from `workspace.staged_paths()` (§7.2), so paying the embedding cost there buys nothing a direct feed into reranking doesn't already get for free. This also sidesteps the comparability problem a genuinely cheaper heuristic (e.g. plain lexical/grep matching) would introduce: mixing an ungraded lexical match into a cross-encoder-scored ranked list has no principled way to interleave the two, whereas feeding fresh chunks into the same reranker the persistent-index candidates already go through keeps every candidate on one shared, comparable relevance scale. `adaptive_top_k` (already resolved, §12 item 12 deep dive) trims the combined, reranked list exactly as it does today — no new stage, no new numeric placeholder. Grounded in real precedent, though not copied wholesale from any one system: Cursor's own incremental re-embedding (Merkle-tree diffing, content-hash-cached chunk embeddings) confirms production systems don't shy away from real recomputation over a small delta, but folds it back into one continuously-current index rather than treating it as a separate excluded category the way Lucifer's own locked decision already does. Sourcegraph Cody is the closer analog: it pulls snippets from currently-open files directly, with no embedding step at all — since it already has the full content in hand, there's nothing to search *for* — then merges them with its separately-searched remote results into one shared relevance ranking before returning results to the model; this draft's mechanism applies that same shape (skip the step that only exists to find content you don't yet have, unify everything through one shared scoring step) to Lucifer's own two-stage recall/rerank split specifically, since Cody's own unification step isn't itself documented as a cross-encoder rerank. A pure grep/lexical fallback — real precedent: VS Code's documented behavior when Copilot's own semantic index isn't available, "text search, grep, file search, and language intelligence" — was considered and declined for this specific case: that pattern is a designed *degradation* for when the index itself is unreliable, not the steady-state answer for content the harness already knows is in scope and can afford to chunk properly.

**Superseded (v0.65):** this mechanism's target — the cross-encoder reranking stage in-session-edited chunks were fed into alongside `RECALL_K`'s own candidates — no longer exists in v0's actual, current design (single-stage via `text-embedding-3-small`, above). In-session-edited files' chunks are now included unconditionally and unscored, alongside whatever `text-embedding-3-small`'s single recall pass returns for the rest of the index, rather than being fed into a shared cross-encoder scoring pass that doesn't exist to feed. This is a genuine simplification, not a downgrade of this mechanism's own reasoning: the original design's whole point was giving in-session content and persistent-index candidates one comparable relevance scale to interleave on, via the reranker; with no reranker, there's no shared scale left to construct in the first place, and a file the model is actively editing doesn't need a relevance score to justify surfacing it — the harness already knows it's in scope by construction. `adaptive_top_k` still trims the combined result exactly as before (below); the AST/tree-sitter chunking mechanism this resolution reuses (C26) is entirely unaffected. `MAX_RERANK_CANDIDATES` (C43/C46, below) is superseded the same way, for the same reason — see its own note.
**Resolved (v0.40, Tier-4 checklist C43):** a shared ceiling, `MAX_RERANK_CANDIDATES`, now bounds the *total* candidate count reaching the reranking stage in any one `search_code` call — combining both sources, rather than leaving the fresh-scored path (C32) uncapped alongside `RECALL_K`'s already-capped one. In-session-edited files' chunks are given priority within that ceiling, deterministically ordered by `workspace.staged_paths()` then by source order within each file (no relevance-based pre-filtering, which would need its own cheap scorer to decide what to drop before the reranker even runs); `RECALL_K`'s own persistent-index contribution fills whatever room remains, clamped to zero if staged content alone reaches the ceiling. `MAX_RERANK_CANDIDATES` is expressed in `RECALL_K`'s own unit (chunk count, not tokens) and scale, not as an independently-tuned constant, so the two move together once C14 (§12 item 4) resolves rather than drifting apart. When the combined pool exceeds the ceiling, the excess isn't silently dropped: `ToolResult.details` gains `staged_chunks_included`/`staged_chunks_total` and `recall_chunks_included`/`recall_chunks_total`, the same discipline already established for §5.2's output-size truncation and the B4 deep dive's multi-block `edit_file` failures — structured, mechanical, signaled through the existing envelope rather than a new one.

Grounded in two real, verified findings, not invented from scratch. First: production cross-encoder reranking APIs enforce hard input ceilings for exactly this reason, not as a hypothetical concern — Cohere's real Rerank API rejects a request outright once `document_count × max_chunks_per_doc` exceeds 10,000 (1,000 documents at the default `max_chunks_per_doc=10`). That means an uncapped candidate pool here isn't only a latency risk: once `Qwen/qwen-reranker-8B`'s own real limits are known (C14), Lucifer's current uncapped design could construct a request the reranker itself rejects outright, surfacing as `GATEWAY_ERROR`/`INFRA` (§5.1) with no clean recovery path — a real failure mode this resolution's graceful truncation avoids rather than a purely theoretical one. Second: the more commonly documented real pattern for merging multiple retrieval sources ahead of one reranking pass is each source contributing its own independently-capped top-k before combining — confirming per-source capping (which is what motivates giving the fresh-scored path a cap at all) is real, standard practice, not an invented constraint.

Worth being honest about what that second finding does and doesn't support: it confirms per-source capping generally, but it does not itself document the specific priority-merge shape adopted here — one shared ceiling with staged content taking precedence, rather than each source simply getting its own independent cap that just adds up. That specific shape is this draft's own reasoned design, not copied from a named system: chosen because it directly bounds the thing that actually needs bounding (total reranker workload, the concern C43 itself names) and because it naturally tracks `RECALL_K`'s real value once C14 resolves rather than needing a second, separately-tuned number. A simpler, more directly precedented alternative was considered and named rather than silently passed over: capping the fresh-scored path independently, at the same illustrative order of magnitude as `RECALL_K` itself, with the two capped sources simply combining — total bounded at roughly 2×`RECALL_K` rather than exactly `RECALL_K`. Declined in favor of the shared-ceiling version for a tighter, more predictable total bound at no real extra mechanism cost (one clamp instead of two independent ones) — a real judgment call between two defensible options, not a case where only one was viable.

`MAX_RERANK_CANDIDATES`'s exact numeric value is left as a new illustrative placeholder, the same status `RECALL_K` itself already has — see §13 item 62. This resolution closes C43 without waiting on C45 (§13 item 61, no bound on individual staged-file size): a session staging one unusually large file or many ordinary ones hits the same shared ceiling either way — C45, whenever it resolves, would only shrink how *often* the ceiling gets hit, not remove the need for it.

**Superseded (v0.65):** with no reranking stage in v0's actual current design (above), there is no candidate pool reaching a reranker for `MAX_RERANK_CANDIDATES` to bound — this mechanism, like C50's reranker-side counter just above, is dormant rather than deleted, reactivating with no code change if a reranker is ever added to the live registry (§1). In-session-edited chunks are included unconditionally instead, per C32's own v0.65 superseding note above; the persistent index's `text-embedding-3-small` recall pass is bounded by `adaptive_top_k(model)` directly (below), not by this ceiling. `MAX_RERANK_CANDIDATES`'s own placeholder value (C46, v0.53) is unaffected and stays recorded for the same dormant-path reason C14's own value does — see the closing resolution below.

- Every retrieval chunk and query is scoped by a stable repository identity, not just file path and symbol name — necessary once more than one repo can be indexed by the same Lucifer deployment.

**Resolved (§12 item 12 deep dive, `canonical_repo_id()` — cross-check A5):** derived primarily from the repo's git remote `origin` URL, not the local checkout path — a local path isn't stable across machines or sandbox instances, the same reasoning the old draft gave. Normalization is deliberately conservative rather than a full cross-scheme unification: lowercase the host, strip a trailing `.git` suffix, strip a trailing slash. Checked against a real, widely-used tool built for exactly this (npm's own `normalize-git-url` package) before assuming this was easy: it deliberately does *not* unify `ssh://` and `https://` forms or strip `.git` either, because full scheme-unification is a genuinely nontrivial problem even for dedicated tooling — so this draft doesn't claim to solve it either. Known, accepted limitation: two clones of the same repo added via different URL schemes get different canonical IDs under this scheme and would be indexed as if they were different repos. For a repo with no `origin` remote configured at all (a valid git state the old draft's own reasoning didn't cover), the fallback is the repo's root (first) commit hash — stable across machines for the same content-derived-not-path-derived reason the remote-URL preference already rests on.

- The persistent index's own staleness relative to the repo's current commit is tracked separately from per-chunk content staleness (i.e., "is the whole index behind `HEAD`" is a different signal from "is this one chunk's content current").

**Resolved (v0.68, Tier-4 checklist C54 — new item, closes §13 item 69):** confirms the `commit()`-time incremental-update trigger above as correct, and extends it to answer a genuine, previously-untracked question the original ASSUMPTION never addressed — how the persistent index gets built the very *first* time, for a repository Lucifer has never indexed before. Surfaced while walking through a concrete usage scenario (analyzing a brand-new repo for test-coverage reporting), not by a fresh design pass. Two cases that looked like they'd need separate answers turn out to be the same underlying condition: a brand-new repo with no index at all, and switching which embedding model is active (§2's v0.66 tier-switch, or a future Qwen-embedding activation) against a repo that already has one, built for a now-different model. The persistent index is keyed by both `canonical_repo_id()` (already established above) *and* the identity of the embedding model that built it, and "no index entry recorded for this `(repo, active_embedding_model)` pair" is the one condition that triggers a fresh, full build — covering a never-seen repo and a repo seen only under a different model with one shared mechanism, not one for each.

Grounded in standard, real RAG/vector-store practice, not invented for this case: production guidance for handling an embedding-model change converges on pinning the model's name/version in config and treating a mismatch as a mandatory full re-embed, since two different models' embeddings occupy genuinely non-comparable vector spaces that can never safely be mixed in one index — exactly the reasoning §2's own v0.66 "Operational consequence" paragraph already gives for why a tier switch needs a full rebuild rather than an incremental one. What's new here is only the mechanical form that reasoning takes: keying the index by model identity turns "does this index match the active model" into a fact the harness checks for itself, the same way `canonical_repo_id()` already lets it check repo identity — one dimension added to an existing key, not a new kind of check.

**Trigger point: lazy, on the first `search_code` call that needs it — not eager at session start.** The closest real precedent, checked rather than assumed, actually argues the opposite: Cursor builds its codebase index eagerly the moment a project is opened, not on a query, holding semantic search back — its own blog states it isn't available until "at least 80%" of that indexing work is finished — while the build runs in the background. Adopting that shape here was considered and declined, for a reason specific to how Lucifer itself is built, not a disagreement with Cursor's own reasoning: Cursor's eager build amortizes its own up-front cost over an IDE session that stays open and gets queried repeatedly for hours or days; Lucifer has no equivalent "project open" moment to amortize against — every session is already its own fresh, budget-metered process invoked for one specific task (§1's v0.39 topology), and plenty of real trajectories (fixing one lint error, running one specific test) never call `search_code` at all. Building the index unconditionally at every session start would mean paying Cursor's own documented cost — the same real precedent states large repositories without a shareable pre-built index "can require hours of processing" — on trajectories that never asked for semantic search, directly against the same "don't pay for a capability nobody asked for this trajectory" discipline this draft already applies to the dormant reranker seam (above) and to config-gated model activation generally (C48/C49). Triggering the build on the first `search_code` call that actually needs it instead means the cost is only ever paid by a trajectory that's actually using the capability — a deliberate divergence from the closest real precedent, named honestly as a divergence rather than overclaimed as a match.

**Blocking and signaling, not a background job.** This architecture has no persistent daemon or background-worker concept anywhere else in this spec (the same fresh-process-per-session topology that already ruled out a LiteLLM/`mcp-context-forge`-style cooldown-and-retry for this section's own reranker-degradation mechanism, above), so there's no mechanism to build the index off to the side while the triggering `search_code` call returns early — it blocks until the build completes, then answers the original query against the now-current index. The triggering call's `ToolResult.details` gains two new fields, `index_built: true` and `index_build_seconds: <float>`, the same structured-signal discipline already used for every other mechanically-detectable event this draft tracks (§5.2's truncation fields, C43's `staged_chunks_included`/`total`, C50's `retrieval_capability_withdrawn`) rather than a silent delay the model or a reviewer has no way to notice from the result alone. A failure during the build itself (a sandbox or filesystem error, say) surfaces through the existing `INFRA` taxonomy exactly like a failure in any other tool call (§5.1) — no new error category needed, since nothing about this trigger is a new *kind* of failure, only a new kind of work `search_code` sometimes has to do first.

**No new budget mechanism — the existing three already backstop this.** A same-pass gap check confirms §3.2's `Budgets` need no new field and §5.4's suspend/resume trigger table needs no new row: an index build that runs long is ordinary wall-clock and token consumption, not a new kind of event, and if it's slow enough to threaten `wall_clock_seconds`/`token_budget`, those two independent budgets already route to the same suspend/resume mechanism (§5.5) any other long-running stretch of a trajectory would — the same "a slower, already-existing backstop is an acceptable trade-off for not adding new machinery" reasoning self-audit A1 and C41 already used elsewhere in this draft. Cursor's own "can require hours" figure is worth taking seriously as a real, not hypothetical, tail risk for an unusually large repo — but it argues for nothing more than what already exists here.

**Narrows §2's v0.66/v0.67 "operator's responsibility" language accordingly:** with detection and triggering both automatic, the operator's real remaining responsibility after a tier switch (§2) is exactly "edit config, then restart" — the rebuild itself is no longer a separate manual step to remember or forget, closing a latent gap the original wording left as an implicit trust in the operator: forgetting a manual rebuild step would previously have meant either a silent mixed-vector-space index or a confusing failure at query time; now the very next `search_code` call after the restart detects the mismatch itself and rebuilds before answering, with no way to skip that step by omission. See §2's own narrowing note.

**Considered and declined: a separate manual "build the index" administrative command.** A dedicated provisioning step, run ahead of time by a human who'd rather pay a large repo's build cost predictably during a maintenance window than on a trajectory's first `search_code` call, is a real, defensible operational convenience — but not one v0 needs a new mechanism for. The lazy trigger above already correctly builds on demand, and an operator wanting to pre-pay that cost can already do so today with no new subcommand, simply by making one `search_code` call ahead of time (interactively, or via C27's non-interactive invocation, §10) — it hits the identical trigger condition and leaves the same fresh index behind for every trajectory that follows. A separate command doing the same thing through a second code path would be new surface for no behavioral gain, the same "reuse before inventing" restraint this draft already applies elsewhere (self-audit A1, B2, B6, and C40's own tree-sitter-pack choice over a bespoke per-language integration).
- Start with a lightweight vector store (pgvector or local FAISS/Chroma); a dedicated store is a later operational/scale decision, not a prerequisite for repo isolation (repo isolation comes from the repository-identity scoping above, not from store choice).

**Resolved (§12 item 12 deep dive, `adaptive_top_k` — cross-check A5):** the number of final reranked results returned to the model scales with the active model, not a flat constant:

```python
def adaptive_top_k(model: ModelSpec) -> int:
    return clamp(usable_budget(model) // AVG_CHUNK_TOKENS, MIN_TOP_K, MAX_TOP_K)  # usable_budget: §8, §12 item 11 deep dive
```

Deliberately reuses §8's `usable_budget(model)` (item 11's resolution) rather than adding a second per-model registry override: `usable_budget` already accounts for a model's *effective*, degradation-adjusted capacity, not just its raw `context_window`, so this needs no new field on `ModelSpec` (§2). Databricks' own long-context RAG research is direct support for making retrieval breadth model-dependent in the first place — it found retrieval quality actively degrading past a model-specific point, not merely plateauing, stating plainly that the right number of retrieved chunks "depends on both the generation model and the task." Worth being explicit about a distinction this could otherwise blur: this was originally a different knob from `RECALL_K` (§12 item 4) — `RECALL_K` governed how many candidates went *into* reranking; `adaptive_top_k` governed how many *final* reranked results came back out to the model. The two composed (recall pulls `RECALL_K` candidates, reranking scores them, `adaptive_top_k` trims what's actually returned) but resolved independently.

**Note (v0.65):** with no reranking stage in v0's actual current design (above), `RECALL_K` degenerates to the same value as `adaptive_top_k(model)` — the single recall call against `text-embedding-3-small` is now sized directly by this formula, rather than feeding a post-rerank trim. The formula itself, and its underlying reasoning (retrieval breadth should scale with the active model's usable budget), is unchanged; only what it feeds directly into is. `RECALL_K` stays a distinct, named parameter rather than being removed from the design, per the kept seam below.

In practice, `adaptive_top_k` will return `MAX_TOP_K` for all four real pool models under ordinary operation; the model-adaptive floor genuinely engages only under real budget pressure (deep into a long trajectory, close to the compaction threshold) or if a smaller-context model later joins the pool. That's not a defect in the mechanism resolved at §12 item 12 — the clamp is still real, correct protection for exactly those cases — but it means the ceiling, not the per-model formula, is what actually governs this number today, the same honest character C16's own clamp-collapse finding surfaced for `EFFORT_MAX_TOKENS`.
