## 5. Error Handling & Safety Model

### 5.1 Error taxonomy

Exactly three categories. Every error type maps to exactly one category — there is no separate "retryable" flag; retry behavior is fully implied by category.

| Category | Meaning | Loop behavior |
|---|---|---|
| `SELF_CORRECTABLE` | The model's call was wrong in a way the model itself can fix (bad path, bad args, ambiguous edit, disallowed command) | Feed back as observation; counts toward stuck-detection and tool-kind budget — one increment per failure, not two, and each threshold fires once on exact-equality — see §3.2 |
| `INFRA` | Something outside the model's control failed (sandbox crash, timeout, resource limits, gateway error) | Feed back as observation; never counts toward stuck-detection or the tool/verification-kind budgets — see §3.2. **v0.49/C47:** `GATEWAY_ERROR` specifically also counts toward a dedicated gateway-kind escalate counter; every other `INFRA` subtype stays fully excluded. **v0.50/C50:** a `GATEWAY_ERROR` from an embedding or reranker sub-call (`search_code`, §6/§9) also counts toward a separate, retrieval-specific withdrawal/degradation counter there — independent of the gateway-kind escalate counter above, which only ever tracks the active chat/escalation-pool model, a disjoint population from the two retrieval-role models. |
| `UNSAFE` | An actual safety-policy violation | Hard abort, trajectory ends, no override, no resume |

**ASSUMPTION — draft `error_type` enumeration** (the locked decisions establish the 3-category structure and pin one specific mapping — resource-limit violations → `INFRA`/`SANDBOX_ERROR` — but don't enumerate the full list; this is a starting proposal for review, not a locked decision):

```
SELF_CORRECTABLE:
  SCHEMA_VALIDATION_ERROR      # caught pre-dispatch, §5.6
  FILE_NOT_FOUND
  FIND_BLOCK_NOT_FOUND         # edit_file: find text absent
  FIND_BLOCK_AMBIGUOUS         # edit_file: find text matches >1 location
  PATH_OUTSIDE_REPO
  SENSITIVE_PATH_BLOCKED       # blocked write via edit_file/create_file, or blocked read/exec via run_command's argv/cwd (§6.2); also independently risk-flags, §5.4
  COMMAND_NOT_ALLOWLISTED      # includes blocked mutating git subcommands
  COMMAND_ARG_REJECTED         # e.g. network host not on the restricted-mode allowlist
  STALE_FILE_VIEW              # server-side staleness check failed, §7.2

INFRA:
  SANDBOX_ERROR                # includes memory/disk/process-count limit violations
  SANDBOX_SYNC_FAILURE
  COMMAND_TIMEOUT               # process-group kill, §6.2
  GATEWAY_ERROR                 # model API failure — also covers a truncated/incomplete response from an undersized per-call max_tokens (§4.4, B6 deep dive); also covers a failed direct_endpoint call (§2, v0.65) — one broadened category regardless of routing path, not split, see below
  NETWORK_ERROR                 # allowlisted host unreachable, as opposed to COMMAND_ARG_REJECTED
  INTERNAL_ERROR

UNSAFE:
  SAFETY_POLICY_VIOLATION       # kept deliberately narrow — hard-abort should be rare
```

**Resolved (v0.65):** `GATEWAY_ERROR` covers a failed call to a `direct_endpoint`-routed model (§2) exactly as it already covers a failed Gateway-routed one — broadened, not split into a second category. Every downstream mechanism that reads `GATEWAY_ERROR` (C47's active-model escalation counter, C50's retrieval-withdrawal/degradation counters, §3.2/§3.3's INFRA-exclusion rules) keeps working unchanged for `text-embedding-3-small` specifically without a single conditional added anywhere for "was this call Gateway-routed or direct" — the harness never needs to know or branch on that distinction once a call has failed, only which model failed and in what role. Grounded in real precedent rather than invented: LiteLLM's own unified exception-mapping normalizes failures from every backend it supports — a standard provider API, a self-hosted deployment, or a `custom_llm_server` — into one shared exception taxonomy regardless of transport, the same "one category, described broadly enough to be accurate, not one category per transport" approach `GATEWAY_ERROR` has used since it was first named a "model API failure," not a Gateway-specific one.

**Resolved (v0.2):** `PATH_OUTSIDE_REPO` and `COMMAND_NOT_ALLOWLISTED` stay `SELF_CORRECTABLE`, not `UNSAFE`. Both are pre-execution catches — validation that runs before dispatch, the same architectural slot as `SCHEMA_VALIDATION_ERROR` — so by the time either fires, nothing has actually happened; the guardrail worked. Both also sit in front of a second, independent backstop rather than being the last line of defense: `run_command`'s sandbox mount means even a successful escape only reaches a disposable copy, filesystem-isolated from the real repo (§6.2, §7.3), and the "nothing touches the real filesystem until `commit()`" staging invariant (§7.1) means an out-of-bounds `edit_file`/`create_file` path still has to clear the commit boundary before it could do anything — §7.6 now re-checks paths there too, as a second gate, so that boundary is real rather than assumed. Categorizing these `UNSAFE` would also cut off escalation entirely: the weak triage-tier model most likely to fumble into a blocked git subcommand or a miscounted relative path never gets the chance to retry or hand off to a stronger model, which undercuts the "escalation is the safety net, not the classifier" logic behind triage in the first place (§4.1). And the locked non-goal list already says a risk-based review interrupt isn't the same thing as `ErrorCategory.UNSAFE` (§11) — if the instinct is "a human should see this," §5.4's risk-flag mechanism is the intended path, not a hard abort. A *pattern* of these errors (not a single occurrence) is now an explicit risk-flag candidate — see §5.4.

### 5.2 Typed result envelope

Every tool result uses this envelope; the harness branches only on `error_type`, never on `message` text:

```python
class ToolResult:
    ok: bool
    error_type: ErrorType | None   # None iff ok
    message: str                    # human-readable, for the model/transcript
    hint: str | None                # optional correction guidance for the model
    details: dict                   # structured, tool-specific (e.g. matched line ranges)
```

**Resolved (B6 deep dive):** the model-invocation step itself (§3.1, before any tool call even exists) can also fail — e.g. a truncated response from an undersized `max_tokens`, §4.4 — and is represented the same way: an equivalent `ok`/`error_type`/`message`/`hint`/`details` structure, not a second, bespoke error shape invented for that one failure surface. Nothing was actually dispatched in that case, but the branching discipline (harness decides only on `error_type`) stays uniform either way.

**Resolved (§12 item 13 deep dive, output-size cap — cross-check A3):** any tool's captured output (`run_command` above all, but also an oversized `read_file`/`grep_search`/`search_code` result) is capped at a fixed character length before it's ever added to the transcript, not left unbounded. Grounded in real precedent rather than invented: Claude Code's own Bash tool caps captured output at 30,000 characters by default, via **middle-truncation** — the beginning and end of the output are kept, the middle is dropped — on the reasoning that errors and summaries most often live at one end or the other, not buried in the middle of a long run. This draft adopts the same shape and the same illustrative order of magnitude. Truncation is capture-time and mechanical, never model-involved, and doesn't change `ok`/`error_type` — the call still succeeded; only how much of its output survived into the transcript changed. It's signaled through the existing `details` field rather than a new envelope shape (the same discipline the B4 deep dive already applied to multi-block `edit_file` failures): `details` gains `truncated: bool`, `original_length: int`, and how much of the head/tail was kept. This is deliberately a different mechanism from §8's compaction tiering, answering a different question — a capture-time bound on one result's size, not how already-captured transcript content ages over a session — and was already flagged as such when §8 was resolved (§12 item 10 deep dive).

**Further resolved (v0.57, Tier-3 checklist C19):** the 30,000-character cap is confirmed, re-verified fresh against Claude Code's own current, live documentation rather than left on the original citation — `BASH_MAX_OUTPUT_LENGTH` defaults to exactly 30,000 characters (hard ceiling 150,000). That research also surfaced a real nuance worth naming honestly: Claude Code's actual mechanism is no longer the flat middle-truncation this draft attributes to it — successful command output is inlined up to ~30,000 characters and then spilled to a file with only a head preview (no real data loss, since the file can be read back), and only failed-command output gets true head+tail middle-truncation, at a smaller ~10,000-character budget. This draft's single flat mechanism (one cap, one middle-truncation rule, applied uniformly regardless of `ok`) was already a deliberate simplification, chosen over that kind of tiered/spill-to-file complexity at the time §12 item 13 was first resolved — that choice isn't reopened here, only the two numbers already flagged as placeholders within it. The head/tail split within the 30,000-character cap is now set to a symmetric 50/50 — 15,000 characters head, 15,000 characters tail — matching the one real, verified precedent found for this specific sub-question: OpenAI's Codex CLI splits its own output cap exactly 50/50 (10 KB / 256 lines total, 5 KB + 128 lines head, 5 KB + 128 lines tail), confirmed against the actual Codex source change that introduced it. No real precedent for an asymmetric split (e.g., weighting toward the tail on the theory that errors and summaries cluster there) turned up anywhere researched, including Claude Code's own undocumented ratio — so 50/50 is adopted as the grounded choice rather than inventing an asymmetry with nothing real behind it. `details.truncated`/`details.original_length` (already specified above) are joined by no new field: "how much of the head/tail was kept" is now simply 15,000 characters each, fixed rather than variable, so no separate accounting field is needed beyond `original_length` itself.

### 5.3 Error-budget abort signal

The abort signal returned by the error-budget check must be captured and acted on by the caller (the Orchestrator), never discarded — i.e. no code path may check the budget, see an abort signal, and silently continue the loop. See §3.2 for what "abort" actually routes to.

### 5.4 `UNSAFE` vs. "needs human approval" — distinct states

These are never routed through the same handling path:

| Trigger | State | Can a human override / continue? |
|---|---|---|
| `error_type` category `UNSAFE` | Hard abort | No — terminal, no override, no resume |
| Tool-kind abort threshold exceeded (§3.2) — stuck-repeat (§3.3) is one path into this counter, not the only one | Suspend | Yes — approve/guide/abort via §5.5; resume resets the counter (§3.2, C41) |
| Verification-kind budget exceeded (§3.2) | Suspend | Yes — resume resets the counter (§3.2, C41) |
| `max_iterations`/wall-clock/token budget exhausted (§3.2) | Suspend | Yes — resume grants an extended budget (§3.2, B3 deep dive) |
| Risk-flag triggered | Suspend | Yes |
| `done` files_changed mismatch (§3.4) | Review pause | Yes |
| External-repo drift detected at `commit()` (§7.6) | Review/pause | Yes — via §5.5 |

**Resolved (consistency check):** the tool-kind row previously read "Stuck-repeat budget exceeded" as if that were the trigger itself. It isn't — §3.2 is explicit that stuck-repeat detection (§3.3) just increments the same tool-kind counter that any other `SELF_CORRECTABLE` tool failure does, so a spread-out run of *different* tool errors reaches `tool_abort_threshold` exactly the same way a run of *identical* ones does. The old label made it easy to misread this as suspend-on-stuck-only, missing that the non-identical case suspends too — fixed to name the actual counter, with stuck-repeat as one path into it rather than the trigger. Also added the missing row for §7.6's `commit()`-time external-drift check, which already routes to this same suspend/resume path but had no entry in this table.

**Resolved (v0.19, Tier-2 checklist C7 — closes §13 item 11's remaining half):** risk-flag's criteria are four single-occurrence triggers — a trajectory pauses the first time any one of them fires, not on a repeated pattern (contrast the pattern-based policy-blocked-command trigger just below, a different mechanism resolved for a different reason back in v0.2): a blocked `SENSITIVE_PATH_BLOCKED` error occurring, as defense-in-depth even though the attempted access — a write via `edit_file`/`create_file`, or a read/exec via `run_command`'s `argv`/`cwd` since the consistency-check fix in §6.2 — was already blocked; an edit touching CI/deploy config or a dependency manifest; content matching a secret-like pattern, even outside a formally "sensitive" path; and, treated as the primary and best-evidenced of the four rather than a peer of the other three, an unusually large or deletion-heavy diff.

Grounded in two real signals, not asserted: Claude Code's own real "Auto mode" classifier explicitly skips risk-checking ordinary in-repo file writes/edits at all, reasoning that they're already "reviewable via version control" — logic that transfers directly here, since Lucifer already reviews every diff unconditionally via §7.5 regardless of risk-flag. That makes risk-flag's actual job narrower than a from-scratch safety net: surfacing a subset of trajectories to a human earlier than the end-of-task review, not replacing that review, which already exists either way. And an empirical study of 1,293 real agent-authored security pull requests found diff size/line-count a far stronger predictor of human rejection than whether a change touched a security-relevant keyword or domain (rejected PRs averaged 2,720 changed lines vs. 1,873 for merged ones) — real evidence, not just intuition, for why the fourth criterion is the anchor rather than an equal-weight candidate.

**Resolved (v0.62, Tier-3 checklist C39 — closes §13 item 55):** the fourth criterion's real numeric shape is `changed_lines > 400` (additions plus deletions combined, summed across every file in the current review round — the same aggregate-round scope C45/C34 already lock this criterion to, not any single file's size) **or** `deletion_ratio ≥ 0.5` (deletions at least half of the round's total changed lines); either condition alone fires the single-occurrence pause — the size and deletion-ratio dimensions are independent triggers, not a combined score.

The 400-line figure is real, not invented: it's GitHub's own production cutoff, converged on independently in two of its own shipped features — the diff viewer auto-collapses any file past 400 combined additions/deletions behind a manual "Load diff" click, and GitHub Copilot's PR-summarization feature independently excludes any file past that same 400-line mark from summarization. It also sits inside the classic code-review-effectiveness range: Google's own internal engineering-practices documentation calls 100 lines "usually a reasonable size" for a single changelist and 1,000 lines "usually too large," and the Cisco/SmartBear peer-code-review study (the widely-cited source behind "review in sessions under ~400 LOC, effectiveness drops past that") brackets the same 200–400-line zone from the opposite direction — three independent real sources landing in the same place. GitHub's own number is a *per-file* convention; this spec reapplies it at the *round* level instead, by design, consistent with C45's already-locked aggregate-round scoping — a round touching several modest files can cross 400 sooner than any one file would alone, but since this trigger only ever causes a pause for human review, never a block, that extra sensitivity is an acceptable, even intended, bias rather than a mismatch worth re-deriving a separate number to correct.

The 1,293-PR study already cited above for this criterion's existence was revisited specifically for a usable number and came back thinner than hoped, named honestly rather than overclaimed: its own regression gives diff size a real but weak predictive coefficient (0.049, dwarfed by other signals like title length), and it reports only two group means (2,720 vs. 1,873 lines) with no percentile breakdown, ROC-style cutoff, or deletion-specific figure anywhere in it — useful as corroboration that size matters at all, not as a source for this specific number.

The deletion-ratio half has no comparably real number anywhere researched, and is named honestly as this draft's own reasoned construction rather than external precedent: no git-hosting platform, CI security scanner, or coding-agent safety writeup found (including public postmortems of real agentic mass-deletion incidents) publishes a fixed deletion-ratio percentage as a standing rule. The one real, citable deletion-aware mechanism found — "Anomalicious" (Gonzalez et al.), an academic anomalous-commit detector that flags a deletion count more than two standard deviations from a repository's own historical baseline — is a genuinely more principled design than a flat ratio, but was considered and declined for v0: it requires tracking a per-repo historical-diff-statistics baseline, infrastructure this spec has no other use for and doesn't otherwise build, a disproportionate addition for one trigger's threshold. `deletion_ratio ≥ 0.5` (a diff that's at least half deletions) is adopted instead as the one self-evidently-defensible breakpoint available — a majority-deletion diff — rather than a researched figure, matching the same honest-placeholder-vs-precedent distinction this draft already draws elsewhere (C18's `MIN_MERGE_CHUNK_TOKENS`).

**Noted (v0.42, Tier-4 checklist C45):** whatever numeric threshold eventually fills this in, it is understood to score an aggregate review round (§7.5, broadened by C34 to every suspend/resume checkpoint), not any single file's absolute content size — so a small, targeted textual change to one already-enormous staged file is not itself unusual by this criterion's own logic. This is a known consequence of C45's own accepted no-individual-file-size-bound resolution (§7.7), not a separate gap to fix here.

**Resolved (v0.2):** a *pattern* of `COMMAND_NOT_ALLOWLISTED`/`PATH_OUTSIDE_REPO` failures reaching the tool-kind abort threshold (§3.2) is a confirmed candidate — surfaced with a specifically-labeled reason ("repeated policy-blocked command attempts"), not a generic tool-error message, so the reviewer immediately understands what tripped it. Deliberately *not* a single-occurrence trigger: pausing on the first blocked attempt would undercut the fast-tier-as-legitimate-first-attempt intent almost as much as `UNSAFE` would, just recoverably instead of fatally. If there's a separate governance need to know about every blocked attempt regardless of whether it ever becomes a pattern, that's better served by an operator-facing audit log decoupled from loop control flow entirely — mirroring the role `SANDBOX_ERROR`/`INFRA` telemetry would already need — rather than folded into this mechanism; audit/telemetry infrastructure itself stays outside this spec's scope. The rest of the candidate list above is now resolved separately — see the v0.19 resolution above.

### 5.5 Suspend/resume — one shared mechanism

Stuck, failing, risk-flagged, or budget-exhausted trajectories pause for human input through a single shared suspend/resume mechanism rather than each having bespoke handling. On resume, the human can: approve and continue, provide guidance that's injected as the next observation, approve a partial diff subject to the hold-the-round rule (§7.5), grant an extended budget when the pause was budget-driven (§3.2 — B3 deep dive), or abort the session outright (a human choice, distinct from the automatic `UNSAFE` hard-abort).

**Resolved (v0.38, Tier-4 checklist C41):** whichever of the first three resume options the human picks — approve and continue, guidance-injection, or partial-diff-approval — also resets the tool-kind and verification-kind abort-threshold counters (§3.2) to zero, one shared consequence of resuming through this one shared mechanism rather than three bespoke rules per option. See §3.2 for the full grounding.

**Resolved (B3 deep dive, wind-down step):** choosing "abort the session outright" — from whichever pause it's chosen, including a declined budget-grant request (§3.2) — triggers one forced final model call before the session actually ends: text-only, no tool schema offered, so it cannot take one more action on the way out. The model is asked only for what isn't already mechanically recoverable — what it was attempting, what's still blocked, its own read on the state — never asked to enumerate which files changed or restate a diff; that stays deterministic, rendered straight from Workspace (§7.2, §7.5), the same line §8's compaction rule already draws between tracked fact and untracked reasoning. `UNSAFE` is explicitly excluded from this: its hard-abort is immediate, with no further model call of any kind — forcing "one more turn to talk" after a safety violation would hand back exactly the trust `UNSAFE`'s "no override, no resume" semantics exist to withhold. A manual interrupt (Ctrl-C/SIGINT) is treated as the human exercising this same "abort outright" choice through a different input path, so it gets identical treatment — one shared trigger, not a separate case.

**Resolved (v0.30, Tier-4 checklist C30):** no new storage mechanism — the forced summary is simply appended to `transcript.jsonl` (§7.7, C28) as one more `(action, result)` entry, exactly like every other turn in the trajectory, and rendered live in the terminal as it's generated, the same way the CLI presenter already surfaces every other turn. Grounded in real precedent across every CLI-native agent researched with no product layer sitting on top of its own transcript: Claude Code's JSONL session log, Aider's plain-text chat history, and OpenAI Codex CLI's interactive rollout JSONL all treat a session's final message as nothing special — just the last line of whatever log already exists, no separate summary artifact. Real elevation to a more visible surface only happens where a genuinely different surface already exists for other reasons — GitHub Copilot's coding agent posts to the pull request it opens, a surface Lucifer doesn't have in v0 — or in an explicit automation flag, as with Codex CLI's `--output-last-message`, scoped specifically to its non-interactive mode. Persistence for later reading falls out of a decision already locked in rather than needing a new one: §7.7's abort-preservation resolution (C11, v0.23) already guarantees a true abort's session directory is never purged, precisely so a human can do a post-mortem — since the summary is now just the transcript's last line, it lands exactly where that post-mortem already looks. For the non-interactive invocation (§10, C27), if a wind-down step is ever triggered there, it composes with what §10 already says that mode does — "prints a final result" — rather than needing a new file or flag; this is noted as a natural fit, not a full answer, since whether/how non-interactive mode reaches a suspend/resume trigger at all with no human present to answer it is a separate, still-open question this pass doesn't address.

**ASSUMPTION:** `ask_user` (§6.4, a tool the *model* calls to proactively ask the human a question) is treated as sharing the same underlying pause/wait transport as the harness-triggered suspend/resume, just with a different trigger source (model-initiated vs. harness-initiated). This is a natural reading, not an explicit locked decision — flagged for confirmation, since it's plausible the two were intended as genuinely separate mechanisms.

### 5.6 Schema validation before dispatch

Malformed tool-call arguments are caught by JSON-schema validation against each tool's declared schema before the call ever reaches a tool executor. A validation failure never touches Workspace or the sandbox; it's returned to the model as a `SELF_CORRECTABLE` / `SCHEMA_VALIDATION_ERROR` result.
