## 4. Model Routing

### 4.1 Triage vs. escalation

Triage (initial model choice) and escalation (mid-trajectory model swap) are separate mechanisms with separate trigger paths — never conflated.

- **Triage** runs once, at trajectory start, and picks the starting model from the registry (§2).
  **Resolved (v0.18, Tier-1 checklist C2 — closes §13 item 8):** triage's mechanism is a fixed, operator-configured default starting model, not a task-complexity classifier or any other automatic heuristic. The model registry (§2) gains a new field, `is_default_triage_model: bool`, and exactly one chat-pool model must set it `True`; that's the model triage picks when no override is set. §4.2's starting-model override, when set, substitutes a different model for that one invocation/session — it isn't layered on top of some separate automatic mechanism underneath, because there is no separate mechanism underneath. This mirrors the reasoning just applied to `ESCALATION_PATH` (§4.3, v0.17): an operator-declared default is far cheaper to build and maintain than a real classifier, and there's markedly less to build one *from* here than there was for escalation. GitHub Copilot does run genuine automatic per-task routing — evaluating a task "across several dimensions like reasoning, code generation complexity, bug diagnosis difficulty, and tool orchestration needs" before picking a model — but the classification mechanism itself isn't publicly documented, so there's nothing concrete to adopt even if a more sophisticated triage were wanted. Claude Code, the closer precedent used throughout this spec, doesn't do automatic triage at all — a model is configured, and that's what runs. Building a Copilot-style classifier stays a real option for a future version, named explicitly rather than silently dropped (the same treatment kind-aware escalation paths got, §4.3) — v0 does not attempt it.
- **Escalation** runs mid-trajectory, triggered by the tool/verification/gateway escalate-threshold budgets (§3.2 — the gateway dimension added v0.49, Tier-4 checklist C47), and moves to the next model along a defined path.

**Resolved (v0.51, Tier-3 checklist C36 — updates §13 item 52):** `openai/gpt-5.6-luna` is the model that gets `is_default_triage_model=True`, chosen alongside — not independently of — C21's `ESCALATION_PATH` ordering (§4.3 directly below): it's that path's own starting entry, and triage's whole mechanism (this section, v0.18/C2) is exactly "pick the registry's flagged default starting model," so the two decisions share one answer rather than needing separately-argued ones. See §4.3/C21 for the grounding — real Intelligence Index and pricing data placing it within one point of this deployment's strongest configured model at roughly a twelfth of the cost.

**Resolved (self-audit A3):** the reason triage doesn't need to be conservative is that escalation, not triage, is responsible for catching a trajectory where the current model turns out not to be capable enough — the fast/cheap tier is a legitimate first attempt precisely because a struggling trajectory has a path up from there, not a dead end. This is also why §5.1 avoids treating a policy-blocked action (`PATH_OUTSIDE_REPO`, `COMMAND_NOT_ALLOWLISTED`) as `UNSAFE`: doing so would cut a struggling weak-tier model off from ever reaching escalation, foreclosing the exact recovery path this section describes.

### 4.2 Overrides

- An explicit starting-model override (e.g. a CLI flag/config value) affects **triage only** — it pins the first model chosen, nothing else.
- Escalation stays active by default even with a starting-model override set — a pinned start can still escalate up if the trajectory struggles.
- A **separate, explicit hard-pin flag** disables escalation entirely, keeping one model for the whole trajectory. This is a distinct flag from the starting-model override; setting the override alone does not imply the hard-pin.
- **Resolved (v0.18, Tier-1 checklist C2):** "no override set" now has a concrete meaning — the registry's `is_default_triage_model` (§4.1) runs. The override was always specified as pinning *the first model chosen*; it now pins over a real, config-driven default instead of an unspecified one. **ASSUMPTION (validation, not locked):** exactly one chat-pool model having `is_default_triage_model=True` is checked at load/startup, the same treatment §4.3's `ESCALATION_PATH` validation got (v0.17) — zero or more than one is a config error, not a runtime fallback. §13 item 52.

### 4.3 Escalation path and ceiling

```python
ESCALATION_PATH: list[str]  # ordered, weakest → strongest; not required to include every candidate model
def escalate(current: str) -> str:
    idx = ESCALATION_PATH.index(current)
    if idx == len(ESCALATION_PATH) - 1:
        return current  # no-op at the ceiling — never an error
    return ESCALATION_PATH[idx + 1]
```

**Resolved (v0.17, supersedes the B2 deep dive — operator-declared ordering):** `ESCALATION_PATH` is populated by explicit operator/deployment configuration, not derived from any benchmarking process this spec defines or any runtime component computes. Whoever administers the model registry (§2) declares the ordered list of model IDs directly — e.g. alongside the registry entries themselves, in the same deployment config surface — and the agent follows that declared order mechanically; the `escalate()` logic above is unchanged, only how the list gets populated changes.

This replaces the B2 deep dive's answer — a composite-scored ordering built from `tool_call_reliability` plus coding-task correctness, benchmarked against Lucifer's own schema — outright, not just refines it. The v0.4→v0.5 changelog entry recorded that criterion as tracing to a locked decision ("the locked decisions explicitly say needs real benchmark data"); this change is a deliberate amendment to that locked position, made explicitly by the same authority who set it, not a silent reinterpretation of it. Two reasons motivated the change: an operator-maintained list is simpler to keep current as models are added to or deprecated from the registry than a benchmarking pipeline that would need re-running (or re-trusting) on every roster change; and it matches real precedent for the closest production analogue — Claude Code's own multi-model fallback chain (`fallbackModel`, an ordered array) is explicitly operator/user-declared, not benchmark-derived ("the order of the array is the order Claude Code tries, so the array is a priority list, not a set... users choose their chain based on preferences like capability-first or cost-first optimization"). GitHub Copilot's model auto-selection is a different mechanism still (one up-front per-task routing choice, deliberately no mid-task escalation at all) but is likewise not benchmark-derived at the ordering level — neither production system researched here runs the kind of internal quality-benchmarking pipeline the B2 criteria envisioned.

- `ESCALATION_PATH` is still not required to include every candidate model (unchanged from B2) — an operator can omit a model from the path entirely, e.g. one they don't trust as an escalation target at all.
- **ASSUMPTION (validation, not locked):** the config is validated at load/startup, not at escalation time — every model ID in `ESCALATION_PATH` must already exist in the registry (§2) and have `supports_tool_calling: true`; an unresolvable entry (a typo, or a model since removed from the registry) is a startup config error, not a runtime fallback or a silent skip. This is what actually delivers the "easier to maintain" benefit named above: deprecating a model becomes a forced, visible edit to this config (the startup check fails until the path is fixed) rather than a stale reference nobody notices until an escalation tries to reach it mid-trajectory.
- **ASSUMPTION (ordering guidance, not enforced):** nothing in this draft validates that an operator-declared ordering is actually monotonically improving. The B2-era caution about a lateral move risking "repeating the same failure with different wording" is retained as *advice* to whoever configures the list, not as a property this draft's mechanism checks — checking it would require exactly the kind of benchmarked quality signal this change moves away from needing.

**Considered and deferred (B2 deep dive; unaffected by the v0.17 change above):** a *kind-aware* escalation — separate paths for tool-kind vs. verification-kind failures, each optimized for its own axis — was considered instead of one single path. Deferred for v0: the locked decision describes escalation as following "a defined path with an explicit ceiling" (singular, both times), which reads as one total order, not two. That reasoning turns on the path being singular, not on how it's populated, so it holds under operator-declared ordering the same way it held under composite-scored ordering — still deferred, for the same reason. (If ever revisited, an operator-declared config would make a bifurcated path a smaller lift than it would have been under B2's approach — two operator-maintained lists instead of two benchmarking passes — but that's a note for a future version, not a reason to reopen this now.) Recorded here so it isn't silently re-proposed later without the reason it wasn't adopted being visible.

**Resolved (v0.51, Tier-3 checklist C21 — updates §12 item 7):** the real ordered sequence, populated with real model IDs from §1's registry rather than left unpopulated — `["openai/gpt-5.6-luna", "Qwen/Qwen3.6-27B", "ibm-granite/granite-4.1-30b", "openai/gpt5.4"]`. `google/gemma-4-26B-A4B-it` — a candidate per §1's ASSUMPTION, since it does support tool-calling — is deliberately left out of the path entirely, exercising the "not required to include every candidate model" option above rather than leaving a weak entry in.

Unlike the deployment-internal facts C12/C13 supplied directly (several registry names have no public spec sheet to check against), all five candidate models here turned out to be real, publicly documented, currently-shipping models — grounded in actual research, not invented benchmarking or unverifiable operator assertion. Primary source: Artificial Analysis's Intelligence Index, the one metric available across all four selected models on a single consistent methodology — `openai/gpt-5.6-luna` 52 (OpenAI's own explicit cheapest/fastest GPT-5.6 tier, $0.20/$1.20 per 1M tokens in/out), `openai/gpt5.4` 53 (highest of the four, $2.50/$15.00 per 1M — roughly 12x Luna's price for one point of Intelligence Index), `Qwen/Qwen3.6-27B` 38 (open-weight reasoning model, $0.60/$3.60 per 1M via its API, also self-hostable), `ibm-granite/granite-4.1-30b` 9 (open-weight, self-hosted, no API price). `google/gemma-4-26B-A4B-it` isn't on a directly comparable Intelligence Index score from the same source, but its own numbers point the same direction regardless: strong general-knowledge/instruction-following (GPQA Diamond 79.2%, IFBench 72.4%) paired with a real, specific weakness on exactly the axis this pool needs — agentic/tool-calling performance (TerminalBench Hard 13.6%, τ²-Bench 43.6%, coding-specific rank #96/205) — a role mismatch, not a general capability shortfall, and the reason it's excluded here despite being cheaper than every other candidate.

`openai/gpt-5.6-luna` opens the path (and is also `is_default_triage_model`, §4.1) rather than a cheaper-but-weaker alternative: it scores within one point of `gpt5.4`'s own Intelligence Index at roughly a twelfth of the price, and carries real documented coding-agent numbers (Coding Agent Index 74.6, Terminal-Bench 2.1 84.7%) close behind the top tier of its own model family (Sol: 80/88.8%). Its one documented weakness — an MRCR long-context-recall score of 41.3%, well below its other numbers — is a real, named trade-off, not a hidden one: accepted here because it's the kind of gap this spec's other mechanisms already exist to backstop (escalation itself, plus §8's compaction keeping working context bounded), not because it's immaterial.

Worth being honest about where this ordering is *not* a clean, single-axis benchmark ranking, per the ordering-guidance ASSUMPTION above (§13 item 51's advisory caution against assuming an operator-declared path is automatically monotonic): `ibm-granite/granite-4.1-30b`'s Intelligence Index (9) sits below `Qwen/Qwen3.6-27B`'s (38) immediately ahead of it in this path — on that one metric, this is a lateral-or-backward step, not a strict improvement. Kept anyway, deliberately: IBM markets this model family specifically on instruction-following and tool-calling efficiency rather than raw reasoning-benchmark performance — the same axis `tool_call_reliability` (§2, C6) exists to capture, and the one the B2 deep dive originally argued matters most for this exact question, since escalation targets respond to tool-kind failures particularly (§3.2). No real per-model `tool_call_reliability` measurements exist yet to confirm this directly — that field stays an unpopulated placeholder, unaffected by this resolution — so this step is a reasoned bet on a different, real capability axis, not a benchmark-confirmed one; an operator with real tool-call-reliability telemetry on these two models could reasonably reorder or drop this step, and `ESCALATION_PATH`'s own mechanism (unchanged) supports that with no code change either way.

`openai/gpt5.4` closes the path as ceiling model despite OpenAI's own public documentation now listing it deprecated in favor of GPT-5.5: it's still the model actually present in this deployment's registry (§1, confirmed real per C13), and swapping the registry entry itself is an operational Gateway decision outside this spec's own scope — flagged here for the record, not resolved, since nothing about `escalate()`'s mechanism depends on which specific model occupies the ceiling slot.

### 4.4 Effort as a per-invocation parameter

Model "effort" (e.g., a reasoning-effort dial) is a parameter passed on each individual invocation, not a fixed attribute of a chosen model — the same model can be called at different effort levels at different points in the trajectory.

**Resolved (B6 deep dive):** formalizes what this section previously only stated in prose, and closes the cross-check's B6 divergence (the old draft scales `max_tokens` by effort; this draft had no per-call token ceiling of any kind, at any effort level):

```python
EffortLevel = Literal["low", "medium", "high", "xhigh", "max"]

class InvocationParams:
    model: str
    effort: EffortLevel
    max_tokens: int   # this call's ceiling — reasoning + visible output together

EFFORT_MAX_TOKENS: dict[str, dict[EffortLevel, int]]  # per-model, resolved v0.54 (Tier-3 checklist C16) — each model's own five tiers, scaled off its own registry max_output_tokens (§2), not one scale shared flat across models
EFFORT_MAX_TOKENS = {
    "openai/gpt5.4":               {"low": 4_000, "medium": 8_000, "high": 16_000, "xhigh": 24_000, "max": 32_000},
    "openai/gpt-5.6-luna":         {"low": 4_000, "medium": 8_000, "high": 16_000, "xhigh": 24_000, "max": 32_000},
    "ibm-granite/granite-4.1-30b": {"low": 1_000, "medium": 2_000, "high": 4_000,  "xhigh": 6_000,  "max": 8_000},
    "Qwen/Qwen3.6-27B":            {"low": 1_000, "medium": 2_000, "high": 4_000,  "xhigh": 6_000,  "max": 8_000},
}  # ~12.5/25/50/75/100% of each model's own max_output_tokens (§2) — only populated for the triage/escalation pool (§4.3), the only models max_tokens_for() is ever invoked against

def max_tokens_for(model: str, effort: EffortLevel) -> int:
    return min(EFFORT_MAX_TOKENS[model][effort], registry[model].max_output_tokens)  # defensive clamp — by construction already equal to the ceiling at "max," but stays in place as cheap insurance against the table drifting out of sync with §2
```

**Further resolved (v0.54, Tier-3 checklist C16):** `EFFORT_MAX_TOKENS` becomes a per-model table rather than one shared flat scale — the checklist's own framing ("real per-model, per-effort-level values") turned out to name a real schema gap, not just a missing set of numbers. Cross-checking the placeholder flat scale against §2's now-real `max_output_tokens` values (C12, v0.44) showed `high`/`xhigh`/`max` collapsing to an identical clamped 32,000 for the two 32,000-ceiling models (`gpt5.4`, `gpt-5.6-luna`), and `medium` through `max` collapsing to an identical clamped 8,000 for the two 8,000-ceiling models (`granite-4.1-30b`, `Qwen3.6-27B`) — four of five tiers indistinguishable for half the escalation pool. Each model's own five tiers are now set proportionally against its own registry ceiling (~12.5/25/50/75/100%), which keeps all five tiers genuinely distinct for every model rather than fitting one shared curve that can't serve both a 32,000-ceiling and an 8,000-ceiling model at once. This leans on real precedent rather than an arbitrary split: Claude's own `effort` parameter — a five-level `low`/`medium`/`high`/`xhigh`/`max` enum structurally identical to this one — documents `max_tokens` as a separate, explicitly-set hard ceiling from effort itself ("set large `max_tokens` at `high` and above"), and Claude's extended-thinking docs recommend 16,000+ tokens as a real starting point for complex tasks with a ~32,000 soft ceiling before batch processing is needed — both land close to this table's own `high`/`max` values for the two 32,000-ceiling models, not chosen to match but a reassuring landing point given they weren't derived from Anthropic's numbers at all. OpenAI's `reasoning.effort` docs, by contrast, give no fixed numbers at all — effort there is explicitly adaptive to task complexity rather than tied to a fixed per-tier ceiling — and a real empirical benchmark (a community test of DeepSeek V4-Pro's own effort levels, openclaw/openclaw#75706) found token consumption non-monotonic across tiers in practice, the same honest caution this draft already applied to `ESCALATION_PATH`'s own non-monotonic step (C21, v0.51): these are reasoned, evidence-grounded numbers, not measured facts about Lucifer's own four models at this deployment. `max_tokens_for()`'s clamp against the registry ceiling stays in place even though it's now a no-op by construction at each model's own `max` tier — cheap insurance against a future hand-edited table drifting out of sync with §2, the same reasoning that kept `tool_call_reliability` carried as a currently-unread field (C6, v0.18). Only the four triage/escalation-pool models are populated; `max_tokens_for()` is never invoked outside that pool (§2), so `google/gemma-4-26B-A4B-it` — real per §2, but deliberately excluded from `ESCALATION_PATH` (C21, v0.51) — needs no entry here either.

Two real systems confirm this is a correctness requirement, not a cost-hygiene nicety: reasoning tokens are billed as output tokens and count against the per-call ceiling in both OpenAI's reasoning-effort models (an undersized ceiling returns a truncated, `incomplete`-status response — tokens spent, nothing usable) and Claude's extended thinking (the thinking budget must be smaller than `max_tokens`, a hard constraint at the request level). Sizing a call's token ceiling to its effort level is therefore something the harness must do on every invocation, not an optional refinement — hence `max_tokens` moving from "absent" to a required field on `InvocationParams`, not just a `token_budget`-adjacent note.

An invocation whose response comes back truncated/incomplete because `max_tokens` was undersized for the effort requested is categorized `INFRA` — reusing `GATEWAY_ERROR` (§5.1) rather than adding a new `error_type`: it isn't something the model got wrong (the model doesn't choose its own ceiling) and isn't a safety issue, so it gets the same self-audit A1 treatment as any other `INFRA` failure — it doesn't feed the tool/verification-kind escalate/abort budgets, it just consumes an iteration and wall-clock time, and a pathological run of these is still caught by `max_iterations`/`wall_clock_seconds` (§3.2), which already route to the resumable suspend/resume path. `GATEWAY_ERROR` ("model API failure") already implicitly covered invocation-level failures before this resolution — what's actually new is that §3.1's loop pseudocode never showed a branch for it: the loop previously assumed `model.next_action(...)` always returns a usable action, with error handling shown only around tool dispatch. This resolution is what makes that branch explicit, reusing the pre-existing category rather than introducing a new failure surface (§5.2 now notes the same typed-envelope shape applies there too, even though nothing was actually dispatched).

`token_budget` (§3.2) itself is untouched by this: it stays a flat, effort-agnostic cumulative ceiling across the whole trajectory. A trajectory that spends more of its turns at high effort simply depletes it faster — that's an expected consequence of B3's resolution making budget exhaustion resumable, not a gap this needs its own mechanism for. (§3.2 resolves the cross-check's other B6 sub-question: no new budget dimension, but a `token_budget`-driven resume does now show a deterministic per-effort-level invocation tally alongside the raw count.)

**ASSUMPTION (open interaction, not specified):** whether escalation (model swap) and effort-bumping (same-model retry at higher effort) are independent axes that get tuned separately, or whether an escalation event always also resets effort to a defined level on the new model, is not stated by the locked decisions. This draft treats them as orthogonal — escalation picks the model, effort is set per-call by whatever policy invokes it — but flags this as needing an explicit decision.
