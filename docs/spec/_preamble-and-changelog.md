**Changelog (v0.6 → v0.7):** resolved B3's second sub-question — the "graceful wind-down step" — via deep dive, informed by researching how GitHub Copilot's own SDK and cloud coding agent actually handle this (real precedent, not assumed: the SDK's credit-budget resume is deterministic-info-only, no forced model summary, while the separately-documented cloud coding agent forces a wrap-up summary specifically when a run is genuinely ending, not resumed). Adopted that same split for Lucifer, re-anchored to this spec's own structure rather than copied wholesale: since B3 already made all budget exhaustion resumable, "a run actually ending" can only mean a human choosing "abort the session outright" (§5.5) — including a declined budget-grant request — never a pause by itself. **Changelog (v0.7 → v0.8):** resolved the cross-check's B4 divergence (`edit_file`'s multiplicity) via deep dive, again informed by real precedent — Claude Code's own shipped tools (a simple single-edit tool plus a separate, atomic, sequentially-applied `multi_edit` for the batch case) versus Desktop Commander's `edit_block`, which deliberately stays single-block-per-call on the philosophy that edits should stay small and focused. Updated §6.1 (the schema and mechanism) and §3.3 (generalized "identical attempt" to compare the whole ordered block list, not a single block); split §13 item 14 — the block-multiplicity half is now resolved, the occurrence-index/replace-all half stays open, unchanged — and added items 32–33 for the residual `details`-shape gap and the considered-and-declined 11th tool. Closed by stating the check runs once per call, against pre-call state, not re-evaluated between blocks (§6.1) — no other content changed.

**Changelog (v0.8 → v0.9):** resolved the cross-check's B5 divergence (verification baseline capture timing — eager vs. lazy) via deep dive. Chose eager, but anchored precisely to Workspace's first staged edit rather than to literal session start: the suite runs once, right before that first edit would land (whether from an explicit `edit_file` call or a detected `run_command` side-effect per §7.3), reusing the pre-command sandbox state §7.3's change-detection already inspects before every `run_command` — no new mechanism, and no cost for a session that never stages an edit or that spends several turns on read-only exploration first. Considered and declined the old draft's lazy alternative (deferring capture to the first `done` call): by then the sandbox is no longer pristine, so a true baseline would require reverting and restoring the live sandbox's staged edits or standing up a second throwaway sandbox — mechanism nothing else in this spec needs — and would concentrate that cost inside whichever `done` call happens to be first, roughly doubling its sandbox work right when the model is trying to close out the task. Named the one case eager/first-edit doesn't save that lazy would have: a session that stages at least one edit and is then abandoned before ever calling `done` still pays the baseline cost. Updated §3.5 (the resolution and rationale) and §7.3 (a cross-reference noting the shared checkpoint); split §13 item 7 — the capture-timing half is now resolved, the verification-suite-source (config vs. auto-detect) half stays open, unchanged — and added item 34 for the mechanism this introduces (detecting the trigger condition concretely, not just as an ordering property in prose). A consistency check afterward found one real gap: the resolution's own wording anchored the trigger to "Workspace's first staged edit," which is fine for `edit_file`/`create_file` but operationally incoherent for a `run_command` side-effect, since §7.3 only ever discovers those *after* the command has already executed — there is no way to capture baseline "before" a specific call once the harness already knows, in hindsight, that it produced the first edit. Also found: the original wording never mentioned `create_file` at all, even though it's the third mutating tool (§6) and its own first call is just as valid a trigger as `edit_file`'s. Fixed by re-anchoring the trigger to dispatch rather than outcome — baseline runs once, before the first call to any of the three mutating tools (`edit_file`/`create_file`/`run_command`), regardless of what that call turns out to do — which is mechanically simpler (a plain tool-name check before dispatch) and resolves §13 item 34 outright rather than leaving it open. Updated §3.5, §7.3, and §13 item 34; no other content changed.

**Changelog (v0.12 → v0.13):** resolved §12 item 10 (compaction's tiering/eviction mechanism, cross-check A4) via deep dive, grounded in real precedent researched for this specifically: Anthropic's own server-side compaction (one model-generated summary replacing everything before a cut point, plus a separate fixed-length truncation-with-marker for an individually oversized tool result — no tiers, no fact/prose distinction), a production coding-agent context-management writeup converging on the same shape, and Google's Agent Development Kit's "memory pointer" pattern (large tool output written to external state, model gets back only a short key) as the one real precedent for genuine reference-eviction. Declined Anthropic's design for the same reason this draft already gives for rendering file-touch/action-history facts deterministically rather than asking a model to restate them: a coding agent's compaction risks a misremembered file body or function signature silently corrupting a later edit, a correctness cost general chat-style compaction doesn't carry. Declined the truncation-with-marker design for an unrelated reason — it bounds one oversized result at write time and can't be reissued to recover what it drops, answering a different question than aging transcript content, one §12 item 13 already tracks separately. Adopted a scaled-down version of the ADK pattern rather than the pattern itself: no external store, since Lucifer's five non-mutating tools are already deterministic, idempotent reads against state that already persists (the sandbox, Workspace, the retrieval index), so a pointer just naming the original call is enough to make it recoverable. The result (§8): everything outside the protected tier now goes through drop-entirely (resolved infra retries; superseded intermediate verification runs) and reference-eviction (aged-out non-mutating-tool output → a recoverable pointer) before whatever's left — genuinely untracked reasoning — gets the pre-existing narrow model-summarization pass, in that order, so the mechanical tiers shrink what the lossy step ever has to touch. Updated §8 (the resolution, considered-and-declined, and ASSUMPTION notes) and §12 item 10 (marked resolved, struck through, pointing back to §8); added §13 items 41–43 for the newly-illustrative pointer format and recency-only "superseded" definition.
